# Module A16. Shipping agents

> **Level:** Senior AI · **Time:** ~50 minutes · **Format:** situation → theory → practice → quiz

---

## 🏢 The situation

You found a way to improve the emails: the new prompt version scores +9% on personalization against the golden set. You ship it Wednesday morning and go for coffee.

By lunch Igor writes: "The emails got weird. Half are fine, half read like a different person wrote them."

You look: prompt v4 really is better on the golden set. But in production it met cases the set did not contain — leads with no trigger event, where v3 refused to write and v4 started inventing a hook. The metric went up, the product got worse.

Worse still, you cannot roll back quickly: v4 has already queued 200 emails, some sent, some awaiting approval. Timur asks: "Do you even have a 'yesterday' button?"

## 🎯 Your task

1. Ship changes so they reach a fraction of traffic first.
2. Have a real rollback — by config, not by another deploy.
3. Understand that an agent versions more than code.

---

## 📚 Theory

### What counts as a version here

In an ordinary service the version is a commit. An agent's behavior is set by at least five independent things:

| What | Changes | Who usually changes it |
| --- | --- | --- |
| Pipeline code | With a release | Engineer |
| Prompt version | Separately from code (A4) | Engineer, sometimes PM |
| Model and its version | By the provider too! | The provider, without asking you |
| Tool schemas | With a release | Engineer |
| The RAG knowledge base | Constantly | Marketing, support |

Two consequences. First: **pin the model version explicitly**, never "latest". Second: write all five versions into the trace (A14) — otherwise "what changed between yesterday and today" has no answer.

### Separating deploy from release

The key practice: **deploy ≠ release**. Code with the new prompt version ships switched off and is enabled by config. Then:

- rollback needs no deploy and takes seconds;
- one build serves both versions, so the comparison is fair;
- you can enable the new version for internal users only.

For agents this matters more than for ordinary services: you will flip back and forth more often, because quality is not binary.

### Idempotency during rollback

A rollback mid-flight leaves some tasks done by the new version and some by the old. From A13 we have task keys; here we add a rule: **the version is pinned when the task starts and never changes mid-run**. A task begun on v4 finishes on v4 even if v3 was globally re-enabled. Otherwise you get an email assembled half by one set of rules and half by another.

## 💻 Practice

```python
import os, json, hashlib, time

# --- Rollout config: lives outside the code, changes without a deploy ---
# rollout.json: {"outreach_prompt": {"stable": "v3", "canary": "v4", "percent": 5,
#                                    "force_users": ["igor@datacore.io"]}}
class Rollout:
    def __init__(self, path="rollout.json", ttl=15):
        self.path, self.ttl, self._at, self._cfg = path, ttl, 0, {}

    def cfg(self, key):
        if time.time() - self._at > self.ttl:            # re-read without a restart
            self._cfg = json.load(open(self.path, encoding="utf-8"))
            self._at = time.time()
        return self._cfg.get(key, {})

    def variant(self, key, unit_id, user=None):
        """Stable split: the same lead always lands in the same branch."""
        c = self.cfg(key)
        if user and user in c.get("force_users", []):
            return c.get("canary", c["stable"]), "forced"
        bucket = int(hashlib.sha256(f"{key}:{unit_id}".encode()).hexdigest()[:8], 16) % 100
        if bucket < c.get("percent", 0):
            return c.get("canary", c["stable"]), "canary"
        return c["stable"], "stable"


rollout = Rollout()

# --- The version is pinned at task start and lives with it to the end ---
def start_task(lead, campaign_id):
    version, branch = rollout.variant("outreach_prompt", lead["id"])
    task = {"lead": lead, "campaign_id": campaign_id,
            "pinned": {"prompt": version, "model": MODELS["large"],   # explicit, never "latest"
                       "code": os.environ.get("GIT_SHA", "dev")},
            "branch": branch}
    save_task(task)
    return task


def run_task(task):
    with span("outreach", lead_id=task["lead"]["id"], **task["pinned"], branch=task["branch"]):
        # the prompt comes from the pinned version, not from the current config
        system = load_prompt("outreach", task["pinned"]["prompt"])
        return build_email_with(system, task["lead"])


# --- Comparing branches: not only quality, but behavioral health ---
def canary_report(key, hours=24):
    rows = query_spans(name="outreach", since_hours=hours)
    out = {}
    for branch in ("stable", "canary"):
        b = [r for r in rows if r["branch"] == branch]
        if not b:
            continue
        out[branch] = {
            "runs": len(b),
            "refusal_rate": round(share(b, lambda r: r["status"] == "refused"), 3),
            "human_edit_rate": round(share(b, lambda r: r.get("edited")), 3),
            "check_failure_rate": round(share(b, lambda r: r.get("checks_failed")), 3),
            "escalation_rate": round(share(b, lambda r: r.get("escalated")), 3),
            "cost_per_run": round(avg(b, lambda r: r["cost"]), 4),
        }
    return out


# --- Automatic rollback on stop conditions ---
STOP_RULES = [
    ("human_edit_rate",     lambda s, c: c > s * 1.3, "edits rose by more than 30%"),
    ("check_failure_rate",  lambda s, c: c > s * 1.5, "automatic checks fail more often"),
    ("refusal_rate",        lambda s, c: c < s * 0.5, "the agent stopped refusing — suspicious"),
    ("cost_per_run",        lambda s, c: c > s * 2.0, "cost doubled"),
]

def guard_canary(key):
    rep = canary_report(key)
    if "canary" not in rep or rep["canary"]["runs"] < 30:
        return {"decision": "wait", "why": "not enough data"}
    for metric, rule, why in STOP_RULES:
        s, c = rep["stable"][metric], rep["canary"][metric]
        if rule(s, c):
            set_percent(key, 0)                       # rollback by config, no deploy
            alert(f"canary {key} rolled back: {why} (stable={s}, canary={c})")
            return {"decision": "rollback", "why": why, "report": rep}
    return {"decision": "ok", "report": rep}
```

What this would have done in our story:

1. **v4 would have reached 5% of leads**, not all of them. Igor would have noticed the oddity on ten emails, not a hundred.
2. **The refusal stop-rule would have caught it automatically.** A drop in refusals from 12% to 1% signals that the agent stopped admitting ignorance, even though "quality" rose.
3. **Rollback is `percent: 0` in config**, applied in seconds.
4. **Queued tasks would have finished on their own version**, with no hybrid emails.
5. **`force_users`** lets the team see the new version before customers do.

**Assignment.** Take your last prompt change and, from the traces, compute retroactively what both branches would have looked like: refusals, edits, cost. It often turns out that a change accepted as an improvement degraded one of those metrics — nobody was looking at it.

---

## 📌 Remember

- An agent versions five things: code, prompt, model, tool schemas and the knowledge base.
- Pin the model version explicitly: a provider can update "latest" without involving you.
- Separate deploy from release: enabling happens by config, so rollback takes seconds.
- Move the canary on numbers, not on a schedule, and watch more than quality at every step.
- A sharp improvement is a reason to investigate: a collapse in refusals usually means lost caution.
- The version is pinned at task start and lives with it, or you get hybrid results.
