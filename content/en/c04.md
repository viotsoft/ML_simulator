## 🏢 The situation

Friday, 17:20. Viktor, the CFO, walks into the meeting room and puts a printout on the table:

> "In October the support agent refunded 1.84 million. Policy says identity must be verified before a refund. Audit sampled a hundred refunds: nine had no verification. Compliance wants an explanation on Monday."

You open the agent's system prompt. It is all there:

```
IMPORTANT: before calling process_refund you MUST call get_customer
and confirm the customer's identity is verified. NEVER process a refund
without verification. This is a critical compliance requirement.
```

Capital letters, the word MUST, three sentences about how important it is. And a nine percent miss rate. Kostya suggests the obvious: "let's write it even harder, add examples." You already know that will not fix it — because the wording is not the problem.

A second problem surfaces alongside. A customer writes: "the item arrived broken, I was charged twice, and I cannot log into my account." The agent answers about the broken item and says nothing about the rest. Three distinct problems in one message; the agent sees one.

And a third: when the agent does escalate to a human, the operator receives the whole conversation and works it out from scratch. Average escalation handling time: 14 minutes.

## 🎯 Your task

1. Understand why a prompt instruction cannot guarantee ordering — and what replaces it.
2. Build a programmatic gate: `process_refund` is physically unavailable until `get_customer` has verified identity.
3. Decompose a multi-concern request into items and assemble a structured handoff to a human.

## 📚 Theory

### A prompt is guidance, not a guarantee

The domain's key distinction, and it shows up on the exam almost verbatim:

| | Prompt-based guidance | Programmatic enforcement |
| --- | --- | --- |
| What it is | an instruction in the system prompt | a hook, a prerequisite, a gate in code |
| Reliability | high, but **not 100%** | deterministic |
| Where it fits | style, tone, preferred ordering | compliance, money, irreversible actions |
| Cost of a violation | inconvenience | a fine, an incident, a lawsuit |

The phrasing from the guide is worth memorising: **when deterministic compliance is required, prompt instructions alone have a non-zero failure rate**. Viktor's nine percent is not "a badly written prompt", it is the normal behaviour of a probabilistic system. More capital letters will move nine percent to five, not to zero. Compliance needs zero.

An important implementation detail: the gate returns **not an exception but a `tool_result` with a clear error**: "`process_refund` blocked: call `get_customer` first and obtain a verified `customer_id`." The model sees this as a tool result, understands what is missing, and makes the missing call itself. The ordering is deterministic and the conversation is not broken.

### A multi-concern request: decompose, investigate in parallel, synthesise

The second symptom — "answered one of three". The exam phrases the skill like this: **decompose a multi-concern request into distinct items, investigate each in parallel using shared context, then synthesise a unified resolution**.

```
"broken item + double charge + cannot log in"
        │
        ├─ item 1: return/replace the product     ─┐
        ├─ item 2: the duplicate charge           ─┼─ in parallel, shared customer context
        └─ item 3: account access                 ─┘
        │
        └─ one answer: a resolution and a timeline for each item
```

Note the phrase "shared context": customer data is fetched once and reused by every branch — three `get_customer` calls would be both slower and more expensive.

### A structured handoff to a human

The third symptom — 14 minutes per escalation. The cause is that the operator receives a raw transcript and rebuilds the picture alone. The guide requires a **structured handoff protocol** and lists what belongs in it:

- **the customer identifier** — so nobody has to search;
- **the root cause** — what the agent established, not a retelling of the chat;
- **the amount or subject** — the specifics of the operation;
- **the recommended action** — what the agent proposes doing.

The guide's framing is worth remembering: the summary is for a human **who does not have access to the conversation transcript**. That rules out the temptation to write "see the chat above".

```json
{
  "customer_id": "C-88214",
  "issue": "double_charge",
  "root_cause": "payment retried on a gateway timeout; both charges confirmed settled",
  "amount": 4900,
  "recommended_action": "refund one charge, apologise, no documents required",
  "blocked_by": "amount above the agent's autonomous refund limit"
}
```

## 💻 Practice

A prerequisite gate on top of the agentic loop from module C1. Ordering is guaranteed by code, not by text.

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

CUSTOMERS = {"C-88214": {"name": "Irina P.", "verified": True, "orders": ["88214"]}}
AUTONOMOUS_REFUND_LIMIT = 3000

TOOLS = [
    {"name": "get_customer",
     "description": "Returns customer data and whether their identity is verified.",
     "input_schema": {"type": "object",
        "properties": {"customer_id": {"type": "string"}}, "required": ["customer_id"]}},
    {"name": "process_refund",
     "description": "Issues a refund. Requires a verified customer.",
     "input_schema": {"type": "object",
        "properties": {"customer_id": {"type": "string"}, "amount": {"type": "number"}},
        "required": ["customer_id", "amount"]}},
    {"name": "escalate_to_human",
     "description": "Hands the case to an operator with a structured summary.",
     "input_schema": {"type": "object",
        "properties": {
            "customer_id": {"type": "string"},
            "issue": {"type": "string"},
            "root_cause": {"type": "string", "description": "The established cause, not a retelling of the chat"},
            "amount": {"type": "number"},
            "recommended_action": {"type": "string"},
        },
        "required": ["customer_id", "issue", "root_cause", "recommended_action"]}},
]

class Gate:
    """A programmatic prerequisite: session state lives in code, not in the prompt."""
    def __init__(self):
        self.verified_ids = set()

    def check(self, name, args):
        if name == "process_refund":
            if args.get("customer_id") not in self.verified_ids:
                return ("BLOCKED: refunds require a verified identity. "
                        "Call get_customer first and confirm verified=true.")
            if args.get("amount", 0) > AUTONOMOUS_REFUND_LIMIT:
                return (f"BLOCKED: amount above the autonomous refund limit ({AUTONOMOUS_REFUND_LIMIT}). "
                        "Use escalate_to_human with a structured summary.")
        return None

    def record(self, name, args, result):
        if name == "get_customer" and result.get("verified"):
            self.verified_ids.add(args["customer_id"])

def run_tool(name, args):
    if name == "get_customer":
        return CUSTOMERS.get(args["customer_id"], {"error": "not_found"})
    if name == "process_refund":
        return {"ok": True, "refunded": args["amount"]}
    if name == "escalate_to_human":
        return {"ok": True, "ticket": "H-1042", "handoff": args}
    return {"error": f"unknown_tool:{name}"}

def agent(question: str, max_iterations: int = 12):
    gate = Gate()
    messages = [{"role": "user", "content": question}]
    system = ("You are a Datacore support agent. Resolve the customer's request completely. "
              "If the message contains several distinct problems, address every one of them.")
    for _ in range(max_iterations):
        resp = client.messages.create(model=MODEL, max_tokens=1024, system=system,
                                      tools=TOOLS, messages=messages)
        if resp.stop_reason != "tool_use":
            return "".join(b.text for b in resp.content if b.type == "text")
        messages.append({"role": "assistant", "content": resp.content})
        results = []
        for b in resp.content:
            if b.type != "tool_use":
                continue
            blocked = gate.check(b.name, b.input)           # ← the gate runs before execution
            if blocked:
                print(f"    ⛔ {b.name}: {blocked}")
                results.append({"type": "tool_result", "tool_use_id": b.id,
                                "content": blocked, "is_error": True})
                continue
            out = run_tool(b.name, b.input)
            gate.record(b.name, b.input, out)
            print(f"    → {b.name}({b.input}) = {out}")
            results.append({"type": "tool_result", "tool_use_id": b.id,
                            "content": json.dumps(out)})
        messages.append({"role": "user", "content": results})
    return None

if __name__ == "__main__":
    print(agent("Customer C-88214: the item from order 88214 arrived broken, "
                "I was charged 4900 twice, and I cannot log into my account."))
```

**Assignment.**

1. Replace the gate with a system-prompt instruction ("you MUST call get_customer first") and run the request twenty times. Count how many runs go straight to `process_refund`. That is the non-zero failure rate.
2. Make the gate message uninformative (`"BLOCKED"` with no explanation) and watch the agent repeat the same call instead of correcting itself. A useful error is part of the gate, not decoration (more on this in module C7).
3. Test escalation: raise the refund amount above the limit and confirm `escalate_to_human` receives every field of the structured summary rather than a pointer to the chat.

## 🎯 On the exam

- **Objective 1.4** is covered: programmatic enforcement vs prompt guidance, prerequisites and gates, multi-concern decomposition, structured handoff.
- Scenario: **Customer Support Resolution Agent** — this is its home turf. Questions usually read: "in N% of runs the agent skips the verification step — what do you do?"
- The main trap: options like "rewrite the prompt more forcefully", "add few-shot examples with the correct order", "lower the temperature". All of them reduce the probability, but the exam asks about **deterministic** compliance — the answer is always a programmatic gate or hook.
- Handoff trap: "give the operator the full conversation transcript" sounds informative, but the guide explicitly describes a human **without access to the transcript**: what is needed is a structured summary with root cause and recommendation.
- For multi-concern requests, remember the phrase "shared context": items are investigated in parallel, but customer data is fetched once.

---

## 📌 Remember

- A prompt instruction expresses a preference. Only code — a hook, a prerequisite, a gate — provides a guarantee.
- Where breaking the order costs money or compliance, a non-zero failure rate is unacceptable, so a prompt is insufficient by definition.
- A blocked call returns to the model as a `tool_result` explaining what is missing. The agent then fixes itself and the conversation continues.
- A multi-concern request is decomposed into items, investigated in parallel on shared context, and synthesised into one answer.
- A handoff summary carries the customer id, the root cause, the amount and the recommended action — and is written for someone who never saw the transcript.
