## 🏢 The situation

Igor arrives with an obvious request:

> "The agent writes emails, I send them, and then I type into the CRM by hand: sent, replied, agreed to a call. Half an hour a day of copy-paste. Let it write to the CRM itself."

A reasonable request. But behind it is a transition you have not made yet: until now the agent only **read** and **generated**. Now it will **change state in someone else's system**.

An hour later Olya from legal drops by:

> "I hear you're giving a robot access to the CRM. With what permissions? Who sees personal data? What happens if it deletes a deal? I need answers before this goes live, not after."

Good questions. Answering them is what this module is.

## 🎯 Your task

1. Give the agent write tools such that the worst case is tolerable.
2. Handle secrets: the agent must never see your CRM API key.
3. Understand what MCP is and when it saves you from writing integrations.

## 📚 Theory

### A tool is your system's API for the model

A tool description is not human documentation, it is a contract. Three rules that save weeks of debugging:

1. **A narrow job.** Not `crm_update(entity, field, value)` but `crm_log_reply(lead_id, category, note)`. A broad tool means a broad class of mistakes.
2. **The description explains when to call it.** "Record a lead's reply in the CRM. Call only after the reply has been classified" — the model reads that as an instruction.
3. **Errors come back as text, not exceptions.** The model should see "lead not found" and try differently, not crash the process.

### Secrets never reach the model

The CRM key lives in your service, not in the model's context. The model calls `crm_log_reply(lead_id=...)`, your code attaches the token and makes the request. The model never sees the key — so it cannot quote it into an email and cannot hand it over under injection.

The same logic applies to identifiers: the agent works with `lead_id`, not with the customer's email and phone. Only the personal data the task actually needs enters the context.

### Idempotent writes

A retry (from A2) plus a write equals duplicate CRM records. The fix is an idempotency key: `f"{lead_id}:{message_id}"`. A repeat call with the same key does not create a second note, it returns the first. Without it, a retry after a timeout doubles your data and nobody knows why.

### MCP: when not to hand-write an integration

**Model Context Protocol** is a standard where tools are described once and connect to any client. The idea is simple: instead of writing wrappers over every API for every agent, you connect an existing MCP server (or write one of your own and it works everywhere).

When it helps: common systems where a server already exists; several agents over the same tools; wanting to separate the integration's owner from the agent's owner.

When it does not: one or two narrow operations — a 20-line function is simpler; and remember that MCP removes neither permissions, nor idempotency, nor logging.

## 💻 Practice

```python
import os, json, hashlib, requests, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

# Secrets live here and never enter the model's context
CRM_TOKEN = os.environ["CRM_AGENT_TOKEN"]      # token of a SERVICE user with a reduced role
CRM_URL = os.environ["CRM_URL"]

# --- Narrow tools: one operation, one tool ---
TOOLS = [
    {"name": "crm_get_lead",
     "description": "Fetch a lead card by id. Returns work fields only, "
                    "without personal contact details.",
     "input_schema": {"type": "object", "properties": {"lead_id": {"type": "string"}},
                      "required": ["lead_id"]}},
    {"name": "crm_log_reply",
     "description": "Record the outcome of triaging a lead's reply. Call only after the reply "
                    "has been classified. Repeat calls with the same message_id are safe.",
     "input_schema": {"type": "object", "properties": {
         "lead_id": {"type": "string"},
         "message_id": {"type": "string", "description": "email id — the idempotency key"},
         "category": {"type": "string", "enum": CATEGORIES},     # from A3
         "note": {"type": "string", "description": "One sentence for the account manager"},
         "follow_up_date": {"type": ["string", "null"]},
     }, "required": ["lead_id", "message_id", "category", "note"]}},
    # There is no crm_delete_lead tool here, and there never will be — that is Olya's answer
]

SAFE_FIELDS = {"id", "company", "industry", "stage", "owner", "last_touch_at"}

def crm_get_lead(lead_id):
    r = requests.get(f"{CRM_URL}/leads/{lead_id}",
                     headers={"Authorization": f"Bearer {CRM_TOKEN}"}, timeout=10)
    if r.status_code == 404:
        return {"error": "lead not found"}          # the error goes back to the model as text
    r.raise_for_status()
    data = r.json()
    return {k: v for k, v in data.items() if k in SAFE_FIELDS}   # personal-data filter


def crm_log_reply(lead_id, message_id, category, note, follow_up_date=None):
    # Idempotency key: a retry after a timeout will not create a second note
    key = hashlib.sha256(f"{lead_id}:{message_id}".encode()).hexdigest()[:32]
    r = requests.post(
        f"{CRM_URL}/leads/{lead_id}/notes",
        headers={"Authorization": f"Bearer {CRM_TOKEN}", "Idempotency-Key": key},
        json={"category": category, "note": note[:500], "follow_up_date": follow_up_date,
              "author": "agent:outreach"},         # the log shows the robot wrote this
        timeout=10)
    if r.status_code == 409:
        return {"ok": True, "note": "record already existed (idempotency)"}
    if r.status_code == 403:
        return {"error": "no permission for this operation"}   # the model sees it and stops trying
    r.raise_for_status()
    return {"ok": True, "note_id": r.json()["id"]}


IMPL = {"crm_get_lead": crm_get_lead, "crm_log_reply": crm_log_reply}

def run_tool(name, args):
    try:
        return json.dumps(IMPL[name](**args))
    except Exception as e:
        # The model must see the error as a result, not have the process crash
        return json.dumps({"error": f"{type(e).__name__}: {e}"})


def process_reply(lead_id, message_id, email_text):
    messages = [{"role": "user", "content":
                 f"lead_id={lead_id}, message_id={message_id}\nEmail:\n{email_text}\n"
                 "Triage the reply and record the result in the CRM."}]
    for _ in range(5):                                    # loop limit from A7
        resp = client.messages.create(model=MODEL, max_tokens=800, tools=TOOLS, messages=messages)
        if resp.stop_reason != "tool_use":
            return resp.content[0].text
        messages.append({"role": "assistant", "content": resp.content})
        messages.append({"role": "user", "content": [
            {"type": "tool_result", "tool_use_id": b.id, "content": run_tool(b.name, b.input)}
            for b in resp.content if b.type == "tool_use"]})
    return "stopped on the step limit"
```

What matters here — and what you tell Olya:

1. **A dedicated service user** with a reduced role. The CRM log shows `agent:outreach`, so authorship is never ambiguous.
2. **It cannot delete a deal:** no such tool exists and the role does not allow it. A limit at the capability level, not a request in a prompt.
3. **Personal contacts never enter the context** — the `SAFE_FIELDS` filter on read.
4. **An idempotency key** makes retries safe: a repeat after a timeout will not double the records.
5. **Errors return to the model as text.** It sees "no permission" and stops looping on attempts.

## 📌 Remember

- A tool is a narrow contract: one operation, a description with a calling condition, errors as text.
- Permissions are designed from the worst case. Whatever must never happen should have no tool at all.
- Secrets live in your code, not in the model's context: the agent works with ids, not keys and contacts.
- Every write to an external system is idempotent, or retries will duplicate data.
- Agent actions run as a dedicated service user, so the log shows what the robot did.
- MCP saves you from writing the same integrations twice, but removes neither permissions, idempotency nor logging.

**Further reading:** the Model Context Protocol specification; OWASP least-privilege practices; and your CRM's documentation on idempotent requests and service accounts.
