# Module C9. The built-in tools

> **Level:** Practitioner · **Time:** ~40 minutes · **Format:** situation → theory → practice → quiz
>
> **CCAR-F objective:** 2.5 — Select and apply built-in tools (Read, Write, Edit, Bash, Grep, Glob) effectively

---

## 🏢 The situation

A new developer, Artem, comes to you with a task: "rename the `calculate_refund` function and fix all its callers." He opens Claude Code and comes back forty minutes later:

> "It read eighty files, ate the whole context, and then proposed renaming the wrong thing. Also Edit keeps failing with something about non-unique text, so now he is afraid to touch the file."

You read the transcript and see three separate tool-selection mistakes:

1. **Reconnaissance by reading.** The agent started with `Read` across every file to "understand the codebase". Eighty files, four of which were relevant.
2. **Searching with the wrong tool.** To find the call sites it went through files by name with `Glob`, hoping to guess where they lived.
3. **Edit with no plan B.** The line `return calculate_refund(order)` appears three times in the file, `Edit` cannot pick an anchor and fails. Artem concluded the file was "broken".

None of these is about the model. All three are about which tool exists for what. This is the most down-to-earth objective in domain 2 and one of the most frequently tested.

## 🎯 Your task

1. Sort out what `Grep` searches and what `Glob` searches.
2. Understand when to use `Edit` and when `Read` + `Write`.
3. Establish the right order for exploring unfamiliar code.

**`Grep` — content search.** Function names, error messages, import lines. "Find everyone who calls `calculate_refund`" is `Grep`.

**`Glob` — path pattern matching.** "Find every `**/*.test.tsx`" is `Glob`. It knows nothing about contents.

**`Read` / `Write`** — whole-file operations. **`Edit`** — a targeted modification located by a unique text match.

**`Bash`** — everything else: run the tests, look at git history, execute a command.

### When Edit fails

`Edit` locates the spot by a unique anchor text. If the string occurs several times in the file, there is no unambiguous location and the edit does not apply. That is not a broken file — that is a missing unique anchor.

The guide gives a concrete fallback: **`Read` + `Write`**. Read the whole file, change the right place with the surrounding context in view, write it back. The second, more elegant option is to widen the anchor with adjacent lines until the match becomes unique. Both beat giving up.

### The exploration order: Grep → Read → change

Artem's first mistake is the expensive one. The guide states the skill explicitly: **build codebase understanding incrementally — start with `Grep` to find entry points, then use `Read` to follow imports and trace flows, rather than reading all files upfront**.

The difference is dramatic:

```
❌ Read 80 files → context full, understanding absent
✅ Grep "calculate_refund" → 6 files → Read those six → everything is clear
```

And a separate technique for cross-cutting renames, which the guide spells out step by step: **first identify all exported names, then search for each name across the codebase**. This matters when a function travels through wrapper modules: `calculate_refund` may be re-exported as `refund` in `__init__.py`, and searching for the original name alone misses half the call sites.

## 💻 Practice

This practice runs in Claude Code itself, on this repository, rather than in Python. Every command is safe and changes nothing.

**Exercise 1. Grep vs Glob.** In a Claude Code session at the project root, ask:

```
Find every place countPassed is called — using content search only,
without reading whole files. Tell me which tool you used.
```

Then:

```
Find every markdown file of the agent track by name pattern. Which tool is right here?
```

The first is `Grep` (contents), the second is `Glob` (paths). Notice that `Grep` finds the call sites without knowing which files to look in.

**Exercise 2. The right exploration order.** Two requests in separate sessions; compare context consumption:

```
Session A: Read every file in public/js/ and content/, then explain
           how the track separation works.
Session B: Explain how the track separation works. Start with a content search
           and read only the files you genuinely need.
```

Session B usually fits in 4–6 reads instead of dozens — and the answer is more accurate, because attention is not diluted (the same effect as in module C6).

**Exercise 3. A non-unique anchor.** Find a line in `public/js/app.js` that occurs several times — `bindSectionTabs();`, for instance. Then ask:

```
Replace the third occurrence of bindSectionTabs() with bindSectionTabs(); // check
```

Watch how the agent copes: it will either widen the anchor with surrounding lines or read the whole file and write it back. Both are correct; giving up is not.

**Exercise 4. A cross-cutting rename through wrappers.** Ask:

```
The gradeQuiz function in server.js is called from several places. First find every
name under which it is exported or reassigned, then search for each of those names
to assemble the full caller list. Change nothing.
```

That is exactly the two-step technique from the guide: names first, then a search per name.

## 🎯 On the exam

- **Objective 2.5** is covered: `Grep` for contents, `Glob` for paths, `Read`/`Write` for whole files, `Edit` by unique anchor, `Read` + `Write` as the fallback, incremental exploration, tracing through wrappers.
- Scenarios: **Developer Productivity with Claude** (exploring unfamiliar and legacy code) and **Code Generation with Claude Code**.
- Trap: "you need to find every call site of a function — which tool?" with `Glob` among the options. `Glob` matches file names and never sees contents.
- Trap: `Edit` failed on a non-unique match, and the options include "use Bash with sed" or "rewrite the whole function". The expected answer is `Read` + `Write` (or a more unique anchor).
- Exploration trap: "read every file in the module to get the full picture". The exam expects the incremental approach: `Grep` for entry points, then `Read` along the references.

---

## 📌 Remember

- `Grep` looks inside files, `Glob` looks at file names. That is the first thing questions on this objective check.
- `Edit` works by a unique text anchor. A non-unique match is not a file problem, it is a missing anchor.
- The fallback for a non-unique match is `Read` + `Write` (or widening the anchor with surrounding context).
- Codebases are learned incrementally: `Grep` finds entry points, `Read` follows imports. Bulk reading upfront spends context and yields no understanding.
- To trace through wrappers, collect every exported name first, then search for each one.
