# Module C10. CLAUDE.md: hierarchy and scoping

> **Level:** Practitioner · **Time:** ~45 minutes · **Format:** situation → theory → practice → quiz
>
> **CCAR-F objectives:** 3.1 — Configure CLAUDE.md files with appropriate hierarchy, scoping, and modular organization · 3.3 — Apply path-specific rules for conditional convention loading

---

## 🏢 The situation

Datacore rolls Claude Code out to the whole engineering team — forty people, a monorepo of twelve packages. A week later you have three tickets, and all three are about conventions.

**The first.** Artem, the same new hire: "My agent writes tests in the wrong style. Kostya's writes them correctly for some reason." You dig in: two months ago Kostya carefully wrote up the testing conventions — and put them in `~/.claude/CLAUDE.md`. On his own machine. The file is not in the repository and never reached the team.

**The second.** The root `CLAUDE.md` has grown to 900 lines: API conventions, test style, terraform rules, the release process, migration agreements. It loads in full in every session. A developer editing CSS gets two hundred lines about terraform in their context.

**The third, and the subtlest.** Dasha from the platform team: "We put the test conventions in `tests/CLAUDE.md`, but half our tests sit next to the code — `components/Button.test.tsx`. The rules never load for those." A directory file is bound to a directory, and the tests are spread across the tree.

## 🎯 Your task

1. Work through the three levels of the hierarchy and see where "mine" ends and "the team's" begins.
2. Break the monolithic `CLAUDE.md` into modules so context is not filled with the irrelevant.
3. Understand when a rule binds to a directory and when it binds to a path pattern.

- **`~/.claude/CLAUDE.md`** — user level. Applies to you only and **does not reach version control**. Personal preferences yes, team standards no.
- **`CLAUDE.md` at the root or `.claude/CLAUDE.md`** — project level. Lives in the repository, applies to everyone.
- **`CLAUDE.md` in a subdirectory** — rules for its own subtree.

Diagnosing Artem's problem takes one command: **`/memory`** shows which memory files are currently loaded. It is also the first tool to reach for when an agent behaves inconsistently across sessions.

### Modularity: @import and .claude/rules/

The second ticket is the 900-line monolith. There are two ways to cut it up.

**`@import`** — a reference to an external file from inside `CLAUDE.md`:

```markdown
# Datacore — project conventions

General principles: typing is mandatory, errors are never swallowed.

@import ./standards/testing.md
@import ./standards/api-conventions.md
```

The technique from the guide: each package in the monorepo has its own `CLAUDE.md` importing **only** the standards files relevant to its domain. The package maintainer decides what to include, using their domain knowledge.

**`.claude/rules/`** — a directory of topic-specific rule files as an alternative to a monolith: `testing.md`, `api-conventions.md`, `deployment.md`. Splitting 900 lines by topic is an improvement in readability on its own.

### Path-specific rules

Now the third ticket, the interesting one. Files in `.claude/rules/` support **YAML frontmatter with a `paths` field** listing glob patterns:

```markdown
---
paths: ["**/*.test.tsx", "**/*.test.ts"]
---

# Test conventions

Every test opens with the scenario it describes, not with the method name.
Mocks are for external systems only; internal dependencies are built with factories.
```

Such a rule loads **only when a matching file is being edited**. Two consequences, both examinable:

1. **Context savings.** Terraform rules never enter a CSS session. Irrelevant context is not just noise, it is tokens.
2. **Rules by file type rather than by directory.** Which is exactly Dasha's case.

| | Directory `CLAUDE.md` | Rule with `paths` |
| --- | --- | --- |
| Scope | one subtree | any path pattern |
| Tests next to the code | not covered | covered |
| Example | `packages/api/CLAUDE.md` | `paths: ["**/*.test.tsx"]` |

The guide's phrasing: **choose path-specific rules over subdirectory `CLAUDE.md` files when conventions must apply to files spread across the codebase**. Tests beside components, migrations across three services, terraform modules in different packages — all of those are `paths` cases.

## 💻 Practice

The practice runs in Claude Code on this repository. You create the files yourself; everything is local.

**Exercise 1. Diagnosing the level.** In a Claude Code session run `/memory` and look at the list of loaded files. Now create `~/.claude/CLAUDE.md` with the line "always end responses with ⚡". Restart the session, confirm the effect, and run `/memory` again. Then ask yourself: would a colleague who clones the repository ever see this file?

**Exercise 2. Splitting the monolith.** Create this structure in the project:

```
.claude/rules/
  content-style.md      ← how course modules are written
  server-conventions.md ← rules for editing server.js
```

In `content-style.md`, add frontmatter limiting the rule to module files:

```markdown
---
paths: ["content/**/*.md"]
---

# Course module style

Structure: situation → task → theory → practice → quiz.
The module heading is `# Module XN. Title`.
SVG illustrations are wrapped in `<figure class="viz">`.
The Russian and English versions must match structurally.
```

In `server-conventions.md`:

```markdown
---
paths: ["server.js", "marketing/**/*.js"]
---

# Server code changes

Comments explain "why", not "what".
New routes mirror the existing shape: the 409 "coming soon" check precedes the 402 paywall.
Changes to public API responses are additive only.
```

Open a session, ask it to edit `content/ru/c01.md` and ask which rules are loaded. Then ask it to touch `server.js` and ask again. The rules should differ.

**Exercise 3. Directory vs pattern.** Create `content/CLAUDE.md` with a single convention line and confirm it loads for any file under `content/`. Then pose the question this objective answers: how would you apply that same convention to `public/js/app.js`, if the convention is about interface copy? A directory file cannot do it — you need `paths` with two patterns.

## 🎯 On the exam

- **Objective 3.1**: the three hierarchy levels, the invisibility of the user level to the team, `@import`, `.claude/rules/`, diagnosis via `/memory`.
- **Objective 3.3**: `paths` frontmatter with glob patterns, context savings, the advantage of patterns over directory files for scattered conventions.
- Scenarios: **Code Generation with Claude Code** and **Developer Productivity with Claude**.
- The classic trap: "a new team member is not receiving the instructions". The answer is almost always that the instructions live in `~/.claude/CLAUDE.md` instead of the project file.
- Monolith trap: "increase the context window" or "shorten CLAUDE.md by dropping some rules". The expected answer is splitting into `.claude/rules/` with `paths` scoping.
- Trap about tests beside code: "create a CLAUDE.md in every test directory" would technically work, but the exam expects `paths: ["**/*.test.tsx"]` — one rule instead of dozens of files.

---

## 📌 Remember

- `~/.claude/CLAUDE.md` is for you and never for the team. Team standards live in the project file in the repository.
- A directory `CLAUDE.md` applies to its subtree; the root one applies to the whole project.
- `@import` pulls in external standards files; `.claude/rules/` splits rules by topic instead of one monolith.
- `/memory` shows which memory files are loaded — the first step when behaviour diverges between sessions.
- `paths` frontmatter with glob patterns loads a rule only for matching files: less irrelevant context and fewer tokens.
- Conventions for files spread across the tree are scoped by path pattern, not by a directory file.
