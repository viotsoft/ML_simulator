# Module C13. Claude Code in CI/CD

> **Level:** Practitioner · **Time:** ~50 minutes · **Format:** situation → theory → practice → quiz
>
> **CCAR-F objective:** 3.6 — Integrate Claude Code into CI/CD pipelines

---

## 🏢 The situation

The automated review Kostya set up in module C6 finally rolled out to every pull request. Two weeks later the team asks him to turn it off. You go through the complaints.

**Complaint 1.** The job sometimes hangs for forty minutes and dies on timeout. The log shows the agent asked a clarifying question and is waiting for an answer. In CI there is nobody to answer.

**Complaint 2.** The review output is free-form text in the build log. To turn it into inline PR comments, Kostya wrote a regex parser. It breaks every time the wording changes.

**Complaint 3.** The author pushed three commits in a row. The review ran three times and wrote the same four findings each time. Twelve comments about one problem.

**Complaint 4.** The test generator proposes tests that already exist and tests that check getters. One in eight is useful.

**Complaint 5, from Dasha.** "Your agent generated the code for a task and then reviewed its own work and wrote 'looks great'."

Five complaints, five points of this objective.

## 🎯 Your task

1. Run Claude Code so it never waits for input.
2. Get structured output instead of text that must be parsed.
3. Remove duplicate comments, raise test quality, and separate generation from review.

**`-p` (or `--print`)** — non-interactive mode. Claude Code performs the task and prints the result without requesting input. Without it, a CI agent will eventually ask a question and hang until the timeout — complaint 1.

**`--output-format json`** together with **`--json-schema`** — machine-parseable structured output. Instead of regexing prose you get JSON of a known shape that converts directly into inline PR comments — complaint 2.

```bash
claude -p "Review the changes in this PR" \
  --output-format json \
  --json-schema ./ci/review-schema.json
```

### What to put in the context

**`CLAUDE.md` is the mechanism for providing project context** to a CI-invoked run: testing standards, fixture conventions, review criteria. The job asks no questions and knows nothing about your project beyond what you put in files. This directly answers complaint 4: the guide asks you to **document testing standards, valuable test criteria and available fixtures in `CLAUDE.md`** so test generation stops producing noise.

**Prior review findings.** When re-running after new commits, include the previous review's results in context and instruct explicitly: report only **new or still-unaddressed** issues. That is complaint 3 — twelve comments about one problem.

**Existing test files.** So the generator does not propose scenarios the suite already covers. The other half of complaint 4.

### Session isolation

Dasha's complaint is about a separate fact from the guide worth memorising: **the same session that generated code is less effective at reviewing its own changes** than an independent review instance. Its context holds its own decisions and justifications, and it tends to confirm them.

The practical consequence: in the pipeline, generation and review are **separate runs with clean context**. Not "ask the same agent to check itself", but a separate process that sees only the diff and the project standards.

## 💻 Practice

The output schema — `ci/review-schema.json`:

```json
{
  "type": "object",
  "properties": {
    "findings": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "file":     { "type": "string" },
          "line":     { "type": "integer" },
          "severity": { "type": "string", "enum": ["blocker", "major", "minor"] },
          "category": { "type": "string" },
          "message":  { "type": "string" },
          "suggestion": { "type": "string" }
        },
        "required": ["file", "line", "severity", "message"]
      }
    },
    "summary": { "type": "string" }
  },
  "required": ["findings", "summary"]
}
```

The review job — `.github/workflows/review.yml`:

```yaml
name: AI review
on: pull_request

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }

      - name: Collect prior findings
        id: prior
        run: |
          gh pr view "$PR" --json comments \
            --jq '[.comments[] | select(.author.login=="github-actions") | .body]' \
            > prior-findings.json
        env:
          PR: ${{ github.event.pull_request.number }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

      - name: Review
        run: |
          git diff origin/${{ github.base_ref }}...HEAD > pr.diff
          claude -p "$(cat <<'PROMPT'
          Review the changes in pr.diff against the project standards in CLAUDE.md.

          prior-findings.json holds the findings already posted on this PR.
          Report ONLY new or still-unaddressed issues.
          Do not repeat anything already raised or already fixed.

          False positives cost more than misses: if you are not confident something
          is a defect, do not report it. Every finding carries a file, a line and a
          concrete suggestion.
          PROMPT
          )" \
            --output-format json \
            --json-schema ./ci/review-schema.json \
            > review.json

      - name: Post comments
        run: node ci/post-comments.js review.json
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

The `CLAUDE.md` section that raises test generation quality:

```markdown
## Testing standards

A valuable test exercises a boundary or an error path.
We do not write tests for getters, constructors or trivial delegation.

Available fixtures: `tests/fixtures/users.js` (a user with and without progress),
`tests/fixtures/db.js` (a temporary DATA_DIR that cleans itself up).
Add a new fixture only when the existing ones do not fit.

Naming: `describe('countPassed')` → `it('does not count modules of another track')`.
Mock external systems only; use a temporary directory for the filesystem.
```

**Assignment.**

1. Run `claude -p "list the changed files"` with and without the `-p` flag from a script with no terminal. The difference is whether it ever finishes.
2. Run the review with and without `--json-schema`. Try writing a parser for the second variant, then change the prompt wording and see whether the parser survives.
3. Remove the prior-findings block from the prompt and run the review twice on the same diff. Count the duplicates.
4. Ask one session to generate a function and then, in the same session, to review it. Then review the same code in a clean session. Compare the two lists of findings.

## 🎯 On the exam

- **Objective 3.6** is covered: the `-p`/`--print` flag, `--output-format json` with `--json-schema`, `CLAUDE.md` as the project context channel, prior findings against duplicates, existing tests against copies, isolating generation from review.
- Scenario: **Claude Code for Continuous Integration** — built entirely around this objective, plus domain 4 for prompt quality.
- Hang trap: options like "raise the job timeout" or "add a request to the prompt not to ask questions". The expected answer is the `-p` flag.
- Parsing trap: "write more robust regular expressions". The answer is schema-enforced structured output.
- Duplicate trap: "delete the old comments before each run" sounds reasonable, but the guide asks for something else — include prior findings in context and instruct the model to report only new or unaddressed issues.
- Self-review trap: "ask the same session to double-check its code" is explicitly named as less effective than an independent instance.
- On test quality, remember: noisy tests are not the model's fault but the absence of documented standards and fixtures in `CLAUDE.md`.

---

## 📌 Remember

- `-p` (`--print`) is non-interactive mode for pipelines; without it the job risks waiting for input until timeout.
- `--output-format json` with `--json-schema` produces machine-parseable findings ready to post as inline comments.
- `CLAUDE.md` is how you hand a CI job project context: testing standards, fixtures, review criteria.
- Prior findings go into the context with an instruction to report only new or unaddressed issues — otherwise the PR fills with duplicates.
- Existing tests in context stop the generator proposing scenarios already covered.
- The session that wrote the code is worse at reviewing it. Review runs as a separate instance with a clean context.
