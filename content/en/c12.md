# Module C12. Plan mode vs direct execution

> **Level:** Practitioner · **Time:** ~50 minutes · **Format:** situation → theory → practice → quiz
>
> **CCAR-F objectives:** 3.4 — Determine when to use plan mode vs direct execution · 3.5 — Apply iterative refinement techniques for progressive improvement

---

## 🏢 The situation

Monday, two tasks in the queue, and you watch the team get both wrong — in opposite directions.

**Task one.** Artem has a stack trace: `formatInvoice` crashes on an empty date. A two-line fix in a single file. Artem opens plan mode, the agent explores the repository for twenty minutes, produces a page-long plan, Artem approves it — and the agent makes the same two lines. Half an hour for a one-line guard.

**Task two.** Kostya migrates billing from one payments library to another: 45 files, two integration approaches with different infrastructure requirements. He writes "replace it everywhere" and runs directly. An hour later: 45 changed files, an approach chosen that requires a webhook endpoint which does not exist, and half the edits unusable. Revert.

By evening a third story arrives. Dasha asks the agent for an address normaliser: "bring addresses to a consistent shape". Three iterations, three different notions of "consistent". On the fourth she writes five "input → output" examples — and gets what she needs on the first try.

## 🎯 Your task

1. Formulate the criterion for choosing between planning and direct execution.
2. Understand the role of the Explore subagent in multi-phase tasks.
3. Learn the four iterative refinement techniques — and the rule for when to fix everything at once and when one at a time.

**Plan mode** is for tasks with at least one of four properties: large-scale change, multiple valid approaches, architectural implications, multi-file modifications. Its purpose is **safe exploration and design before anything is changed**, so you do not pay for rework.

**Direct execution** is for simple changes with clear scope: one function, a clear stack trace, an obvious fix.

And a third option the exam calls out separately: **the combination**. Plan the migration in plan mode, choose the approach — then execute the chosen plan directly. That is what Kostya skipped.

### The Explore subagent

Multi-phase tasks have a distinct problem: the discovery phase is verbose. Walking the repository, reading files, chasing dependencies — all of it fills the context before the actual work begins.

The remedy is the **Explore subagent**: it isolates verbose discovery output and returns a **summary** to the main conversation. The same mechanics as `context: fork` in module C11, applied to the investigation phase.

This ties directly to plan mode: planning starts with discovery by definition, and without isolation the context can run out before the plan exists.

### Four iterative refinement techniques

The third story — Dasha and "a consistent shape" for addresses. The guide lists the techniques, and the first is her solution.

**1. Concrete input/output examples.** The most effective way to communicate an expected transformation when prose is interpreted inconsistently. Two or three examples remove an ambiguity no paragraph of description will:

```
"5 Lenin St, apt 12"        → {street: "Lenin", building: "5", apartment: "12"}
"Lenin 5-12"                → {street: "Lenin", building: "5", apartment: "12"}
"18 Mira Ave, block 2"      → {street: "Mira", building: "18", block: "2"}
```

**2. Test-driven iteration.** Write the test suite first — expected behaviour, edge cases, performance requirements — then implement, and iterate by **sharing the test failures** as feedback. A test is the same input/output example, only executable.

**3. The interview pattern.** Ask Claude to **ask you questions** before implementing, to surface considerations you had not anticipated. Especially valuable in an unfamiliar domain: cache invalidation strategy, failure modes, behaviour under partial failure — the things people remember on day three.

**4. The rule for grouping fixes.** A subtle point the exam likes:

| Situation | How to fix |
| --- | --- |
| The problems **interact** | all of them in one detailed message |
| The problems are **independent** | sequentially, one at a time |

The logic is simple: if fixing one problem changes the conditions for another, fixing them in turn means redoing work. And independent problems dumped into one message dilute attention — the same effect as module C6.

## 💻 Practice

The practice runs in Claude Code on this repository. Nothing destructive.

**Exercise 1. Calibrating the choice.** For each task decide: plan mode, direct execution, or the combination. Then do the first two and compare the time.

```
A. In server.js, add a check that the quiz amount is an integer.
B. Move progress storage from data/users.json to SQLite, keeping the API.
C. Fix a typo in the Russian text of module c03.
D. Add a fourth track to the simulator.
```

A and C are direct execution (one place, obvious fix). B and D are plan mode: many files, architectural implications, multiple valid approaches.

**Exercise 2. Explore for discovery.** Ask the same question two ways and compare the remaining context:

```
Way 1: Work out how marketing content generation is built
       by reading every file in marketing/.
Way 2: Work out how marketing content generation is built.
       Push discovery into an Explore subagent and return a summary to the main session.
```

**Exercise 3. Examples instead of prose.** Ask for a module-heading normaliser in prose first:

```
Write a function that brings module headings to a consistent shape.
```

Then with examples:

```
Write a module-heading normaliser. Examples:
"# Module A1. The CEO's idea"        → {track: "a", num: 1, title: "The CEO's idea"}
"# Module C10. CLAUDE.md: hierarchy" → {track: "c", num: 10, title: "CLAUDE.md: hierarchy"}
"# Module M21. ML System Design"     → {track: "m", num: 21, title: "ML System Design"}
```

Compare how many iterations each took to reach something usable.

**Exercise 4. The interview pattern.** Before asking for an implementation, write:

```
I want to add server-side caching of rendered module markdown.
Do not write code. Ask me the questions whose answers are needed
so the solution does not have to be redone. Especially about
invalidation and failure modes.
```

Note how many of its questions you had not thought through.

**Exercise 5. Grouping fixes.** Find two interacting problems in your code (a date format and the sorting that depends on it, say) and two independent ones. Describe the first pair in a single message and the second pair one at a time. Consider which arrangement would have hurt more reversed.

## 🎯 On the exam

- **Objective 3.4**: plan mode criteria (scale, multiple approaches, architecture, many files) vs direct execution (simple, clearly scoped), safe exploration before changes, the Explore subagent, the plan-then-execute combination.
- **Objective 3.5**: input/output examples, test-driven iteration, the interview pattern, the rule for grouping interacting and independent problems.
- Scenarios: **Code Generation with Claude Code**, **Developer Productivity with Claude**.
- Plan mode trap: the option "use plan mode for everything, to be safe". The exam explicitly names direct execution as appropriate for simple, well-scoped changes.
- Refinement trap: "rewrite the task description in more detail". When prose is interpreted inconsistently, the answer is concrete input/output examples, not longer prose.
- Grouping trap: the options usually offer "always fix one problem at a time" or "always send everything at once". The correct answer depends on whether the problems interact.
- For Explore, remember the phrasing: isolate verbose discovery output and return summaries to avoid exhausting the context window.

---

## 📌 Remember

- Plan mode: scale, multiple approaches, architecture, many files. Direct execution: a well-understood change with clear scope.
- Planning exists to explore safely and avoid paying for rework. It is not free: on a one-line fix it is pure loss.
- The combination is legitimate and often optimal: plan the choice of approach, then execute directly.
- The Explore subagent isolates verbose discovery and returns a summary, so the context survives into implementation.
- When prose is read inconsistently, give 2–3 input/output examples. That beats any amount of refined description.
- Tests first, then iterate on the failures. The interview pattern surfaces the questions you did not think to ask.
- Interacting problems go in one message; independent ones go one at a time.
