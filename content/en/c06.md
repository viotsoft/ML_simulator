## 🏢 The situation

Two tasks land on the same day, and both look like "just run it through an agent".

**The first.** Kostya sets up automated review on pull requests. The first big PR is 18 files, 2,400 lines. The agent receives the whole diff in one chunk and returns six comments, all about the first two files. About the other sixteen: silence. Meanwhile the nastiest defect was cross-file: `payments/refund.py` changed a signature, and the call site in `support/handlers.py` still uses the old one.

**The second.** Viktor asks: "get billing under test, it is forty thousand lines with not a single test and it makes me nervous." Kostya proposes a plan: walk the files alphabetically and write tests. You look at the file list and realise the first thirty are configs and constants, while all the risk sits in three modules — and you do not yet know which three.

Different tasks, and **their decomposition strategies must differ too** — which is what the last objective of domain 1 is about.

## 🎯 Your task

1. Tell the two patterns apart: a fixed pipeline (prompt chaining) and dynamic adaptive decomposition.
2. Decompose a large PR review so the cross-file defect does not get lost.
3. Build a plan for an open-ended task that studies the structure before deciding what to do.

**Prompt chaining** — a chain of steps known in advance, each receiving the previous one's output. It fits where the list of aspects is fixed: security review → style review → coverage review. Predictable, cheap, easy to debug.

**Dynamic adaptive decomposition** — subtasks are generated from intermediate findings. The first step is reconnaissance; the plan is built from its results and keeps changing as dependencies surface. More expensive, but it is the only way to handle tasks whose parts you cannot enumerate upfront.

### Reviewing a large PR: local passes plus a cross-file pass

Kostya's problem has a name — **attention dilution**: the more material in a single request, the shallower the analysis of each part. Six comments about the first two files is the classic symptom.

The guide gives a concrete recipe:

```
Pass 1 (local, per file — in parallel):
  payments/refund.py     → findings within the file
  support/handlers.py    → findings within the file
  ... 16 more files
        │
        ▼
Pass 2 (cross-file, separate):
  input — the local summaries and the list of changed signatures
  look for: stale call sites, circular dependencies, contracts that drifted apart
```

The key word is a **separate** cross-file pass. You cannot bolt it onto the end of the local one: a local pass sees a single file, and a cross-file defect by definition lives between files. That is exactly why no local pass, however thorough, would have caught the changed signature in `refund.py`.

### An open-ended task: map first, plan second

For "add tests to legacy" the guide describes a three-step sequence worth memorising as a recipe:

1. **Map the structure** — what the modules are, how they connect, where the entry points are.
2. **Identify high-impact areas** — where the code changes often, where the money flows, where production breaks.
3. **Create a prioritised plan that adapts** as dependencies are discovered.

The third point is not decoration. Once you start on tests for the refund module, you discover it depends on four others and half of them need mocks that do not exist. The plan must absorb that — otherwise it falls apart in week two.

Kostya's alphabetical walk is a pipeline applied to a task it was not built for: it burns the first thirty steps on configs and has no way of learning that three modules matter more than all the rest combined.

## 💻 Practice

Both patterns in one file: a chain for the predictable review, an adaptive planner for the open-ended task.

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

def ask(prompt: str, system: str = "", max_tokens: int = 1500) -> str:
    resp = client.messages.create(model=MODEL, max_tokens=max_tokens, system=system,
                                  messages=[{"role": "user", "content": prompt}])
    return "".join(b.text for b in resp.content if b.type == "text")

# ---------- pattern 1: prompt chaining for review ----------
def review_pr(files: dict[str, str]) -> dict:
    """A local pass per file plus a SEPARATE cross-file pass."""
    local = {}
    for path, diff in files.items():                       # trivially parallelisable
        local[path] = ask(
            f"Review the changes in a single file.\n\nFile: {path}\n```\n{diff}\n```\n"
            "Return only findings about this file. Separately list the changed public "
            "signatures as `name(params)` — the next step will need them.",
            system="You are a reviewer. Findings are concrete and cite lines. No generic advice.")

    # the cross-file pass gets summaries, not the full diff: attention stays focused
    summaries = "\n\n".join(f"### {p}\n{r}" for p, r in local.items())
    cross = ask(
        f"Local review summaries for {len(files)} files:\n\n{summaries}\n\n"
        "Find problems impossible to see inside a single file: call sites using a stale "
        "signature, contracts that drifted apart, circular dependencies, changes that require "
        "an edit elsewhere. If there are none, say so.",
        system="You are an architecture reviewer. You care only about cross-file inconsistencies.")
    return {"local": local, "cross_file": cross}

# ---------- pattern 2: dynamic decomposition ----------
PLAN_TOOL = [{
    "name": "submit_plan",
    "description": "A prioritised plan that adapts as findings accumulate.",
    "input_schema": {"type": "object", "properties": {
        "high_impact_areas": {"type": "array", "items": {"type": "string"},
                              "description": "Where the risk is concentrated and why"},
        "tasks": {"type": "array", "items": {"type": "object", "properties": {
            "target": {"type": "string"},
            "why": {"type": "string"},
            "priority": {"type": "integer"},
            "depends_on": {"type": "array", "items": {"type": "string"},
                           "description": "What must be done first"},
        }, "required": ["target", "why", "priority"]}},
        "open_questions": {"type": "array", "items": {"type": "string"},
                           "description": "What will only become clear during the work and may change the plan"},
    }, "required": ["high_impact_areas", "tasks"]},
}]

def plan_open_ended(goal: str, structure_map: str) -> dict:
    """Step 1 — the structure map (given). Step 2 — impact areas. Step 3 — an adaptive plan."""
    resp = client.messages.create(
        model=MODEL, max_tokens=2000, tools=PLAN_TOOL,
        tool_choice={"type": "tool", "name": "submit_plan"},
        messages=[{"role": "user", "content":
            f"Goal: {goal}\n\nStructure map:\n{structure_map}\n\n"
            "Do not walk the files in order. First determine where the risk is concentrated "
            "(money, frequent changes, external integrations) and prioritise by that. "
            "Put anything that could change the plan mid-flight into open_questions."}],
    )
    return next(b.input for b in resp.content if b.type == "tool_use")

if __name__ == "__main__":
    pr = {
        "payments/refund.py": "- def refund(order_id):\n+ def refund(order_id, reason, actor_id):\n      ...",
        "support/handlers.py": "  def on_refund_request(req):\n      return refund(req.order_id)",
        "config/limits.py": "- REFUND_LIMIT = 500\n+ REFUND_LIMIT = 5000",
    }
    r = review_pr(pr)
    print("=== CROSS-FILE PASS ===")
    print(r["cross_file"][:800])

    print("\n=== PLAN FOR THE OPEN-ENDED TASK ===")
    plan = plan_open_ended(
        "Get the billing module under test (40k lines, no tests)",
        "billing/\n  refunds.py (called from support, gateway, admin)\n"
        "  gateway_client.py (external API, retries)\n  invoices.py\n"
        "  constants.py\n  formatters.py\n  ... 28 more utility files")
    print(json.dumps(plan, indent=2)[:900])
```

**Assignment.**

1. Remove the cross-file pass and confirm that the mismatch between `refund(order_id)` and the new signature is found by no local review. That is the defect from the situation.
2. Feed the whole diff in one request instead of local passes and count how many files actually received comments. That is what attention dilution looks like.
3. In `plan_open_ended`, replace the instruction with "walk the files alphabetically" and see where the first five tasks of the plan end up.

## 🎯 On the exam

- **Objective 1.6** is covered: prompt chaining vs dynamic decomposition, the rule for choosing, local plus cross-file passes, the three-step recipe for open-ended tasks.
- Scenarios: **Claude Code for Continuous Integration** (reviewing large PRs), **Developer Productivity with Claude** (legacy code, tests, exploring unfamiliar systems).
- Trap: "increase the context window / send the whole PR at once, since it fits". Fitting is not the same as being analysed — attention dilution is named separately in the guide.
- Trap: "add a cross-file dependency check to the local pass prompt". A local pass sees one file; you need a **separate** cross-file pass.
- For open-ended tasks the answer almost always contains the ordering: **structure map first, then high-impact areas, then a prioritised adaptive plan** — not "start writing tests from the first file".

---

## 📌 Remember

- The steps are known upfront — prompt chaining. The steps depend on findings — dynamic decomposition.
- A large review splits into per-file local passes **plus a separate cross-file pass**. Without the second, cross-file defects are never found.
- Attention dilution is real: the more that goes into one request, the shallower each part is analysed.
- An open-ended task is approached in order: structure map → high-impact areas → prioritised plan.
- A plan for an open-ended task must adapt: dependencies surface as you go, and a rigid plan breaks on them.
