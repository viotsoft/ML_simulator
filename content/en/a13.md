## 🏢 The situation

Friday, 16:40. Timur from infrastructure writes in the company chat:

> "The model provider is degraded, answering every other request. Your service retries in an infinite loop and has eaten all the workers. I also see eight identical notes on one lead in the CRM and three emails to the same person in ten minutes. I turned you off."

The post-mortem finds three separate failures:

- **Retries with no ceiling.** The provider returned 529, the code retried forever, the queue stalled.
- **Repeats after timeouts.** The request went out, the response arrived late, the retry created a second note — and the first one landed too.
- **No degradation.** The system knows only "fully working" and "down". There is no state in between.

Marina asks what any manager would ask: "So what should have happened instead?"

## 🎯 Your task

1. Make a provider outage stop turning into an avalanche.
2. Guarantee that a retry never creates a second action in the outside world.
3. Design a degraded mode: what the system does when the models are unavailable.

### The circuit breaker

Retries with backoff (from A2) protect against a single failure, but not against a **mass** one. When the provider is down, three thousand tasks start retrying at once — finishing off both the provider and themselves.

A circuit breaker works like an electrical one: it counts recent failures and, past a threshold, **opens the circuit** — stops trying at all for a minute. Then it lets one probe request through: success closes it again, failure keeps it open.

| State | What it does | Transition |
| --- | --- | --- |
| Closed | Lets requests through | 5 consecutive failures → open |
| Open | Fails instantly, spending no time or money | After 60 seconds → half-open |
| Half-open | Lets one probe request through | Success → closed, failure → open |

### Process-level idempotency

In A9 we made the CRM write idempotent. But repeats happen outside a single run too: a worker dies after sending the email but before recording "sent" — and the next worker sends it again.

The cure is a **task key**: `outreach:{lead_id}:{campaign_id}`. Before acting, try to claim the key in a store with a TTL. Claimed it — do the work; did not — the task is already running or done. It is a cheap lock that closes 99% of duplicates.

The rule: **the key is derived from business meaning**, not from time or randomness. A `uuid4()` per run protects against nothing.

### Timeouts and a time budget

Every call gets its own timeout, and the whole task gets an overall budget. Without the overall budget, a sum of "reasonable" timeouts becomes minutes of waiting: five steps at 30 seconds is two and a half minutes for one email.

In practice: 20–30 seconds per call, 90 seconds per task, after which you return a partial result or queue it.

## 💻 Practice

```python
import os, time, json, hashlib, threading, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"], timeout=25.0)


class CircuitBreaker:
    """Avalanche protection: when the provider is down, stop knocking."""
    def __init__(self, threshold=5, cooldown=60):
        self.threshold, self.cooldown = threshold, cooldown
        self.failures, self.opened_at = 0, None
        self.lock = threading.Lock()

    def allow(self):
        with self.lock:
            if self.opened_at is None:
                return True
            if time.time() - self.opened_at >= self.cooldown:
                self.opened_at = None          # half-open: let one probe through
                self.failures = self.threshold - 1
                return True
            return False

    def record(self, ok):
        with self.lock:
            if ok:
                self.failures, self.opened_at = 0, None
            else:
                self.failures += 1
                if self.failures >= self.threshold:
                    self.opened_at = time.time()

    @property
    def is_open(self):
        return self.opened_at is not None


breaker = CircuitBreaker()

# The idempotency key comes from business meaning, not from time
def task_key(kind, **parts):
    raw = kind + ":" + ":".join(f"{k}={parts[k]}" for k in sorted(parts))
    return hashlib.sha256(raw.encode()).hexdigest()[:32]


def claim(key, ttl=3600):
    """Claim the task. False means someone is already doing it, or it is done."""
    return redis.set(f"task:{key}", "1", nx=True, ex=ttl)      # your Redis/DB


def call_model(task, **kw):
    if not breaker.allow():
        raise Degraded("circuit breaker open: the provider is unavailable")
    try:
        resp = client.messages.create(**kw)
        breaker.record(True)
        return resp
    except anthropic.APIStatusError as e:
        breaker.record(e.status_code in (429, 500, 502, 503, 529))
        raise
    except anthropic.APITimeoutError:
        breaker.record(False)
        raise


class Degraded(Exception):
    pass


# --- Degraded mode ---
MODE = {"level": "normal"}          # normal | degraded | stopped

def health_loop():
    """The mode switches automatically based on dependency health."""
    while True:
        if breaker.is_open:
            MODE["level"] = "degraded" if small_model_alive() else "stopped"
        else:
            MODE["level"] = "normal"
        time.sleep(10)


def handle_outreach(lead, campaign_id, deadline_s=90):
    key = task_key("outreach", lead=lead["id"], campaign=campaign_id)
    if not claim(key):
        return {"status": "skipped", "why": "the task is already done or in progress"}

    if MODE["level"] == "stopped":
        enqueue_for_later(key, lead, campaign_id)      # nothing is lost
        return {"status": "queued", "why": "models unavailable, task deferred"}

    if MODE["level"] == "degraded":
        # Outbound can wait; inbound cannot. Priority is a choice, not silence.
        enqueue_for_later(key, lead, campaign_id)
        return {"status": "queued", "why": "degraded mode: outbound deferred"}

    started = time.monotonic()
    try:
        ctx = collect_context(lead)                     # A7
        if time.monotonic() - started > deadline_s * 0.6:
            raise Degraded("time budget nearly spent on context gathering")
        draft = build_email(lead, recall(lead["id"]), ctx)   # A10, A12
        return {"status": "drafted", "draft": draft}
    except Degraded as e:
        enqueue_for_later(key, lead, campaign_id)
        return {"status": "queued", "why": str(e)}
    except Exception as e:
        release(key)                                    # not the task's fault — allow a retry
        raise
```

What matters here:

1. **The breaker replaces an avalanche with a fast failure.** When the provider is down you stop burning workers and money on doomed attempts.
2. **`claim()` before acting.** A business-meaning key (`lead + campaign`) prevents a second email to the same person even if a worker died mid-way.
3. **Three modes, and the system is sensible in each.** In "stopped", tasks are still accepted and stored — losing inbound mail is worse than handling it later.
4. **The time budget is checked mid-flight.** If context gathering ate 60% of the budget, the email is queued rather than generated into a wall.
5. **`release(key)` on unrelated errors.** A key must not block a task forever because something else broke.

**Assignment.** Run a drill: stub the provider with an always-failing client and push a hundred tasks through. Check three numbers: how many wasted requests went out after the breaker tripped (should be near zero), how many tasks were lost (zero), how many duplicates appeared in external systems (zero).

## 📌 Remember

- Backoff retries save you from a single failure; a circuit breaker saves you from a mass one.
- A system needs three modes: normal, degraded, stopped. Tasks are never lost in any of them.
- The idempotency key comes from business meaning — `lead + campaign`, not `uuid4()`.
- Claim the task before acting, not after: a worker can die between sending and recording.
- Every call has its own timeout; the task has an overall time budget checked as it runs.
- A drill with a stubbed provider is the only way to know any of this actually works.
