## 🏢 The situation

Viktor, the CFO, brings the API bill: 340 thousand for the month. You look at where it goes.

Two large line items. The first is **pre-merge checks**: the agent reviews every PR while a developer waits to merge. The second is **nightly test generation** and a **weekly supplier document audit**: three thousand documents every Saturday, results needed by Monday.

Kostya proposes: "Move everything to the Message Batches API, that is fifty percent off." You realise half of that proposal is right and the other half would stop development.

An old story surfaces alongside. The code generation job and the code review job are one process: the agent writes the code, then reviews it in the same context. Of the last thirty generated functions, review found no problems at all. QA found six.

And a third: reviews of large PRs still produce contradictory findings — in one file it proposes extracting shared logic, in another it proposes duplicating exactly that logic.

## 🎯 Your task

1. Decide which workloads suit batching and which do not.
2. Compute batch submission frequency from an SLA and handle batch failures.
3. Separate generation from review across independent instances, and remove contradictions with a multi-pass architecture.

What to remember about the Message Batches API:

- **50% cost savings**;
- **up to a 24-hour processing window**, with **no guaranteed latency SLA**;
- suitable for **non-blocking, latency-tolerant** workloads: overnight reports, weekly audits, nightly test generation;
- **unsuitable for blocking** workflows — pre-merge checks above all;
- **does not support multi-turn tool calling within a single request**: it cannot execute a tool mid-request and return the result. That rules out an entire class of agentic tasks;
- **`custom_id`** correlates request and response pairs.

Kostya's proposal has to be split: nightly test generation and the Saturday audit go to batches; pre-merge checks stay synchronous, or a developer waits a day to merge.

**Computing the frequency.** The technique from the guide: with a 30-hour SLA and processing taking up to 24 hours, a document cannot wait more than 6 hours to be submitted — send a batch every 4 hours, keeping margin for resubmissions.

**Handling failures.** Resubmit **only the failed documents**, identified by `custom_id`, with modifications that address the cause: a document that exceeded the context limit gets chunked, for instance. Blindly resending the whole batch doubles the bill and repeats the same error.

**And the technique that saves the most:** refine the prompt on a **sample set** before running the large volume. Three thousand documents processed with a bad prompt are three thousand documents to process again.

### Independent review vs self-review

The second symptom is a review that finds none of its own mistakes. The guide explains why: **a model retains reasoning context from generation, making it less likely to question its own decisions in the same session**.

And draws a conclusion people often get wrong: **independent review instances, without the prior reasoning context, are more effective at catching subtle issues than self-review instructions or extended thinking**. "Ask it to think again" and "turn on thinking" are not substitutes for an independent reviewer.

This is the same statement you met in module C13 in a CI setting; here it is stated as an architectural principle.

### Multi-pass review

The third symptom is contradictory findings. The remedy is familiar from module C6, but with a different emphasis here: **splitting into per-file local passes plus cross-file integration passes avoids attention dilution AND contradictory findings**.

The contradiction arises when one request tries to hold both the local context of twenty files and the overall picture at once. Splitting the passes removes the conflict: the local pass owns the file, the integration pass owns the data flow between files.

And a third technique of the objective: **verification passes where the model self-reports confidence alongside each finding**, to enable calibrated review routing. Low-confidence findings go to a human, high-confidence ones post directly. Calibration itself is covered in module C20.

## 💻 Practice

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

# ---------- 4.5: workload routing and batch frequency ----------
def route(workload: str, blocking: bool, needs_tool_calling: bool) -> str:
    if blocking:
        return f"{workload}: synchronous API — someone is waiting"
    if needs_tool_calling:
        return f"{workload}: synchronous API — batches do not support multi-turn tool calling"
    return f"{workload}: Message Batches API — 50% savings"

def batch_interval_hours(sla_hours: float, batch_window_hours: float = 24, reserve_hours: float = 2) -> float:
    """The longest gap between submissions that still meets the SLA, with margin for resubmission."""
    return max(0.0, sla_hours - batch_window_hours - reserve_hours)

# ---------- 4.6: generation and independent review ----------
def generate(spec: str) -> str:
    resp = client.messages.create(model=MODEL, max_tokens=1500,
        system="You write production Python. Code only, no explanations.",
        messages=[{"role": "user", "content": spec}])
    return "".join(b.text for b in resp.content if b.type == "text")

def self_review(spec: str, code: str) -> str:
    """The bad variant: the same context that produced the code."""
    resp = client.messages.create(model=MODEL, max_tokens=1500,
        system="You write production Python. Code only, no explanations.",
        messages=[{"role": "user", "content": spec},
                  {"role": "assistant", "content": code},
                  {"role": "user", "content": "Review your code and find the problems."}])
    return "".join(b.text for b in resp.content if b.type == "text")

def independent_review(code: str) -> str:
    """The correct variant: a clean context with none of the author's reasoning."""
    resp = client.messages.create(model=MODEL, max_tokens=1500,
        system="You are a reviewer. You did not write this code and do not know the author's intent. "
               "Look for defects: edge cases, swallowed errors, races, wrong conditions.",
        messages=[{"role": "user", "content": f"Review:\n```python\n{code}\n```"}])
    return "".join(b.text for b in resp.content if b.type == "text")

# ---------- 4.6: multi-pass review with self-reported confidence ----------
VERIFY_TOOL = [{
    "name": "submit_verified_findings",
    "description": "Findings with self-reported confidence for calibrated routing.",
    "input_schema": {"type": "object", "properties": {
        "findings": {"type": "array", "items": {"type": "object", "properties": {
            "file": {"type": "string"}, "issue": {"type": "string"},
            "scope": {"type": "string", "enum": ["local", "cross_file"]},
            "confidence": {"type": "string", "enum": ["high", "medium", "low"],
                           "description": "high — the defect reproduces on a concrete input; "
                                          "low — a suspicion that needs a human eye"},
        }, "required": ["file", "issue", "scope", "confidence"]}},
    }, "required": ["findings"]},
}]

def multi_pass_review(files: dict[str, str]) -> dict:
    local = {}
    for path, src in files.items():
        r = client.messages.create(model=MODEL, max_tokens=1200, tools=VERIFY_TOOL,
            tool_choice={"type": "tool", "name": "submit_verified_findings"},
            system="Local pass: only problems inside this file. scope is always local.",
            messages=[{"role": "user", "content": f"File {path}:\n```python\n{src}\n```"}])
        local[path] = next(b.input for b in r.content if b.type == "tool_use")["findings"]

    summaries = "\n".join(f"{p}: " + "; ".join(f["issue"] for f in fs) for p, fs in local.items())
    r = client.messages.create(model=MODEL, max_tokens=1200, tools=VERIFY_TOOL,
        tool_choice={"type": "tool", "name": "submit_verified_findings"},
        system="Integration pass: only data flow BETWEEN files. scope is always cross_file. "
               "Do not repeat local findings.",
        messages=[{"role": "user", "content": f"Local pass summaries:\n{summaries}"}])
    cross = next(b.input for b in r.content if b.type == "tool_use")["findings"]

    all_findings = [f for fs in local.values() for f in fs] + cross
    return {
        "auto_post": [f for f in all_findings if f["confidence"] == "high"],
        "to_human":  [f for f in all_findings if f["confidence"] != "high"],
    }

if __name__ == "__main__":
    print(route("PR pre-merge check", blocking=True, needs_tool_calling=False))
    print(route("nightly test generation", blocking=False, needs_tool_calling=False))
    print(route("support agent with MCP tools", blocking=False, needs_tool_calling=True))
    print(f"\n30h SLA → submit batches at least every {batch_interval_hours(30)}h")

    spec = "Write a function that splits an order total across line items proportionally to their weight."
    code = generate(spec)
    print("\n--- self-review (same context) ---\n", self_review(spec, code)[:400])
    print("\n--- independent review (clean context) ---\n", independent_review(code)[:400])
```

**Assignment.**

1. Run the self-review / independent-review pair on five generated functions and compare the defect counts. Then add "think especially carefully" to the self-review and check whether it catches up with the independent one.
2. Compute `batch_interval_hours` for SLAs of 26, 30 and 48 hours. Note at which SLA batching stops being viable at all.
3. Feed `multi_pass_review` three files where shared logic is duplicated. Confirm the contradictory finding ("extract it" vs "duplicate it") does not appear: the local pass does not know about it, and the integration pass sees both files.
4. Simulate a batch failure: mark two documents as failed and write a function that assembles a resubmission batch from only those, chunking the ones that are too long.

## 🎯 On the exam

- **Objective 4.5**: 50% savings, the 24-hour window, no SLA, suitability for non-blocking workloads, the absence of multi-turn tool calling, `custom_id`, computing submission frequency from an SLA, resubmitting only failed documents, refining prompts on a sample first.
- **Objective 4.6**: the limits of self-review, the superiority of an independent instance over instructions and extended thinking, local plus integration passes against attention dilution and contradictions, self-reported confidence for routing.
- Scenarios: **Structured Data Extraction** (volume, batching), **Claude Code for Continuous Integration** (pre-merge vs overnight work, independent review).
- 4.5 trap: "move every workload to batches for the savings". A pre-merge check blocks a developer — it stays synchronous.
- Second 4.5 trap: an agentic task with tools inside a batch. Batches do not support multi-turn tool calling within a request.
- 4.6 trap: "add a self-check to the prompt" or "enable extended thinking" instead of a second instance. The guide explicitly names the independent instance as more effective.
- On batch failure, the expected answer is resubmitting **only the failed** documents by `custom_id` with modifications (chunking long ones, say), not the whole batch again.

## 📌 Remember

- Batches: −50% cost, up to a 24-hour window, no latency guarantee. Right where nobody is waiting.
- Blocking workflows and multi-turn tool calling within a request stay on the synchronous API.
- Submission frequency comes from the SLA: SLA minus the processing window minus margin for resubmission.
- Only failed documents are resubmitted, by `custom_id`, with the cause addressed.
- Refine the prompt on a sample before the large volume — otherwise you pay for thousands of documents twice.
- The session that generated the code sees its defects poorly. An independent instance beats self-review and extended thinking.
- Local passes plus an integration pass remove both attention dilution and contradictory findings.
- Self-reported confidence lets doubtful findings go to a human while confident ones post directly.
