## 🏢 The situation

Six months later. Datacore's agentic marketing factory is running and you have moved up to **architect of the Claude platform**: every agentic system in the company — support, research, internal developer tooling — now goes through your review.

Wednesday morning, Kostya, the support team lead, walks over:

> "Our support agent handles refund requests. Worked perfectly for two weeks, then yesterday it went insane. Look at the logs."

You look. A conversation with a customer asking for a refund:

```
[1] Customer: I want to return order 88214, wrong item
[2] Agent  → lookup_order(88214)
[3] Tool   → {"status": "delivered", "amount": 4900, "returnable": true}
[4] Agent: "Let me check your order, one moment..."
[5] Agent  → lookup_order(88214)
[6] Tool   → {"status": "delivered", "amount": 4900, "returnable": true}
[7] Agent: "Let me check your order, one moment..."
...
[19] loop aborted: iteration limit reached (10)
[20] Sent to customer: "Let me check your order, one moment..."
```

Two hundred conversations like this in a day. The customer gets "one moment" and then silence. Kostya shows you the loop:

```python
for i in range(10):                          # iteration limit
    resp = client.messages.create(...)
    text = "".join(b.text for b in resp.content if b.type == "text")
    if "done" in text.lower() or "DONE" in text:   # ← completion signal
        break
    ...
```

Kostya: "We added a limit and a stop word, straight from the tutorial. Why did it break?"

It broke because the loop asks the text for something the API states in an explicit field. This is not a prompt bug — it is a badly built agentic loop. And it is exactly the first and heaviest objective on the CCAR-F exam.

## 🎯 Your task

1. Understand what actually drives an agentic loop — and why `stop_reason` is the only correct signal.
2. Find the three anti-patterns in Kostya's code, each of which alone is enough to break the agent.
3. Rewrite the loop so it terminates on its own, with the iteration limit as a safety net rather than as logic.

## 📚 Theory

### What an agentic loop is made of

An agent is not "a model that can call tools". It is a **loop**, and every iteration has four steps:

1. send a request to the model with the full conversation history and the tool list;
2. inspect `stop_reason` in the response;
3. if `stop_reason == "tool_use"` — execute the requested tools and **append their results to the history**;
4. repeat — until `stop_reason` becomes `"end_turn"`.

The detail people skip most often: **tool results are appended to the conversation history**. On the next iteration the model does not "remember" the call — it sees it in the messages you sent. That is why the history grows like this:

```
user:      "I want to return order 88214"
assistant: [tool_use: lookup_order(88214)]      ← model response, stop_reason="tool_use"
user:      [tool_result: {...}]                 ← your code appended the result
assistant: [text: "The order is returnable..."] ← stop_reason="end_turn"
```

If the "append `tool_result`" step is missing, or the result goes back in the wrong shape, the model sees exactly what it saw last iteration and makes exactly the same decision. That is Kostya's loop: it called `lookup_order` again and again because, as far as the model could tell, the call never happened.

### Who decides the next step

The exam draws a sharp line between two approaches, and confusing them is expensive:

| | Model-driven | Pre-configured tree |
| --- | --- | --- |
| Who picks the next tool | the model, from context | your code, from conditions |
| Flexibility on unexpected input | high | none |
| Predictability and auditability | lower | complete |
| Where it fits | high variance in requests | regulated flows with a mandatory order |

An agentic loop is the first column. If you hardcode "first `get_customer`, then `lookup_order`, then answer", that is a workflow, and `stop_reason` is not needed there. The design mistake is calling a workflow an agent: you keep the loop but make the decisions in code, and end up with neither flexibility nor predictability.

**1. Natural language as the completion signal.** "If the response contains the word 'done', exit." It breaks when the model answers in another language, rephrases, or — the opposite — says "done" mid-reasoning. Kostya's customer got "one moment" for exactly this reason: the stop word never appeared, so the loop spun for nothing.

**2. The iteration cap as the primary stopping mechanism.** You need a cap — but as a guard against an infinite loop, not as a way to finish work. If the agent routinely hits the cap, you are shipping half-finished results and you do not even know it. The correct reaction to hitting the cap is not `break` with an answer, but **an incident log and an explicit error or escalation**.

**3. The presence of a text block as a completion indicator.** The model regularly returns both text and `tool_use` in one response: "Let me check your order" plus a call to `lookup_order`. A check of "first block is text, so we are finished" will cut the agent off at its first polite sentence.

### Why this is the first objective

The "Agentic Architecture & Orchestration" domain carries 27% — more than any other — and the loop sits at its base. In the exam scenarios (a support agent with MCP tools, a multi-agent research system) the questions are usually diagnostic: you are shown a fragment of a loop or a production behaviour and asked for the cause. Almost always the cause is one of the three above, or a lost `tool_result`.

## 💻 Practice

Below is a minimal correct agentic loop. Run it with your own key and watch it terminate on its own.

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

ORDERS = {
    "88214": {"status": "delivered", "amount": 4900, "returnable": True, "days_since": 5},
}

TOOLS = [{
    "name": "lookup_order",
    "description": "Returns the state of an order by its number: delivery status, amount, "
                   "whether it is returnable, and days since delivery. "
                   "Call once per order — the data does not change during a conversation.",
    "input_schema": {
        "type": "object",
        "properties": {"order_id": {"type": "string", "description": "Order number, e.g. 88214"}},
        "required": ["order_id"],
    },
}]

def run_tool(name, args):
    if name == "lookup_order":
        return ORDERS.get(args["order_id"], {"error": "order_not_found"})
    return {"error": f"unknown_tool:{name}"}

MAX_ITERATIONS = 12   # a safety net, not termination logic

def agent(question: str):
    messages = [{"role": "user", "content": question}]
    for i in range(MAX_ITERATIONS):
        resp = client.messages.create(
            model="claude-sonnet-5",
            max_tokens=1024,
            tools=TOOLS,
            messages=messages,
        )
        print(f"  iteration {i+1}: stop_reason={resp.stop_reason}")

        # THE ONLY continuation condition
        if resp.stop_reason != "tool_use":
            text = "".join(b.text for b in resp.content if b.type == "text")
            return {"answer": text, "iterations": i + 1, "exhausted": False}

        # The model's response goes into history in full — tool_use blocks included
        messages.append({"role": "assistant", "content": resp.content})

        # EVERY call gets a result back, carrying the same tool_use_id
        results = []
        for block in resp.content:
            if block.type == "tool_use":
                out = run_tool(block.name, block.input)
                print(f"    → {block.name}({block.input}) = {out}")
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": json.dumps(out),
                })
        messages.append({"role": "user", "content": results})

    # We only get here on an anomaly: do not ship the stub as an answer
    return {"answer": None, "iterations": MAX_ITERATIONS, "exhausted": True}

if __name__ == "__main__":
    r = agent("The customer wants to return order 88214, wrong item. What should we tell them?")
    if r["exhausted"]:
        print("\n⚠ Iteration limit exhausted — incident, escalate to a human")
    else:
        print(f"\n✅ Done in {r['iterations']} iterations:\n{r['answer']}")
```

**Assignment.** Break the loop in three ways and watch exactly how it dies — these are the same failures the exam asks you to diagnose:

1. Remove `messages.append({"role": "assistant", "content": resp.content})` — the model stops seeing its own call and `lookup_order` fires again and again until the safety net. That is Kostya's bug.
2. Replace the condition with `if "done" in text.lower(): break` — then ask the question in another language.
3. Replace the condition with `if resp.content[0].type == "text": break` — then add a line to the prompt asking the model to narrate what it is doing.

## 🎯 On the exam

- **Objective 1.1** is fully covered: the lifecycle, `stop_reason`, appending `tool_result` to history, the anti-patterns.
- Shows up in the scenarios: **Customer Support Resolution Agent** (the agent loops or replies with half-finished text) and **Multi-Agent Research System** (a subagent never terminates).
- Wording trap: answer options often offer "raise the iteration limit" or "tell the model in the prompt to write DONE". Both treat the symptom and are wrong — the correct answer is always about `stop_reason` and the integrity of the message history.
- Keep the **model-driven vs pre-configured sequence** distinction in mind: a question may be testing precisely whether you know that a hardcoded call order is no longer an agentic loop.

---

## 📌 Remember

- The loop continues while `stop_reason == "tool_use"` and ends on `"end_turn"`. Everything else is guessing protocol state from prose.
- The model's response and the tool results are **both** appended to the history. Skip that step and the agent will keep making the same decision forever.
- A result carries the same `tool_use_id`, and if the model requested several tools, all of them get results back.
- An iteration cap is mandatory, but it is a safety net. Hitting it is an incident and an escalation, not a way to produce an answer.
- The model talks and acts in the same response. Text in a response does not mean the work is finished.
