# Module A5. Grounding in company knowledge

> **Level:** Junior AI · **Time:** ~60 minutes · **Format:** situation → theory → practice → quiz

---

## 🏢 The situation

An email went out to a customer. In it: "Our platform supports 1C integration out of the box."

We do not support 1C integration. At all.

Victor, the CFO, forwards the email with one word: "Explain." Igor is angrier: the customer replied "great, show me on a demo" — and now someone has to explain that it does not exist.

The model did not lie on purpose. It was asked to write a convincing email about a platform for ML teams, so it assembled a plausible claim from general knowledge about such platforms. **It does not know our product.** Everything it knows about it is three lines in the system prompt.

## 🎯 Your task

1. Give the agent access to real facts about the product: docs, the pricing page, the support FAQ.
2. Make it rely on what it retrieved rather than on general impressions.
3. Detect when no facts were found — and stop it from writing at all.

---

## 📚 Theory

### Why models make things up

A model predicts a plausible continuation. If the fact is not in the context but the task demands a claim, it will produce the statistically expected claim. That is not a bug, that is how it works.

The cure is not asking "don't make things up" (we tried that in A1) but **grounding**: the fact must physically be in the context at generation time.

### Chunking: where to cut a document

Bad chunking is every 1000 characters: the section heading ends up in one chunk and the fact in another, and retrieval never connects them.

Rules that work:

- Cut **by structure** — headings, sections, FAQ entries. One chunk, one complete thought.
- **Put context inside the chunk**: the section path ("Pricing → Plans → Enterprise") at the start of the chunk text. Otherwise a chunk reading "Includes 5 seats" will never match a query about Enterprise.
- Keep a couple of sentences of **overlap** between neighbours so a fact on the boundary is not lost.
- Store the **source** with the chunk: file, section, last update. Without it you can neither verify an answer nor show a link.

### Admitting ignorance is a feature

The most valuable behavior of a RAG agent is saying "the knowledge base has no answer". That requires two things:

1. In the prompt: "answer only from the retrieved fragments; if they are insufficient, return `insufficient_context`".
2. In code: if the model returns that flag, or no chunk clears a minimum similarity, do not generate the email — hand the lead to a human.

Without the second condition the first does not hold: under task pressure the model will write something anyway.

## 💻 Practice

A minimal RAG with no external vector database — just numpy. For thousands of chunks that is enough; a dedicated store starts to matter in the tens of thousands.

```python
# pip install anthropic numpy
import os, json, re, numpy as np, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"
MIN_SIMILARITY = 0.35        # below this we treat it as "not found"

# --- 1. Structure-aware chunking, with the section path inside the chunk ---
def chunk_markdown(text, source):
    chunks, path, buf = [], [], []
    def flush():
        if buf:
            body = " ".join(buf).strip()
            if body:
                chunks.append({"text": " › ".join(path) + ": " + body, "source": source,
                               "section": " › ".join(path)})
    for line in text.splitlines():
        m = re.match(r"^(#{1,3})\s+(.*)", line)
        if m:
            flush(); buf = []
            level = len(m.group(1))
            path = path[:level - 1] + [m.group(2).strip()]
        else:
            buf.append(line)
    flush()
    return chunks

# --- 2. Embeddings (any provider; the interface is stubbed here) ---
def embed(texts):
    """Return an (n, d) matrix. Plug in your embeddings provider."""
    raise NotImplementedError("connect an embeddings provider")

KB = []
for path in ["docs/product.md", "docs/pricing.md", "docs/faq.md"]:
    KB += chunk_markdown(open(path, encoding="utf-8").read(), path)
KB_VECTORS = embed([c["text"] for c in KB])
KB_VECTORS /= np.linalg.norm(KB_VECTORS, axis=1, keepdims=True)

# --- 3. Retrieval ---
def search(query, k=4):
    q = embed([query])[0]
    q /= np.linalg.norm(q)
    sims = KB_VECTORS @ q
    idx = np.argsort(-sims)[:k]
    return [(KB[i], float(sims[i])) for i in idx]

# --- 4. Generation strictly from what was retrieved ---
SYSTEM = """You write a cold email on behalf of Datacore.

Take product claims ONLY from the FACTS block. If the facts are not enough for a
convincing email, return insufficient_context=true and do not invent anything.
Tag every product capability claim with its source from the FACTS block."""

def write_email(lead):
    query = f"{lead['industry']} {lead['role']} product capabilities integrations"
    found = search(query)
    if not found or found[0][1] < MIN_SIMILARITY:
        return None, "no relevant product facts retrieved"

    facts = "\n\n".join(f"[{i+1}] ({c['section']}, {c['source']})\n{c['text']}"
                        for i, (c, s) in enumerate(found))
    resp = client.messages.create(
        model=MODEL, max_tokens=900, temperature=0.7, system=SYSTEM,
        tools=[GROUNDED_DRAFT_TOOL],           # + claims[] and insufficient_context fields
        tool_choice={"type": "tool", "name": "save_draft"},
        messages=[{"role": "user",
                   "content": f"LEAD:\n{json.dumps(lead)}\n\nFACTS:\n{facts}"}],
    )
    draft = next(b for b in resp.content if b.type == "tool_use").input
    if draft.get("insufficient_context"):
        return None, "the model reported insufficient facts"

    # Check in code: every product claim must reference a source
    for claim in draft.get("claims", []):
        if not claim.get("source_index"):
            return None, f"claim without a source: {claim['text'][:60]}"
    return draft, None


lead = {"company": "NordFin", "industry": "fintech", "role": "Head of Data",
        "trigger": "posted an ML engineer job opening"}
draft, why = write_email(lead)
if draft is None:
    print(f"— lead handed to a human: {why}")   # this is the correct outcome, not a failure
else:
    print(draft["subject"]); print(draft["body"])
    for c in draft["claims"]:
        print(f"  · {c['text']} → source [{c['source_index']}]")
```

What matters here:

1. **The section path inside the chunk text.** Without it, a chunk reading "Includes 5 seats" never matches a query about the Enterprise plan.
2. **A similarity threshold.** If the best chunk is below it, the knowledge base simply has nothing on this question and there is nothing to generate from.
3. **Two independent stop signals:** the model's flag and the threshold in code. Either one halts the email.
4. **Claims with sources.** An email where every product claim links to a documentation chunk can be verified in a minute — and that is exactly what would have caught the "1C integration".

**Assignment.** Take three real documentation pages from your product, chunk them, ask five questions the pages do not answer — and confirm the agent refused to write in all five cases. Refusing on an unanswerable question is the main sign that RAG works.

---

## 📌 Remember

- Models do not invent maliciously: with no fact in context, they emit the statistically plausible claim.
- "Don't make things up" does not work; grounding does — the fact must physically be in context.
- RAG quality is set by retrieval, not by the model. Debugging starts with printing the retrieved chunks.
- Chunk by structure and put the section path inside the chunk; keep the source next to the text.
- A similarity threshold and an `insufficient_context` flag are two independent ways to say "I don't know".
- A product claim without a source reference counts as a defect. That is how emails get verified in a minute.
