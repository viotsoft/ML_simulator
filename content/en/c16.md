## 🏢 The situation

Syntax errors disappeared after C15. What remains is that 12% and 6% — the semantics. Dasha brings three concrete production cases.

**Case 1.** An invoice with four line items: 22,200 + 15,000 + 3,400 + 900. The extraction has `stated_total: 37,200` — as printed — while the items sum to 41,500. The supplier made a typo, but the system does not know that and pushes an inconsistent invoice into the ERP.

**Case 2.** An extraction failed validation: the delivery date was in the wrong format. The system retried — with the same prompt and the same document. Five times. Same result.

**Case 3.** The required `contract_number` field is empty in 30% of documents. The system retries each of those three times. You dig in: those invoices have no contract number — it lives in an annex to a framework agreement nobody ever gave the system. Retries will never help.

And separately, from code review (module C14): Kostya says developers dismiss findings but there is no way to see the pattern — the dismissed findings have nothing to group them by.

## 🎯 Your task

1. Build a validate → specific error → retry loop instead of blind retries.
2. Learn to tell cases where a retry helps from cases where it is pointless.
3. Design self-checks into the schema itself, and add a field that makes false positives analysable.

## 📚 Theory

### Retry with error feedback

The core technique: on retry, **the specific validation errors are appended to the prompt**. Not "try again", but "here is the document, here is your previous answer, here is what is wrong with it".

The exam asks you to **identify when retries will be ineffective**: if the required information is simply absent from the source, there is nothing to repeat. Dasha's case 3 is exactly that — thirty percent of documents burning three attempts each on a field they physically do not contain. The right response is to return `null` (see schema design in C15) and flag the document as needing an additional source.

### Self-checks built into the schema

Case 1 — the total that does not sum — is solved by an elegant technique from the guide: **extract `calculated_total` alongside `stated_total`** so the discrepancy becomes visible.

```json
{
  "stated_total": 37200.00,      ← as printed in the document
  "calculated_total": 41500.00,  ← the sum of line items, computed by the model
  "totals_match": false,
  "conflict_detected": true,
  "conflict_note": "Line items exceed the stated total by 4300"
}
```

None of these fields "validates" in the strict sense — your code does the validating by comparing two numbers. But the schema forces the model to **write both values out explicitly**, and the discrepancy goes from invisible to checkable in one line of code.

The second form of the same technique is a boolean **`conflict_detected`** for inconsistent source data: one date in the header and another by the signature; USD in the line items and EUR in the total.

### detected_pattern: analysing false positives

Kostya's review problem is solved by one extra field. The guide names the skill directly: **add `detected_pattern` fields to structured findings to enable analysis of false positive patterns when developers dismiss findings**.

The point is that a finding stops being unique prose and gains a **machine-readable label for the construct** that triggered it:

```json
{
  "category": "correctness",
  "message": "The exception may be lost on timeout",
  "detected_pattern": "broad_except_with_return_default"
}
```

Now dismissed findings group up: "pattern `broad_except_with_return_default` dismissed 34 times out of 36" — and you know exactly which few-shot example to add (module C14). Without the label you have 214 different texts and no pattern at all.

### A distinction that is easy to forget

| Error type | What removes it |
| --- | --- |
| JSON syntax | tool use with a schema (C15) — gone as a class |
| Semantics: does not sum, wrong field, contradicts | code validation + retry with feedback |

This continues the point from C15: the schema is about shape, validation is about meaning.

## 💻 Practice

The full loop: extract → validate → retry with specific errors → decide when it is hopeless.

```python
# pip install anthropic
import os, json, re, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

EXTRACT_TOOL = [{
    "name": "extract_invoice",
    "description": "Extract invoice data.",
    "input_schema": {"type": "object", "properties": {
        "invoice_number": {"type": "string"},
        "invoice_date": {"type": "string", "description": "strictly YYYY-MM-DD"},
        "line_items": {"type": "array", "items": {"type": "object", "properties": {
            "description": {"type": "string"}, "amount": {"type": "number"},
        }, "required": ["description", "amount"]}},
        "stated_total": {"type": "number", "description": "The total AS PRINTED in the document"},
        # a self-check inside the schema
        "calculated_total": {"type": "number",
                             "description": "The sum of all line item amounts, computed by you. "
                                            "Compute it honestly even if it differs from stated_total."},
        "conflict_detected": {"type": "boolean",
                              "description": "true when the document contains inconsistent data "
                                             "(differing dates, differing currencies, totals that do not sum)"},
        "conflict_note": {"type": ["string", "null"], "description": "What exactly is inconsistent"},
        "contract_number": {"type": ["string", "null"],
                            "description": "Contract number. null when THIS document does not contain it."},
    }, "required": ["invoice_number", "invoice_date", "line_items",
                    "stated_total", "calculated_total", "conflict_detected"]},
}]

def validate(data: dict) -> list[str]:
    """Semantic validation: what a schema cannot guarantee."""
    errors = []
    if not re.fullmatch(r"\d{4}-\d{2}-\d{2}", data.get("invoice_date", "")):
        errors.append(f"invoice_date = {data.get('invoice_date')!r}: the format must be YYYY-MM-DD")
    s, c = data.get("stated_total"), data.get("calculated_total")
    items_sum = round(sum(i["amount"] for i in data.get("line_items", [])), 2)
    if c is not None and abs(c - items_sum) > 0.01:
        errors.append(f"calculated_total = {c}, but the line items sum to {items_sum}: recompute")
    if s is not None and c is not None and abs(s - c) > 0.01 and not data.get("conflict_detected"):
        errors.append(f"stated_total = {s} differs from calculated_total = {c}, "
                      "yet conflict_detected = false: flag the discrepancy")
    return errors

# Missing data is not a validation error: retrying it is pointless
def missing_from_source(data: dict) -> list[str]:
    return [k for k in ("contract_number",) if data.get(k) is None]

def extract_with_retry(document: str, max_attempts: int = 3):
    messages = [{"role": "user", "content": f"Extract the invoice data.\n\nDocument:\n{document}"}]
    for attempt in range(1, max_attempts + 1):
        resp = client.messages.create(model=MODEL, max_tokens=2000, tools=EXTRACT_TOOL,
                                      tool_choice={"type": "tool", "name": "extract_invoice"},
                                      messages=messages)
        data = next(b.input for b in resp.content if b.type == "tool_use")
        errors = validate(data)
        print(f"  attempt {attempt}: validation errors — {len(errors)}")
        if not errors:
            return {"data": data, "attempts": attempt,
                    "needs_external_source": missing_from_source(data)}

        # Retry WITH FEEDBACK: the document + the failed extraction + the specific errors
        messages = [
            {"role": "user", "content": f"Extract the invoice data.\n\nDocument:\n{document}"},
            {"role": "assistant", "content": resp.content},
            {"role": "user", "content":
                "The extraction failed validation. Errors:\n"
                + "\n".join(f"— {e}" for e in errors)
                + "\n\nCorrect exactly these. Leave the other fields as they are. "
                  "If the data is not in the document, return null — do not invent it."},
        ]
    return {"data": data, "attempts": max_attempts, "unresolved": errors}

DOC = """
INVOICE No. 4412 of 14.08.2026
Steel profile           22,200.00
Mounting hardware       15,000.00
Delivery                 3,400.00
Packaging                  900.00
                Total:  37,200.00
"""

if __name__ == "__main__":
    r = extract_with_retry(DOC)
    d = r["data"]
    print(f"\nstated_total     : {d['stated_total']}")
    print(f"calculated_total : {d['calculated_total']}")
    print(f"conflict_detected: {d['conflict_detected']} — {d.get('conflict_note')}")
    print(f"attempts         : {r['attempts']}")
    if r.get("needs_external_source"):
        print(f"⚠ external source needed for: {r['needs_external_source']} — retries will not help")
```

**Assignment.**

1. Replace the feedback retry with a blind one (leave `messages` unchanged between attempts) and feed a document with the date as `14/08/26`. Count how many attempts are wasted.
2. Remove `calculated_total` from the schema and check whether the system notices the inconsistent invoice at all. That is Dasha's case 1.
3. Make `contract_number` required (drop `null`) and feed a document without one. Compare the behaviour with the current version: how many retries, and what ends up in the field.
4. Add a `detected_pattern` field to the review findings from module C14, enumerating your construct categories. Run it over ten diffs and group by pattern — it becomes obvious which few-shot examples are needed first.

## 🎯 On the exam

- **Objective 4.4** is covered: retry with error feedback, the limits of retries, `detected_pattern` for dismissal analysis, self-checks via `calculated_total`/`stated_total` and `conflict_detected`, semantic errors vs syntax errors.
- Scenario: **Structured Data Extraction**, and partly **Claude Code for Continuous Integration** (false positive analysis).
- Retry trap: "raise the attempt count" or "add exponential backoff" when the information is absent from the document. The expected answer is recognising that retries are ineffective and requesting a different source.
- Repeat trap: "resend the same request" vs "include the source document, the failed extraction and the specific errors in the retry". The latter.
- Totals trap: "add a request to check the arithmetic to the prompt". The guide's technique is more concrete — extract the computed total alongside the stated one so the discrepancy becomes data.
- For `detected_pattern`, remember the motivation: without a machine-readable label, dismissed findings cannot be grouped or systematically analysed.

---

## 📌 Remember

- A retry without feedback is the same request: the model does not know what was wrong and answers the same way.
- A retry carries the source document, the failed extraction and the **specific** validation errors.
- Retries help with format mismatches and structural output errors. When the information is absent from the source they never help — you need a different document.
- `calculated_total` beside `stated_total` turns an invisible discrepancy into a checkable field. `conflict_detected` does the same for inconsistent data.
- `detected_pattern` on findings lets you group dismissals and attack false positives systematically.
- The schema removes syntax; code validation removes semantics. They are different layers, and the second does not vanish with the first.
