## 🏢 The situation

The first complaint from a customer rather than a colleague. Igor forwards it:

> "This is the third time you've sent me the same thing. In January I replied that we are not considering new vendors until the end of the year. Do you not read replies?"

You check: the January reply is in the CRM, category `not_now`, return date December. Everything was recorded correctly. The agent that wrote in March simply knew nothing about it: it received a CRM row with company, role and trigger — and wrote a first touch.

An agent without memory introduces itself anew every time. To a human that reads as disrespect.

1. Separate what the agent remembers within one task from what it remembers between tasks.
2. Put only what is relevant into context: the whole history cannot go in.
3. Answer Olya from legal: how much you store, for how long, and what happens on a deletion request.

### More context ≠ better

The temptation: "the window is 200k tokens, let's paste the entire history". Three reasons not to:

1. **Money.** You pay for every token on every call. Twenty emails of history across 3000 leads is a visible line on the bill.
2. **Accuracy.** Models are worse at finding what matters in long contexts, especially in the middle. Five relevant facts beat twenty pages.
3. **Privacy.** Everything that enters the context enters your logs, traces and possibly the email itself.

The rule: **extract facts, do not store transcripts**. After each interaction, write a short record of what you learned about the customer.

### A memory fact is a structure

Not "the customer said it's not the right time" but an object: kind (`constraint`), value (`not before December 2026`), source (`email msg-4821`), date, lifetime. Such a fact can be filtered for freshness, shown to a human and deleted on request.

Pay special attention to **contradictions**. In January the customer said "not before December"; in May they wrote "actually, let's talk now". The fresher fact wins, but the older one is not erased: it explains the history of the relationship.

### Privacy: Olya's answer

Three questions your memory design must answer:

- **What do we store?** Only facts needed for the work. Not "the customer was rude", not health, not private life.
- **For how long?** Every fact has a lifetime. A date constraint ("don't write until December") lives until that date plus a buffer; a note about someone's role, a year; an unsubscribe, **forever**, or you will write to them again.
- **How do we delete it?** A personal-data deletion request must be one operation keyed by the customer — covering facts, logs and traces. If that is impossible, you are not ready for such a request.

## 💻 Practice

```python
import os, json, sqlite3, datetime as dt, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

db = sqlite3.connect("memory.db")
db.execute("""CREATE TABLE IF NOT EXISTS facts (
    id INTEGER PRIMARY KEY, lead_id TEXT NOT NULL, kind TEXT NOT NULL,
    value TEXT NOT NULL, source TEXT, created_at TEXT NOT NULL,
    expires_at TEXT, superseded_by INTEGER)""")
db.execute("CREATE INDEX IF NOT EXISTS idx_lead ON facts(lead_id)")

# Lifetime depends on the fact kind: an unsubscribe never expires
TTL_DAYS = {"constraint": 400, "role": 365, "objection": 365,
            "referral": 180, "unsubscribe": None}

EXTRACT_TOOL = {
    "name": "save_facts",
    "description": "Extract facts about the customer that will matter in the future",
    "input_schema": {"type": "object", "properties": {
        "facts": {"type": "array", "items": {"type": "object", "properties": {
            "kind": {"type": "string", "enum": list(TTL_DAYS)},
            "value": {"type": "string", "description": "The fact in one phrase, not a retelling"},
        }, "required": ["kind", "value"]}}}, "required": ["facts"]},
}

def remember(lead_id, email_text, message_id):
    """After each interaction, extract facts rather than storing a transcript."""
    resp = client.messages.create(
        model=MODEL, max_tokens=500, temperature=0,
        system="Extract only facts that affect future contact: timing constraints, role and "
               "authority, objections, referrals to other people, unsubscribes. "
               "Never store emotions, health or personal circumstances. Always call save_facts.",
        tools=[EXTRACT_TOOL], tool_choice={"type": "tool", "name": "save_facts"},
        messages=[{"role": "user", "content": email_text}])
    facts = next(b for b in resp.content if b.type == "tool_use").input["facts"]

    now = dt.datetime.now(dt.timezone.utc)
    for f in facts:
        ttl = TTL_DAYS[f["kind"]]
        expires = (now + dt.timedelta(days=ttl)).isoformat() if ttl else None
        # A new fact of the same kind supersedes the old one without erasing it
        db.execute("UPDATE facts SET superseded_by = -1 WHERE lead_id = ? AND kind = ? "
                   "AND superseded_by IS NULL", (lead_id, f["kind"]))
        db.execute("INSERT INTO facts (lead_id, kind, value, source, created_at, expires_at) "
                   "VALUES (?,?,?,?,?,?)",
                   (lead_id, f["kind"], f["value"], message_id, now.isoformat(), expires))
    db.commit()
    return facts


def recall(lead_id):
    """Only current facts go into context — never the whole history."""
    now = dt.datetime.now(dt.timezone.utc).isoformat()
    rows = db.execute(
        "SELECT kind, value, created_at FROM facts WHERE lead_id = ? AND superseded_by IS NULL "
        "AND (expires_at IS NULL OR expires_at > ?) ORDER BY created_at DESC LIMIT 8",
        (lead_id, now)).fetchall()
    return [{"kind": k, "value": v, "since": c[:10]} for k, v, c in rows]


def can_contact(lead_id):
    """Hard blocks are checked in code before generation, not suggested to the model."""
    now = dt.datetime.now(dt.timezone.utc).isoformat()
    if db.execute("SELECT 1 FROM facts WHERE lead_id=? AND kind='unsubscribe'",
                  (lead_id,)).fetchone():
        return False, "the customer unsubscribed"
    row = db.execute("SELECT value, expires_at FROM facts WHERE lead_id=? AND kind='constraint' "
                     "AND superseded_by IS NULL AND expires_at > ? ORDER BY created_at DESC LIMIT 1",
                     (lead_id, now)).fetchone()
    if row and "december" in row[0].lower() and dt.date.today().month < 12:
        return False, f"customer constraint: {row[0]}"
    return True, None


def forget(lead_id):
    """Right to be forgotten: one operation removes everything for this customer."""
    n = db.execute("DELETE FROM facts WHERE lead_id = ?", (lead_id,)).rowcount
    db.commit()
    purge_traces(lead_id)          # and traces too — otherwise deletion is incomplete
    return n


# --- Usage ---
ok, why = can_contact("lead-4821")
if not ok:
    print(f"— not writing: {why}")        # exactly what would have prevented the third email
else:
    memory = recall("lead-4821")
    draft = generate_grounded(lead, ctx, memory=memory)   # facts go into the email context
```

What matters here:

1. **Extraction instead of transcripts.** The store holds eight short facts, not twenty emails.
2. **A lifetime per kind.** An unsubscribe never expires — that is a requirement, not an optimization.
3. **A hard check in code.** `can_contact` stops the email before generation: the model must not "decide" whether to respect a customer's constraint.
4. **History is preserved via `superseded_by`.** A new fact supersedes the old one, but you can still see that the customer changed their mind.
5. **`forget()` deletes everything by key**, traces included. Without that last part, deletion is only formal.

## 📌 Remember

- Memory means extracted facts with a lifetime, not the whole correspondence in context.
- Long context costs money, lowers accuracy and spreads personal data across your logs.
- A memory fact is a structure: kind, value, source, date, lifetime. Otherwise it cannot be filtered or deleted.
- Contradictions resolve by freshness, but the old fact stays — it explains the relationship's history.
- Hard constraints (unsubscribe, "not before December") are enforced in code before generation, not advised to the model.
- The right to be forgotten is one operation keyed by the customer, logs and traces included.
