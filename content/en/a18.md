# Module A18. Designing for trust

> **Level:** Senior AI · **Time:** ~50 minutes · **Format:** situation → theory → practice → quiz

---

## 🏢 The situation

The system is rolled out to the whole sales team, not just Igor. Five new managers, half an hour of training.

Two weeks later you look at per-person statistics and see three distinct behaviors:

- **Two** approve emails in batches without looking. Their edit rate is 2%. Not because the emails are better, but because they do not read them.
- **Two** rewrite nearly every email in full. Writing from scratch would be faster.
- **One** works as intended: skims, edits the occasional one, sends.

The interface is identical for all of them. The difference is trust: the first group trusts blindly, the second not at all, and both are worse than deliberate review.

Marina states the task: "Make it obvious when someone can click through and when they need to read carefully."

## 🎯 Your task

1. Show the agent's uncertainty in a way that actually changes human behavior.
2. Explain decisions through evidence rather than the model's "reasoning".
3. Make undo available — it affects trust more than any explanation.

---

## 📚 Theory

### Calibrated trust

The goal of the interface is not "maximum trust" but **trust that matches quality**. Blind trust and total distrust are equally bad: the first lets errors through, the second means the automation never pays off.

### How to show uncertainty

Three levels, from useless to useful:

1. **A number, "confidence: 0.72"** — nearly useless. People are not calibrated on probabilities and soon stop noticing them.
2. **A category with a consequence** — "needs attention: the hook is weak". This works: it says what is wrong and what to do.
3. **Different interface behavior** — confident emails grouped into an "approve all" batch, doubtful ones shown one at a time with the problem highlighted. This works best because it acts before the person starts reading.

The key: **uncertainty must change the interface, not merely the text inside it**.

### An explanation is evidence, not reasoning

The temptation is to show the model's "chain of thought". The problem is that coherent reasoning raises trust regardless of whether the conclusion is right. A convincing explanation of a wrong email is more dangerous than no explanation.

What to show instead — **verifiable evidence**:

| Bad | Good |
| --- | --- |
| "I chose to mention their growth because it fits" | Hook: ML engineer job opening · source: careers page, March 12 |
| "Confident about the product facts" | 3 product claims · all linked to documentation |
| "The tone is appropriate" | Checks: length ✓ · no price mentioned ✓ · question present ✓ |

The difference is that evidence can be **verified in seconds**, while reasoning can only be believed.

### Undo matters more than explanation

The strongest trust tool is the ability to cancel. From A11 we already have a cancel window. The interface must make it visible: "sends in 14 minutes, cancel". Someone who knows they can stop it is calmer about automation — and, paradoxically, intervenes less.

## 💻 Practice

The server side that shapes what a manager sees:

```python
def review_item(draft, ctx, memory, checks, lead):
    """Assemble the review card: a trust signal plus verifiable evidence."""
    # 1. The confidence signal comes from objective features, not the model's self-assessment
    signals = {
        "has_trigger": bool(ctx.get("jobs") or ctx.get("news")),
        "hook_has_source": bool(draft.get("hook_source")),
        "all_claims_sourced": all(c.get("source_index") for c in draft.get("claims", [])),
        "checks_passed": not checks["problems"],
        "no_open_deal": not lead.get("has_open_deal"),
        "memory_fresh": all(f.get("since", "") >= recent_cutoff() for f in memory),
    }
    weak = [k for k, v in signals.items() if not v]

    if not weak:
        band = "confident"       # eligible for batch approval
    elif len(weak) == 1 and weak[0] in {"memory_fresh"}:
        band = "check"           # look, but quickly
    else:
        band = "attention"       # one at a time, with highlighting

    return {
        "band": band,
        "weak_signals": weak,
        # 2. Evidence instead of reasoning: each item verifiable in seconds
        "basis": {
            "hook": {"text": draft.get("personalization"),
                     "source": draft.get("hook_source"),
                     "date": ctx.get("news_date") or ctx.get("jobs_date")},
            "claims": [{"text": c["text"], "source": source_link(c["source_index"])}
                       for c in draft.get("claims", [])],
            "memory": [{"fact": f["value"], "since": f["since"]} for f in memory],
            "checks": checks["passed"],
        },
        # 3. Undo is always visible
        "undo": {"available_until": checks.get("send_at"), "action": "cancel"},
        "highlight": highlight_spans(draft, weak),   # highlight the problem spots in the text
    }


def highlight_spans(draft, weak_signals):
    """Highlight exactly what pushed this email into 'attention'."""
    spans = []
    if "hook_has_source" in weak_signals and draft.get("personalization"):
        spans.append({"text": draft["personalization"], "why": "hook has no source"})
    for c in draft.get("claims", []):
        if not c.get("source_index"):
            spans.append({"text": c["text"], "why": "claim unsupported by documentation"})
    return spans


# --- Batch approval is available only for confident items ---
def batch_approve(item_ids, user_email):
    items = [load_item(i) for i in item_ids]
    blocked = [i["id"] for i in items if i["band"] != "confident"]
    if blocked:
        return {"error": "the batch contains emails that need attention", "items": blocked}
    for i in items:
        approve(i["id"], user_email)      # A11: every approval is an audit record
    return {"approved": len(items)}


# --- Calibration metric: does trust match quality? ---
def trust_calibration(days=14):
    """If 'confident' has as many edits as 'attention', the signal is useless."""
    out = {}
    for band in ("confident", "check", "attention"):
        items = load_reviewed(days, band=band)
        out[band] = {
            "emails": len(items),
            "edit_rate": round(share(items, lambda i: i["edited"]), 3),
            "cancel_rate": round(share(items, lambda i: i["cancelled"]), 3),
        }
    ok = out["attention"]["edit_rate"] > out["confident"]["edit_rate"] * 2
    out["signal_is_useful"] = ok
    return out
```

What this changes for those five managers:

1. **Batch approval is confined to "confident".** The people who clicked through blindly physically cannot do that to a doubtful email.
2. **Highlighting points at the specific phrase** that made the email need attention. The people rewriting everything can see that one sentence is what needs fixing.
3. **Evidence instead of reasoning.** A hook with a link to the careers page is verified in two seconds; "I judged it appropriate" never is.
4. **The calibration metric audits the signal itself.** If "confident" has the same edit rate as "attention", your signal is decoration, not a tool.

**Assignment.** Look at your own users' statistics: are there people whose edit rate is near zero, and others near one? Both extremes are an interface defect, not a people problem. Ask both groups what they see at the moment of deciding.

---

## 📌 Remember

- The goal is calibrated trust, not maximum trust: blind trust and total distrust are equally harmful.
- A confidence number is nearly useless; changing the interface's behavior is what works.
- Show verifiable evidence, not a chain of thought: convincing reasoning raises trust regardless of correctness.
- Highlight the specific span that caused the doubt, not the whole email.
- Batch approval belongs only where the system is confident; otherwise the gate becomes fiction (A11).
- Accessible undo builds more trust than any explanation — and reduces unnecessary interventions.
