## 🏢 The situation

Two incidents on the same day, both about context, and they look nothing alike.

**Incident one.** A customer is deep in a conversation with the support agent: three orders, two disputed charges, a promise to refund 4900 within five days. On the fortieth turn the agent writes: "We will refund you shortly." The customer: "You promised 4900 within five days — have you forgotten?"

Here is what happened. The history was summarised as it grew, and "refund 4900 on order 88214 by 19 August" became "a refund was discussed". Numbers, dates and promises went first — they are short, and in a summary they look like details.

You notice a second problem in the same log: every `lookup_order` call returns forty-odd fields, from package dimensions to warehouse id, and all of them sit in the context. Five of them are useful.

**Incident two.** Artem is three hours into exploring billing in Claude Code. Early on the agent named concrete classes: `RefundProcessor`, `GatewayRetryPolicy`. Now it answers vaguely: "systems like this usually have a retry layer." The specifics found an hour ago are gone.

## 🎯 Your task

1. Preserve transactional facts so summarisation cannot eat them.
2. Remove what does not belong in the context and arrange what does, accounting for position effects.
3. Structure a long codebase exploration so the specifics do not degrade.

The **progressive summarization risk** is stated concretely in the guide: numerical values, percentages, dates and customer-stated expectations get condensed into vague summaries. That is exactly how "4900 by 19 August" became "a refund was discussed".

The answer is a **case facts block**: transactional facts are extracted into a separate structure **included in each prompt, outside the summarised history**. Summarisation operates on the conversation; the facts live apart and are never compressed.

```
[CASE FACTS — do not summarise]
customer_id: C-88214
open_issues:
  - order 88214: refund 4900, promised by 2026-08-19, status approved
  - order 88301: disputed charge 1200, status investigating
promises_made: refund within 5 business days (stated 2026-08-14)

[CONVERSATION HISTORY — the summarised part]
...
```

The **"lost in the middle" effect**: models reliably process information at the beginning and end of long inputs but may omit findings from middle sections. Hence the skill: **place key findings summaries at the beginning of aggregated inputs** and organise detailed results with **explicit section headers**.

**Tool output bloat.** A `lookup_order` response with forty fields consumes tokens disproportionately to its relevance. The technique: **trim verbose tool outputs to only relevant fields before they accumulate in context**. Technically this is the same `PostToolUse` from module C5 — with a different goal: not normalisation but economy.

And two techniques for multi-agent systems:

- **require subagents to include metadata** in structured outputs (dates, source locations, methodological context) — otherwise synthesis upstream receives facts with nothing to stand on;
- **modify upstream agents to return structured data** (key facts, citations, relevance scores) instead of verbose content and reasoning chains when downstream agents have limited context budgets.

### Context degradation in long exploration

The second incident is objective 5.4. The symptom is described in the guide almost verbatim: in extended sessions the model starts giving inconsistent answers and **referencing "typical patterns" rather than the specific classes discovered earlier**. Exactly what Artem sees.

Four tools against it:

**1. Scratchpad files.** The agent records key findings in a file and references it for later questions. A finding that reaches a file survives a context boundary; one left in the conversation does not.

**2. Subagent delegation.** Verbose exploration goes to a subagent while the main agent keeps high-level coordination. "Find all test files", "trace the refund flow dependencies" are the canonical assignments.

**3. Summarising between phases.** Before spawning the next phase's subagents, the key findings of the previous phase are summarised and **injected into the new agents' initial context**.

**4. `/compact`.** The built-in way to reduce context usage in an extended session when it fills with verbose discovery output.

And a separate technique — **crash recovery**: each agent exports its state to a known location, and on resume the coordinator loads a manifest and injects it into agent prompts. That is not about economy but about a crash in hour six not erasing the work.

## 💻 Practice

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

# ---------- 5.1: case facts outside the summarised history ----------
RELEVANT_ORDER_FIELDS = ("order_id", "status", "amount", "delivered_at", "returnable")

def trim_tool_output(name: str, result: dict) -> dict:
    """Trim to the relevant BEFORE it reaches the context (the same hook as C5)."""
    if name == "lookup_order":
        return {k: v for k, v in result.items() if k in RELEVANT_ORDER_FIELDS}
    return result

class CaseFacts:
    """Transactional facts live apart and are never summarised."""
    def __init__(self, customer_id: str):
        self.customer_id = customer_id
        self.issues: list[dict] = []
        self.promises: list[str] = []

    def add_issue(self, **kw): self.issues.append(kw)
    def add_promise(self, text: str): self.promises.append(text)

    def render(self) -> str:
        lines = ["[CASE FACTS — do not summarise]", f"customer_id: {self.customer_id}"]
        for i in self.issues:
            lines.append("  - " + ", ".join(f"{k}: {v}" for k, v in i.items()))
        for p in self.promises:
            lines.append(f"  promised: {p}")
        return "\n".join(lines)

def build_prompt(facts: CaseFacts, summarized_history: str, user_message: str) -> str:
    # Summary at the start, details under explicit headers: against "lost in the middle"
    return (
        facts.render()
        + "\n\n[CONVERSATION SUMMARY]\n" + summarized_history
        + "\n\n[CURRENT CUSTOMER MESSAGE]\n" + user_message
    )

# ---------- 5.4: scratchpad and delegation in long exploration ----------
SCRATCHPAD = "exploration-notes.md"

def note(finding: str):
    with open(SCRATCHPAD, "a", encoding="utf-8") as f:
        f.write(f"- {finding}\n")

def read_notes() -> str:
    try:
        with open(SCRATCHPAD, encoding="utf-8") as f:
            return f.read()
    except FileNotFoundError:
        return "(empty so far)"

def explore_phase(question: str, prior_summary: str) -> str:
    """Each phase starts from the previous phase's summary, not the accumulated dialogue."""
    resp = client.messages.create(
        model=MODEL, max_tokens=1200,
        system="You are exploring a codebase. Answer CONCRETELY: class, file and function names. "
               "Phrases like 'systems like this usually' count as a non-answer.",
        messages=[{"role": "user", "content":
            f"Found earlier:\n{prior_summary}\n\nScratchpad notes:\n{read_notes()}\n\n"
            f"Phase question: {question}\n\n"
            "End your answer with a line 'KEY: ...' — one sentence to carry into the next phase."}])
    text = "".join(b.text for b in resp.content if b.type == "text")
    for line in text.splitlines():
        if line.startswith("KEY:"):
            note(line.removeprefix("KEY:").strip())
    return text

# ---------- 5.4: a state manifest for crash recovery ----------
def export_state(agent: str, state: dict, path: str = "agent-state.json"):
    manifest = json.load(open(path)) if os.path.exists(path) else {}
    manifest[agent] = state
    json.dump(manifest, open(path, "w", encoding="utf-8"), indent=2)

def load_manifest(path: str = "agent-state.json") -> dict:
    return json.load(open(path, encoding="utf-8")) if os.path.exists(path) else {}

if __name__ == "__main__":
    facts = CaseFacts("C-88214")
    facts.add_issue(order="88214", type="refund", amount=4900, due="2026-08-19", status="approved")
    facts.add_issue(order="88301", type="disputed charge", amount=1200, status="investigating")
    facts.add_promise("refund within 5 business days (stated 2026-08-14)")

    prompt = build_prompt(facts, "The customer raised three orders; two questions are resolved.",
                          "So when does the money arrive?")
    print(prompt)

    raw = {"order_id": "88214", "status": "delivered", "amount": 4900, "delivered_at": "2026-08-14",
           "returnable": True, "warehouse_id": "W-12", "package_width": 34, "package_height": 12,
           "courier_route": "R-882", "barcode": "4600000000001"}
    print("\nbefore trimming:", len(raw), "fields → after:", len(trim_tool_output("lookup_order", raw)))
```

**Assignment.**

1. Run a thirty-turn conversation, summarising the history every ten turns — first with the case facts block, then without. On turn thirty-one ask "what amount did you promise and by when". Compare the answers.
2. Feed the model an aggregated report of ten sections and ask about a fact from the sixth. Then move a key findings summary to the beginning and add explicit section headers. Compare whether the fact is found.
3. Disable the `lookup_order` trimming and run a dialogue with five order lookups. See how many tokens went on package dimensions.
4. Explore this repository in four phases: first passing the whole history, then only a summary plus the scratchpad. Compare when the agent starts answering "systems like this usually".

## 🎯 On the exam

- **Objective 5.1**: progressive summarization risks (numbers, percentages, dates, customer expectations), the "lost in the middle" effect, tool output bloat, passing complete history in subsequent requests, the case facts block, output trimming, summaries at the beginning with section headers, metadata from subagents, structured data instead of verbosity under a limited budget.
- **Objective 5.4**: context degradation and "typical patterns" answers, scratchpad files, subagent delegation, summarising between phases, state manifests for recovery, `/compact`.
- Scenarios: **Customer Support Resolution Agent** (long conversations), **Developer Productivity with Claude** and **Multi-Agent Research System** (exploration, synthesis).
- 5.1 trap: "summarise the history more aggressively so more fits". Summarisation is precisely what eats the amounts and dates — the answer is moving them out of the summarised part.
- Second 5.1 trap: "put the important part at the end, the model remembers the last part best". The guide describes the beginning **and** the end, and the recommendation is specific: key findings summary at the start, details under headers.
- 5.4 trap: "start a new session when answers drift". Sometimes right (see C3), but this objective expects scratchpads, delegation and phase summaries — mechanisms that survive a context boundary.
- On crash recovery, remember the phrasing: agents export state, and the coordinator loads a manifest on resume.

---

## 📌 Remember

- Summarisation eats the most expensive things first: amounts, dates, percentages and promises to the customer.
- Transactional facts move into a case facts block included in every prompt, outside the summarised history.
- Models are reliable at the edges of a long input. The key summary goes at the start; details go under explicit section headers.
- Tool output is trimmed to the relevant fields before it settles into the context.
- In a long session specifics degrade into "typical patterns". Against that: a scratchpad file, subagent delegation, phase summaries and `/compact`.
- For crash recovery, agents export state into a manifest the coordinator loads on resume.
