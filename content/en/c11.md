# Module C11. Slash commands and skills

> **Level:** Practitioner · **Time:** ~45 minutes · **Format:** situation → theory → practice → quiz
>
> **CCAR-F objective:** 3.2 — Create and configure custom slash commands and skills

---

## 🏢 The situation

The conventions are sorted (C10) and the team starts automating the repetitive parts. Four requests arrive in a week, and each runs into the same choice: a command, a skill, or a rule in `CLAUDE.md`.

**Kostya's request.** "Every release I type the same thing at the agent: collect the changes since the last tag, group them by type, format them as a changelog. I want that as one command — and I want everyone to have it."

**Artem's request.** "I built myself a codebase-analysis skill. It works, but afterwards the session has two hundred lines of directory tree in it and the agent drowns in them. I end up restarting the session every time."

**Dasha's request.** "We have a data migration skill. It once deleted more than it should have in the sandbox. I want it to be physically unable to execute anything — writing files only."

**And your own.** You took the shared review skill and tuned it for yourself — and now it breaks for colleagues, because you changed it directly in the repository.

## 🎯 Your task

1. Separate the three mechanisms: slash command, skill, and `CLAUDE.md`.
2. Work through skill frontmatter: `context: fork`, `allowed-tools`, `argument-hint`.
3. Find the right home for personal variants so the team is not broken.

**Slash commands** live in two scopes:
- `.claude/commands/` — project-scoped, shared via version control. The answer to Kostya.
- `~/.claude/commands/` — personal, invisible to colleagues.

The same logic as `CLAUDE.md` in module C10: in the repository means shared, in the home directory means yours.

**Skills** live in `.claude/skills/` and are described by a `SKILL.md` with frontmatter. The frontmatter is what answers the remaining three requests.

### Skill frontmatter

```markdown
---
description: Analyses the codebase structure and returns a compact module map
context: fork
allowed-tools: [Read, Grep, Glob]
argument-hint: the directory to analyse, e.g. packages/api
---

# Codebase analysis

Find the entry points with a content search, follow the imports…
```

**`context: fork`** — the skill runs in an isolated sub-agent context, and its output **does not pollute the main conversation**. That is Artem's answer: codebase analysis produces two hundred lines of tree, of which only the summary belongs in the main session. The guide names two typical fork cases:

- **verbose output** — codebase analysis, log inspection, inventories;
- **exploratory context** — brainstorming alternatives that ultimately are not used.

**`allowed-tools`** — restricting tool access for the duration of the skill. Dasha's answer: the migration skill gets file operations only and is physically unable to execute anything. The same scoping principle as module C8, applied at skill level.

**`argument-hint`** — a prompt telling the developer which parameters are needed when they invoke the skill without arguments. A small thing, but the exam tests it: the hint appears at invocation time rather than in documentation nobody reads.

### Personal variants of skills

Your own mistake was editing a shared skill for yourself. The right path: **create a personal variant in `~/.claude/skills/` under a different name**. The different name matters — otherwise nobody can tell which of the two ran, and you are back to the same confusion.

```
.claude/skills/code-review/SKILL.md      ← shared, team-wide, untouched
~/.claude/skills/code-review-strict/     ← personal variant, different name
```

## 💻 Practice

The practice runs in Claude Code on this repository.

**Exercise 1. A project command.** Create `.claude/commands/changelog.md`:

```markdown
---
description: Builds a changelog from the commits since the last tag
argument-hint: the tag to start from (defaults to the latest)
---

Collect the commits since the given tag (or the latest tag if none is given).
Group them by type: features, fixes, infrastructure, content.
For each group, a bulleted list with one line per change,
phrased from the user's point of view rather than the code's.
Skip commits marked [skip railway] and the publish-state bookkeeping commits.
```

Run `/changelog` and see how it does. Then run it with no argument and check whether the hint appeared.

**Exercise 2. Forking the context.** Create two skills with the same task and different frontmatter:

```
.claude/skills/repo-map-inline/SKILL.md   ← without context: fork
.claude/skills/repo-map-forked/SKILL.md   ← with context: fork
```

The body of both:

```markdown
---
description: Builds a map of the repository modules
context: fork          # only in the second file
allowed-tools: [Read, Grep, Glob]
---

Map the repository: entry points, key modules, how they connect.
Return a compact summary of no more than 15 lines.
```

Run each, then ask a follow-up question about the code and compare how much context is left. That difference is the point of `context: fork`.

**Exercise 3. Restricting tools.** Add `allowed-tools: [Read, Write]` to one of the skills and ask it to "run the tests and fix the failures". Confirm execution is unavailable to it: the restriction holds for the duration of the skill regardless of what its text says.

**Exercise 4. A personal variant.** Copy `repo-map-forked` to `~/.claude/skills/repo-map-mine/` and change the output format to suit you. Confirm both are available and distinguishable by name. Then ask yourself what would happen if you had kept the same name.

## 🎯 On the exam

- **Objective 3.2** is covered: project and user commands, `SKILL.md` and its frontmatter (`context: fork`, `allowed-tools`, `argument-hint`), personal variants under a different name, choosing between a skill and `CLAUDE.md`.
- Scenarios: **Code Generation with Claude Code** and **Developer Productivity with Claude**.
- Verbose-output trap: options like "ask the skill to be shorter" or "clear the context after invoking it". The expected answer is `context: fork` — isolation at the configuration level.
- Safety trap: "add a prohibition on running commands to the skill text". A prohibition in text is a request; `allowed-tools` is a guarantee. The same logic as objectives 1.4 and 1.5.
- Mechanism-choice trap: if the question says "a standard that must always apply", that is `CLAUDE.md`, not a skill. If it says "a process launched for a specific task", that is a skill or a command.
- On personal variants: editing a shared skill in the repository breaks colleagues; the answer is a variant in `~/.claude/skills/` **under a different name**.

---

## 📌 Remember

- `.claude/commands/` holds team-wide commands shared through the repository; `~/.claude/commands/` holds personal ones.
- A skill is described by `SKILL.md` with frontmatter; the frontmatter is what turns text into a configurable tool.
- `context: fork` isolates execution in a sub-agent: verbose or exploratory output never reaches the main conversation.
- `allowed-tools` restricts tool access for the duration of the skill — a guarantee, not a request.
- `argument-hint` prompts for parameters when the skill is invoked without them.
- A personal variant of a shared skill goes in `~/.claude/skills/` and **under a different name**.
- Always-on universal standards belong in `CLAUDE.md`; on-demand task workflows belong in skills and commands.
