## 🏢 The situation

A new product: a system that extracts data from supplier documents. Invoices, delivery notes, specifications — twenty different formats from different counterparties, feeding into the ERP.

The first version asked the model to "return JSON" and parsed the answer. Here is a week of statistics:

- **8%** of responses do not parse: a stray comma, a "Here is the extracted data:" preamble, a ```-fence.
- **12%** parse but land in the wrong fields: the total ends up in `tax`, the delivery date in `invoice_date`.
- **6%** contain invented values: the supplier's invoice has no tax id, yet the JSON has one — plausible and non-existent.
- The document type is unknown upfront, and invoices and delivery notes need different schemas. Right now the team guesses from the file name.

Dasha, who runs the project: "We made the parser more robust and errors dropped from 8% to 5%. It will not go lower."

Nor will it: the parser is not the problem.

## 🎯 Your task

1. Guarantee schema compliance through tool use — and understand which errors that eliminates and which it does not.
2. Choose the right `tool_choice` mode when the document type is unknown.
3. Design the schema so the model does not invent values to satisfy required fields.

---

## 📚 Theory

### Tool use as the structured output mechanism

The objective's claim: **tool use with JSON schemas is the most reliable approach for guaranteed schema-compliant structured output, eliminating JSON syntax errors**.

The idea is simple: you declare a tool whose `input_schema` *is* the schema of your data. The model "calls" it, and what it passes as parameters is guaranteed valid against the schema. No text parsing at all.

Map Dasha's percentages onto that split: tool use removes the 8% of syntax errors entirely. The 12% of wrong-field values and the 6% of invented values it does not touch: those are semantics.

### tool_choice for the job

You saw the three modes in module C8; here they apply to extraction:

| Mode | Behaviour | When |
| --- | --- | --- |
| `"auto"` | the model may return text instead of a call | unsuitable for extraction |
| `"any"` | must call a tool but chooses which | **the document type is unknown**, several schemas exist |
| `{"type": "tool", "name": "..."}` | calls this specific one | the type is known, or a fixed first step is required |

The answer to Dasha's fourth problem is `"any"`: declare one tool per document type (`extract_invoice`, `extract_delivery_note`, `extract_spec`), and the model picks the right one while still being **required** to return structure. Guessing from the file name goes away.

Forced selection of a named tool remains for the "metadata first, enrichment second" case — the same technique as C8.

### Schema design: three techniques

**1. Optional (nullable) fields where the data may be absent.** This is the direct answer to the invented tax id. If a field is required and the document lacks it, the model has to put something there — and what it puts is plausible. The guide states the skill as: **design schema fields as optional when source documents may not contain the information, preventing the model from fabricating values to satisfy required fields**.

**2. An `"unclear"` enum value for ambiguous cases.** The same logic at the enumeration level: if the list has no "cannot tell" option, the model picks the nearest one — and you never learn that it hesitated.

**3. The `"other"` + detail string pattern** for extensible categories. A classifier with a closed list will eventually meet something the list does not cover. `"other"` plus `other_detail` preserves both correctness and information — and gives you the material to extend the list.

And a fourth point, not about the schema itself: **format normalization rules go in the prompt alongside the strict schema**. The schema says `date` is a string; the prompt says dates are normalised to `YYYY-MM-DD` regardless of how they appear in the document.

## 💻 Practice

Extraction with a guaranteed schema, `tool_choice: any` for an unknown type, and a schema designed against fabrication.

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

MONEY = {"type": "number", "description": "Amount, a dot as the decimal separator"}

EXTRACTORS = [
    {
        "name": "extract_invoice",
        "description": "Extract data from an INVOICE. Signals: a total due, remittance details, "
                       "an invoice number and date.",
        "input_schema": {"type": "object", "properties": {
            "invoice_number": {"type": "string"},
            "invoice_date": {"type": "string", "description": "YYYY-MM-DD"},
            "supplier_name": {"type": "string"},
            # optional: small suppliers may omit the tax id entirely
            "supplier_tax_id": {"type": ["string", "null"],
                                "description": "Supplier tax id. null when the document does not contain it. "
                                               "Never derive it from the name and never guess."},
            "line_items": {"type": "array", "items": {"type": "object", "properties": {
                "description": {"type": "string"},
                "quantity": {"type": "number"},
                "unit_price": MONEY,
                "amount": MONEY,
            }, "required": ["description", "amount"]}},
            "stated_total": {**MONEY, "description": "The total AS WRITTEN in the document"},
            "currency": {"type": "string", "enum": ["USD", "EUR", "GBP", "other"]},
            "currency_other": {"type": ["string", "null"],
                               "description": "Fill only when currency = other"},
            "payment_terms": {"type": "string", "enum": ["prepaid", "on_delivery", "net_30", "unclear"],
                              "description": "unclear — when the document states no terms or they are ambiguous"},
        }, "required": ["invoice_number", "supplier_name", "stated_total", "currency", "payment_terms"]},
    },
    {
        "name": "extract_delivery_note",
        "description": "Extract data from a DELIVERY NOTE or acceptance certificate. Signals: a list of "
                       "shipped items, signatures of both parties, no payment demand.",
        "input_schema": {"type": "object", "properties": {
            "note_number": {"type": "string"},
            "delivery_date": {"type": "string", "description": "YYYY-MM-DD"},
            "supplier_name": {"type": "string"},
            "items": {"type": "array", "items": {"type": "object", "properties": {
                "description": {"type": "string"}, "quantity": {"type": "number"},
            }, "required": ["description", "quantity"]}},
            "accepted_by": {"type": ["string", "null"],
                            "description": "Name of the person accepting. null when the signature is illegible."},
        }, "required": ["note_number", "supplier_name", "items"]},
    },
]

NORMALIZATION = """
Normalization rules (apply regardless of how the document looks):
— normalise dates to YYYY-MM-DD; "14.08.2026", "14 August 2026" and "2026/08/14" → "2026-08-14";
— return amounts as numbers with no thousands separators: "1,234.56" → 1234.56;
— when a value is absent from the document and the field allows null — return null;
   do NOT derive it from other fields and do NOT substitute something plausible;
— when a category matches no enum value, choose "other"/"unclear"
   and fill the corresponding detail field.
"""

def extract(document: str) -> tuple[str, dict]:
    """tool_choice: any — the document type is unknown, but structure must come back."""
    resp = client.messages.create(
        model=MODEL, max_tokens=2000, tools=EXTRACTORS,
        tool_choice={"type": "any"},
        messages=[{"role": "user", "content": NORMALIZATION + f"\n\nDocument:\n{document}"}])
    block = next(b for b in resp.content if b.type == "tool_use")
    return block.name, block.input

DOC = """
                          INVOICE No. 4412 of 14 August 2026
Supplier: Buildparts Ltd
Item                         Qty     Price      Amount
Steel profile 40x40          120     185.00     22,200.00
Mounting hardware            400      37.50     15,000.00
                                     Total:     37,200.00
Payment due within 30 days of the invoice date.
"""

if __name__ == "__main__":
    name, data = extract(DOC)
    print(f"tool selected: {name}")
    print(json.dumps(data, indent=2))
    # the document has no tax id — we expect null rather than an invented value
    print("\nsupplier_tax_id:", data.get("supplier_tax_id"))
```

**Assignment.**

1. Make `supplier_tax_id` a required string (drop `null` from the type and add it to `required`) and run the same document five times. Count how often an invented tax id appears. That is exactly Dasha's 6%.
2. Change `tool_choice` to `"auto"` and feed a document that is hard to classify. See how many responses come back as text instead of a call.
3. Remove `"unclear"` from `payment_terms` and feed an invoice with no stated terms. The model will pick something — check what, and consider how you would ever notice in production.
4. Remove the `NORMALIZATION` block and feed three documents with different date formats. The schema still holds and the data is still inconsistent: that is the boundary between shape and meaning.

## 🎯 On the exam

- **Objective 4.3** is covered: tool use with schemas as the most reliable approach, the three `tool_choice` modes, syntax errors eliminated while semantic ones remain, schema design (required vs optional, `"unclear"`, `"other"` + detail), normalization rules in the prompt alongside the schema.
- Scenario: **Structured Data Extraction** — built entirely around this objective.
- The key trap: "a strict schema guarantees correct data". The guide stresses separately that schemas eliminate syntax errors but **do not prevent semantic ones** — totals that do not sum, values in the wrong fields.
- `tool_choice` trap: with an unknown document type and several schemas the answer is `"any"`. `"auto"` still lets the model return text, and forced selection requires knowing the type upfront.
- Fabrication trap: options like "add a prohibition on inventing to the prompt" or "lower the temperature". The expected answer is making the field optional (nullable) so the model is not forced to fill it.
- For enums remember both patterns: `"unclear"` for ambiguity and `"other"` + a detail string for extensible categories.

---

## 📌 Remember

- Structured output comes from tool use with a JSON schema in `input_schema`, not from parsing text. Syntax errors disappear as a class.
- A schema guarantees shape, not meaning: totals may not sum, values may sit in the wrong fields.
- `"auto"` permits text instead of a call; `"any"` guarantees a call when the document type is unknown; forced selection pins a specific tool.
- A required field the source lacks is a direct invitation to fabricate. Make such fields nullable.
- Add `"unclear"` to enums for ambiguous cases and `"other"` with a detail string for extensible categories.
- Format normalization rules live in the prompt alongside the schema: the schema handles types, the prompt handles canonical form.
