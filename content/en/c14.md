# Module C14. Explicit criteria and few-shot

> **Level:** Architect · **Time:** ~50 minutes · **Format:** situation → theory → practice → quiz
>
> **CCAR-F objectives:** 4.1 — Design prompts with explicit criteria to improve precision and reduce false positives · 4.2 — Apply few-shot prompting to improve output consistency and quality

---

## 🏢 The situation

The CI review is wired up correctly (C13): `-p`, an output schema, prior findings in context. And the team still ignores it.

Kostya brings the month's numbers: of 214 findings, developers accepted 61. Broken down by category:

| Category | Findings | Accepted |
| --- | --- | --- |
| Security | 18 | 16 |
| Logic errors | 44 | 33 |
| Stale comments | 87 | 4 |
| Naming style | 65 | 8 |

Two categories drag everything else down. Worse, developers now skim the comments — and miss the very sixteen security findings the whole thing was built for.

You look at the prompt. On comments it says: "check that comments are accurate". On style: "report naming violations". And at the end Kostya added: "be conservative, only report findings you are confident about".

There is a second problem alongside. The finding format drifts: sometimes "file:line — problem", sometimes a paragraph of reasoning, sometimes a five-point list with a suggestion at the end. The posting script survives it thanks to the schema; a human does not.

## 🎯 Your task

1. Replace vague instructions with categorical criteria.
2. Understand why "be conservative" does not work — and what to do with a category that is destroying trust.
3. Achieve output consistency with few-shot examples rather than a longer description.

The first claim of objective 4.1: **explicit criteria beat vague instructions**. The guide's canonical example is precisely Kostya's problem:

```
❌ "check that comments are accurate"
✅ "flag a comment only when the behaviour it claims
   contradicts the actual behaviour of the code"
```

The second claim, less obvious: **general instructions such as "be conservative" or "only report high-confidence findings" fail to improve precision** compared with specific categorical criteria. The model has no calibrated confidence threshold that a word can turn down. What works is not a confidence filter but a definition of **what counts as a problem**.

Hence the skill: write criteria that enumerate what to report (bugs, security) and what to skip (minor style, local project patterns), instead of trying to filter by confidence.

The third claim is about trust. **A high false positive rate in one category undermines confidence in the accurate categories.** That is why the guide names a separate skill: **temporarily disable the problem category** to restore trust while you improve its prompt. That is not defeat, it is managing people's attention.

And a fourth technique: **explicit severity criteria with concrete code examples for each level**. "Blocker", "major" and "minor" without examples get classified differently every run.

### Few-shot: when descriptions are not enough

Kostya's second problem is the drifting format. Objective 4.2 covers it, and its first claim is categorical: **few-shot examples are the most effective technique for consistently formatted, actionable output when detailed instructions alone produce inconsistent results**.

What the examples demonstrate:

- **the desired output format** — location, issue, severity, suggested fix;
- **handling of ambiguous cases** — and, importantly, **the reasoning** for why one action was chosen over a plausible alternative;
- **the boundary between an acceptable pattern and a genuine issue** — this is what reduces false positives;
- **varied document structures** — inline citations vs bibliographies, a methodology section vs details embedded in the text;
- **correct extraction from documents in varied formats** — against empty or null values in required fields.

Volume: **2–4 targeted examples**. Not twenty: the point is not covering cases but conveying a principle.

The property the exam tests separately: few-shot examples let the model **generalise judgment to novel patterns** rather than matching only pre-specified cases. That is why an example with its reasoning beats one without: it conveys a criterion instead of a record.

```
Example (acceptable pattern, do NOT report):
  code:      except Exception: logger.warning(...); return default
  reasoning: graceful degradation is an accepted pattern for external calls in
             this project, and the exception is logged. This is not a swallowed error.

Example (genuine issue, report):
  code:      except Exception: pass
  reasoning: the exception is neither logged nor handled — the failure becomes
             invisible. Severity major: no data loss, but diagnosis is impossible.
```

Two examples side by side draw the boundary better than a paragraph of description: the model sees not a list of prohibitions but the property that separates them.

## 💻 Practice

A review prompt with explicit criteria and few-shot. Compare it with "check that comments are accurate".

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

CRITERIA = """
Report findings ONLY in these categories:

1. security — user input reaches a query or command without escaping;
   a secret in the code; a missing permission check before operating on another user's data.
2. correctness — the code does not do what it should: a wrong condition, a lost
   branch, an unhandled edge case with a concrete input that triggers it.
3. stale_comment — report ONLY when the behaviour a comment claims contradicts
   the actual behaviour of the code. An incomplete, stylistically dated or merely
   terse comment is not a finding.

Do NOT report: naming, formatting, import order, style preferences,
local project patterns, "this could be more elegant".

Severity:
  blocker — causes data loss, a leak, or a production outage.
            Example: a SQL query built by concatenating user input.
  major   — wrong behaviour on real input, with diagnosis made impossible.
            Example: except Exception: pass in a payment handler.
  minor   — behaviour is correct but the next change is riskier.
            Example: a magic number instead of a constant in a limit check.
"""

FEW_SHOT = """
Worked examples. Note the reasoning: the property matters, not the match.

Example 1 — acceptable pattern, do NOT report:
  code:  try: rate = fx.get(cur)
         except TimeoutError: logger.warning("fx timeout, using cached"); rate = cached(cur)
  output: no finding. The exception is narrow, logged, and has a meaningful fallback —
          this is managed degradation, not a swallowed error.

Example 2 — genuine issue, report:
  code:  try: charge(card, amount)
         except Exception: pass
  output: {"category": "correctness", "severity": "major",
           "message": "Charge failure is swallowed: the exception is neither logged
                       nor re-raised, so the payment silently does not go through",
           "suggestion": "Log with the amount and operation id, then re-raise"}

Example 3 — an ambiguous comment, do NOT report:
  code:  # returns the list of active users
         def active_users(limit=None): ...
  output: no finding. The comment is incomplete (limit is unmentioned) but does not
          contradict the behaviour. The stale_comment criterion requires a contradiction.

Example 4 — a comment contradicting the code, report:
  code:  # 30 second timeout
         client = Client(timeout=5)
  output: {"category": "stale_comment", "severity": "minor",
           "message": "The comment claims a 30 second timeout; the code sets 5",
           "suggestion": "Align the comment with the code, or restore 30"}
"""

SCHEMA_TOOL = [{
    "name": "submit_findings",
    "description": "Submit the review results.",
    "input_schema": {"type": "object", "properties": {
        "findings": {"type": "array", "items": {"type": "object", "properties": {
            "file": {"type": "string"}, "line": {"type": "integer"},
            "category": {"type": "string", "enum": ["security", "correctness", "stale_comment"]},
            "severity": {"type": "string", "enum": ["blocker", "major", "minor"]},
            "message": {"type": "string"}, "suggestion": {"type": "string"},
        }, "required": ["file", "line", "category", "severity", "message"]}},
    }, "required": ["findings"]},
}]

def review(diff: str, *, with_criteria=True, with_few_shot=True) -> dict:
    system = CRITERIA if with_criteria else (
        "Review the code. Check that comments are accurate and report naming violations. "
        "Be conservative, only report findings you are confident about.")
    prompt = (FEW_SHOT + "\n\n" if with_few_shot else "") + f"Diff:\n```\n{diff}\n```"
    resp = client.messages.create(
        model=MODEL, max_tokens=2000, system=system, tools=SCHEMA_TOOL,
        tool_choice={"type": "tool", "name": "submit_findings"},
        messages=[{"role": "user", "content": prompt}])
    return next(b.input for b in resp.content if b.type == "tool_use")

DIFF = """
--- a/billing/charge.py
+++ b/billing/charge.py
@@
+# retries up to 3 times
+def charge_with_retry(card, amount):
+    for _ in range(2):
+        try:
+            return charge(card, amount)
+        except Exception:
+            pass
+    return None
+
+def find_invoice(user_input):
+    return db.query("SELECT * FROM invoices WHERE ref = '" + user_input + "'")
"""

if __name__ == "__main__":
    for label, kw in [("criteria + few-shot", {}),
                      ("criteria only", {"with_few_shot": False}),
                      ("vague", {"with_criteria": False, "with_few_shot": False})]:
        r = review(DIFF, **kw)
        cats = [f"{f['category']}/{f['severity']}" for f in r["findings"]]
        print(f"{label:22} → {len(r['findings'])} findings: {cats}")
```

**Assignment.**

1. Run the three configurations five times each. Compare not just the number of findings but the stability: is the SQL concatenation caught every time, and is the "retries up to 3 times" comment over a two-iteration loop classified the same way each run?
2. Remove the severity block with its examples from `CRITERIA` and watch the classification of the same finding drift between runs.
3. Add a fifth few-shot example — an acceptable pattern from your own project that the agent used to flag incorrectly. Check that the model generalised the property rather than memorising the code: feed it a similar but not identical fragment.

## 🎯 On the exam

- **Objective 4.1**: explicit criteria vs vague instructions, the uselessness of "be conservative", the effect of false positives on trust, temporarily disabling a weak category, severity criteria with code examples.
- **Objective 4.2**: few-shot as the most effective consistency technique, 2–4 targeted examples, showing the reasoning, generalisation to novel patterns, distinguishing acceptable patterns from genuine issues, varied document structures, fixing empty extraction fields.
- Scenarios: **Claude Code for Continuous Integration** (review false positives) and **Structured Data Extraction** (few-shot against hallucination and empty fields).
- The main 4.1 trap: the option "add 'only report high-confidence findings' to the prompt". The guide names this as failing to improve precision compared with categorical criteria.
- Second 4.1 trap: "remove the category permanently" vs "temporarily disable it and fix the prompt". The latter is expected.
- 4.2 trap: "write a more detailed format instruction". If the instructions are already detailed and the output is still inconsistent, the answer is few-shot.
- Another 4.2 trap: "add examples for every possible case". The guide speaks of 2–4 targeted examples and of generalisation, not coverage.

---

## 📌 Remember

- A criterion must be checkable and categorical: "contradicts the actual behaviour", not "is inaccurate".
- "Be conservative" and "only confident findings" do not improve precision. Defining what counts as a problem, and what to skip, does.
- One noisy category devalues the accurate ones. Disable it temporarily and fix the prompt rather than tolerating it.
- Severity levels are defined with code examples, or classification drifts between runs.
- When detailed instructions still produce inconsistent output, the answer is few-shot examples, not more detailed instructions.
- 2–4 examples, always with the reasoning for choosing this over a plausible alternative. That is how the model generalises instead of memorising.
- A pair of examples — acceptable pattern vs genuine issue — is the most direct way to cut false positives.
