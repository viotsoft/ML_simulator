# Module A8. The content factory: planner, writer, editor, fact-checker

> **Level:** Middle AI · **Time:** ~55 minutes · **Format:** situation → theory → practice → quiz

---

## 🏢 The situation

Dasha, the CMO, finally gets her turn:

> "You've handled outbound. Now my half of the factory: I need eight blog posts a month. Right now two copywriters produce four. Fair warning: I've tried 'write an article' before — you get smooth text about nothing that I'd be embarrassed to publish under our name."

You try the direct approach: one call, prompt "write a 1200-word article about ML model monitoring". You get exactly what Dasha described: the right words, zero specifics, and three invented "studies show".

The problem is not the model. The problem is that you asked it to do four different jobs at once: invent the structure, write the prose, edit it and verify the facts. Humans cannot do that either.

## 🎯 Your task

1. Split the article into roles, each with its own job and its own quality criterion.
2. Pass state between roles without losses and without infinite loops.
3. Give the fact-checker the right to reject a text, not merely "share an opinion".

---

## 📚 Theory

### Why splitting roles works

One large task forces the model to average: it holds structure, style, facts and length in mind simultaneously and does all of them adequately. Splitting buys three things:

1. **Focus.** Each step has one criterion that is easy to check.
2. **Different settings.** The planner wants temperature 0.3 and a large context, the writer 0.8, the fact-checker 0 plus RAG access.
3. **A visible point of failure.** A bad article is a bad plan, bad prose or a missed fact. Without the split you do not know what to fix.

The price is latency and money: four calls instead of one. For a weekly article that is irrelevant. For a chat reply it is fatal.

### Passing state: contracts between roles

Roles communicate in structures, not prose. A plan is not "here is roughly the outline" but an object: title, audience, claims, and for each claim whether it needs a fact from the knowledge base.

The rule: **each role's output is validated before it moves on**. If the planner returned two sections instead of five, the writer will never know — it will simply produce a short article, and it will look like the writer's fault.

### Who is allowed to say no

A pipeline needs a role that can stop publication. Ours is the fact-checker: it verifies every factual claim against the knowledge base (from A5) and returns the unsupported ones.

An important detail: **the fact-checker does not rewrite the text**. It issues a verdict. Mixing checking and fixing in one role is a mistake — whoever fixes tends to justify what was written.

## 💻 Practice

```python
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"
MAX_REVISIONS = 2

# --- Contracts between roles ---
PLAN_TOOL = {
    "name": "save_plan",
    "input_schema": {"type": "object", "properties": {
        "title": {"type": "string"},
        "audience": {"type": "string"},
        "sections": {"type": "array", "minItems": 4, "maxItems": 7, "items": {
            "type": "object", "properties": {
                "heading": {"type": "string"},
                "claim": {"type": "string", "description": "The section's main point"},
                "needs_fact": {"type": "boolean", "description": "Needs a fact from the knowledge base"},
            }, "required": ["heading", "claim", "needs_fact"]}},
    }, "required": ["title", "audience", "sections"]},
}

FACTCHECK_TOOL = {
    "name": "report",
    "input_schema": {"type": "object", "properties": {
        "unsupported": {"type": "array", "items": {"type": "object", "properties": {
            "quote": {"type": "string"}, "why": {"type": "string"}}, "required": ["quote", "why"]}},
        "verdict": {"type": "string", "enum": ["publish", "revise", "reject"]},
    }, "required": ["unsupported", "verdict"]},
}


def call(system, user, tool, temperature, max_tokens=2500):
    resp = client.messages.create(
        model=MODEL, max_tokens=max_tokens, temperature=temperature, system=system,
        tools=[tool], tool_choice={"type": "tool", "name": tool["name"]},
        messages=[{"role": "user", "content": user}])
    return next(b for b in resp.content if b.type == "tool_use").input


def plan(topic):
    p = call("You are an editor of a tech blog for ML engineers. Build the plan around the "
             "reader's problem, not around the topic's structure. Always call save_plan.",
             f"Topic: {topic}", PLAN_TOOL, temperature=0.3)
    if len(p["sections"]) < 4:                       # validate before passing on
        raise ValueError("plan too short")
    return p


def write(plan_obj, facts):
    return call("You write from a finished plan. Do not add sections, do not invent numbers. "
                "Take factual claims only from the FACTS block.",
                f"PLAN:\n{json.dumps(plan_obj)}\n\nFACTS:\n{facts}",
                DRAFT_ARTICLE_TOOL, temperature=0.8)


def edit(article):
    return call("You are an editor. Remove filler and clichés, preserve every fact and the "
                "structure. Do not add new claims.",
                article["body"], DRAFT_ARTICLE_TOOL, temperature=0.3)


def factcheck(article, facts):
    """Verdict only, no rewriting: the checker must not justify the text."""
    return call("You are a fact-checker. For each factual claim, check whether it appears in "
                "FACTS. Do not check opinions or reasoning. Always call report.",
                f"FACTS:\n{facts}\n\nARTICLE:\n{article['body']}",
                FACTCHECK_TOOL, temperature=0)


def produce(topic):
    plan_obj = plan(topic)
    queries = [s["claim"] for s in plan_obj["sections"] if s["needs_fact"]]
    facts = "\n\n".join(f"[{i+1}] {c['text']}" for i, (c, _) in
                        enumerate(sum((search(q, k=2) for q in queries), [])))   # RAG from A5

    article = write(plan_obj, facts)
    for attempt in range(MAX_REVISIONS + 1):
        article = edit(article)
        report = factcheck(article, facts)
        if report["verdict"] == "publish":
            return {"status": "ready", "article": article, "attempts": attempt + 1}
        if report["verdict"] == "reject" or attempt == MAX_REVISIONS:
            return {"status": "to_human", "article": article,
                    "problems": report["unsupported"], "attempts": attempt + 1}
        # revision: the writer receives concrete problems, not "make it better"
        article = call("Rewrite only the problematic claims. Leave the rest of the text alone.",
                       f"ARTICLE:\n{article['body']}\n\nPROBLEMS:\n"
                       f"{json.dumps(report['unsupported'])}\n\nFACTS:\n{facts}",
                       DRAFT_ARTICLE_TOOL, temperature=0.5)
    return {"status": "to_human", "article": article, "attempts": MAX_REVISIONS + 1}


result = produce("Monitoring ML models in production: what breaks after deployment")
print(result["status"], "| attempts:", result["attempts"])
for p in result.get("problems", []):
    print(f"  ✗ {p['quote'][:70]} — {p['why']}")
```

What matters here:

1. **The plan schema requires 4–7 sections.** The planner cannot get away with three bullets, and the writer receives a guaranteed structure.
2. **The fact-checker only judges.** A different call fixes things — the author does not get to absolve itself.
3. **Revision receives a concrete problem list**, not "improve it". That is the difference between a converging loop and an endless argument.
4. **Three outcomes, not two:** publish, revise, hand to a human. The third is mandatory — otherwise the system spins until the money runs out.

**Assignment.** Run three topics and look at the distribution: how many passed on the first attempt, how many on the second, how many went to a human. If more than half go to a human, the problem is in the plan or the knowledge base, not in the writer.

---

## 📌 Remember

- One large request forces the model to average. Roles with a single criterion each do better.
- Roles exchange structures, not prose; each output is validated before it moves on.
- A pipeline needs a role with veto power — and it must not fix what it checks.
- Every revision loop is bounded, and it has a third outcome: hand it to a human.
- Revision receives concrete problems, not a wish to "make it better".
- Multi-agent costs money and latency: justified for an article, not for a chat reply.
