# Модуль C13. Claude Code в CI/CD

> **Уровень:** Practitioner · **Время:** ~50 минут · **Формат:** ситуация → теория → практика → квиз
>
> **Цель экзамена CCAR-F:** 3.6 — Integrate Claude Code into CI/CD pipelines

---

## 🏢 Ситуация

Автоматическое ревью, которое Костя ставил в модуле C6, наконец выкатили на все пул-реквесты. Через две недели команда просит его выключить. Разбираетесь по жалобам.

**Жалоба 1.** Джоб иногда висит по сорок минут и падает по таймауту. Смотрите лог: агент задал уточняющий вопрос и ждёт ответа. В CI отвечать некому.

**Жалоба 2.** Результат ревью — свободный текст в логе сборки. Чтобы превратить его в комментарии к строкам PR, Костя написал парсер на регулярках. Тот ломается каждый раз, когда меняется формулировка.

**Жалоба 3.** Автор запушил три коммита подряд. Ревью отработало трижды и трижды написало одни и те же четыре замечания. В PR двенадцать комментариев про одну проблему.

**Жалоба 4.** Генератор тестов предлагает тесты, которые уже написаны, и проверяет геттеры. Полезных — один из восьми.

**Жалоба 5, от Даши.** «Ваш агент сам сгенерировал код в задаче, а потом сам же его отревьюил и написал „выглядит отлично“.»

Пять жалоб — пять пунктов этой цели.

## 🎯 Ваша задача

1. Запустить Claude Code так, чтобы он не ждал ввода.
2. Получать структурированный вывод вместо текста, который надо парсить.
3. Убрать дубли комментариев, поднять качество тестов и развести генерацию с ревью.

**`-p` (или `--print`)** — неинтерактивный режим. Claude Code выполняет задачу и печатает результат, не запрашивая ввода. Без него в CI агент рано или поздно задаст вопрос и повиснет до таймаута — жалоба 1.

**`--output-format json`** вместе с **`--json-schema`** — машиночитаемый структурированный вывод. Вместо парсинга прозы регулярками вы получаете JSON заданной формы, который сразу превращается в комментарии к строкам PR — жалоба 2.

```bash
claude -p "Ревью изменений в этом PR" \
  --output-format json \
  --json-schema ./ci/review-schema.json
```

### Что положить в контекст

**`CLAUDE.md` — механизм передачи контекста проекта** запуску из CI. Стандарты тестирования, соглашения о фикстурах, критерии ревью. Джоб не задаёт вопросов и ничего не знает о вашем проекте, кроме того, что вы положили в файлы. Это прямой ответ на жалобу 4: гайд требует **документировать в `CLAUDE.md` стандарты тестирования, критерии ценного теста и доступные фикстуры**, чтобы генерация тестов не выдавала мусор.

**Прошлые находки ревью.** При повторном запуске после новых коммитов в контекст кладут результаты предыдущего ревью и явно инструктируют: сообщать только **новые или до сих пор не исправленные** проблемы. Это жалоба 3 — двенадцать комментариев про одну проблему.

**Существующие тесты.** Чтобы генератор не предлагал сценарии, уже покрытые набором. Вторая половина жалобы 4.

### Изоляция сессий

Жалоба Даши — про отдельный факт из гайда, который стоит запомнить: **та же сессия, что сгенерировала код, менее эффективна при ревью собственных изменений**, чем независимый экземпляр. У неё в контексте лежат её же решения и обоснования, и она склонна их подтверждать.

Практический вывод: в конвейере генерация и ревью — **разные запуски с чистым контекстом**. Не «попроси того же агента проверить себя», а отдельный процесс, который видит только дифф и стандарты проекта.

## 💻 Практика

Схема вывода — `ci/review-schema.json`:

```json
{
  "type": "object",
  "properties": {
    "findings": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "file":     { "type": "string" },
          "line":     { "type": "integer" },
          "severity": { "type": "string", "enum": ["blocker", "major", "minor"] },
          "category": { "type": "string" },
          "message":  { "type": "string" },
          "suggestion": { "type": "string" }
        },
        "required": ["file", "line", "severity", "message"]
      }
    },
    "summary": { "type": "string" }
  },
  "required": ["findings", "summary"]
}
```

Джоб ревью — `.github/workflows/review.yml`:

```yaml
name: AI review
on: pull_request

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }

      - name: Достать прошлые находки
        id: prior
        run: |
          gh pr view "$PR" --json comments \
            --jq '[.comments[] | select(.author.login=="github-actions") | .body]' \
            > prior-findings.json
        env:
          PR: ${{ github.event.pull_request.number }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

      - name: Ревью
        run: |
          git diff origin/${{ github.base_ref }}...HEAD > pr.diff
          claude -p "$(cat <<'PROMPT'
          Отревьюй изменения из pr.diff по стандартам проекта из CLAUDE.md.

          В prior-findings.json — замечания, уже оставленные в этом PR ранее.
          Сообщай ТОЛЬКО новые или до сих пор не исправленные проблемы.
          Повторно найденное и уже исправленное не упоминай.

          Ложные срабатывания дороже пропусков: если не уверен, что это дефект,
          не сообщай о нём. Каждое замечание — с файлом, строкой и конкретным предложением.
          PROMPT
          )" \
            --output-format json \
            --json-schema ./ci/review-schema.json \
            > review.json

      - name: Опубликовать комментарии
        run: node ci/post-comments.js review.json
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

Раздел `CLAUDE.md`, который поднимает качество генерации тестов:

```markdown
## Стандарты тестирования

Ценный тест проверяет поведение на границе или в ошибочном сценарии.
Тесты на геттеры, конструкторы и тривиальные делегирования не пишем.

Доступные фикстуры: `tests/fixtures/users.js` (пользователь с прогрессом и без),
`tests/fixtures/db.js` (временный DATA_DIR с автоочисткой).
Новые фикстуры заводим, только если существующие не подходят.

Именование: `describe('countPassed')` → `it('не считает модули чужого трека')`.
Мокаем только внешние системы; файловую систему — через временный каталог.
```

**Задание.**

1. Запустите `claude -p "перечисли изменённые файлы"` без флага `-p` и с ним в скрипте без терминала. Разница в том, дождётесь ли вы завершения.
2. Прогоните ревью с `--json-schema` и без. Попробуйте написать парсер для второго варианта, затем измените формулировку промпта и посмотрите, переживёт ли парсер это.
3. Уберите из промпта блок про прошлые находки и запустите ревью дважды подряд на одном диффе. Посчитайте дубли.
4. Попросите одну сессию сгенерировать функцию, а затем в ней же — отревьюить её. Затем отревьюйте тот же код в чистой сессии. Сравните списки замечаний.

## 🎯 На экзамене

- **Цель 3.6** закрыта: флаг `-p`/`--print`, `--output-format json` с `--json-schema`, `CLAUDE.md` как канал контекста проекта, прошлые находки против дублей, существующие тесты против копий, изоляция сессий генерации и ревью.
- Сценарий: **Claude Code for Continuous Integration** — целиком построен вокруг этой цели, плюс домен 4 в части качества промптов.
- Ловушка про зависание: варианты «увеличить таймаут джоба» или «добавить в промпт просьбу не задавать вопросов». Ожидаемый ответ — флаг `-p`.
- Ловушка про парсинг: «написать более устойчивые регулярные выражения». Ответ — структурированный вывод по схеме.
- Ловушка про дубли: «удалять старые комментарии перед новым запуском» звучит разумно, но гайд требует другого — класть прошлые находки в контекст и просить сообщать только новое или неисправленное.
- Ловушка про самопроверку: «попросить ту же сессию перепроверить свой код» — прямо названа менее эффективной, чем независимый экземпляр.
- Про качество тестов помните: причина мусорных тестов — не модель, а отсутствие описанных стандартов и фикстур в `CLAUDE.md`.

## 📌 Запомнить

- `-p` (`--print`) — неинтерактивный режим для конвейеров; без него джоб рискует ждать ввода до таймаута.
- `--output-format json` вместе с `--json-schema` даёт машиночитаемые находки, готовые к публикации комментариями к строкам.
- `CLAUDE.md` — способ передать джобу контекст проекта: стандарты тестов, фикстуры, критерии ревью.
- Прошлые находки кладут в контекст и просят сообщать только новое или неисправленное — иначе PR обрастает дублями.
- Существующие тесты в контексте не дают генератору предлагать уже покрытые сценарии.
- Сессия, написавшая код, хуже ревьюит собственные изменения. Ревью запускают отдельным экземпляром с чистым контекстом.
