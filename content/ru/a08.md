> **Уровень:** Middle AI · **Время:** ~55 минут · **Формат:** ситуация → теория → практика → квиз

---

## 🏢 Ситуация

Даша, CMO, дождалась своей очереди:

> «Исходящие вы закрыли. Теперь моя часть фабрики: мне нужно восемь статей в блог в месяц. Сейчас два копирайтера пишут четыре. Только предупреждаю: у меня был неудачный опыт с "напиши статью" — на выходе получается гладкий текст ни о чём, который стыдно публиковать под нашим именем.»

Вы пробуете в лоб: один вызов, промпт «напиши статью на 1200 слов про мониторинг ML-моделей». Получаете ровно то, что описала Даша: правильные слова, нулевая конкретика, три выдуманных «исследования показывают».

Проблема не в модели. Проблема в том, что вы попросили её сделать четыре разные работы одновременно: придумать структуру, написать текст, отредактировать и проверить факты. Человек так тоже не умеет.

## 🎯 Ваша задача

1. Разложить статью на роли, каждая со своей задачей и своим критерием качества.
2. Организовать передачу состояния между ролями без потерь и без зацикливания.
3. Сделать так, чтобы фактчекер имел право забраковать текст, а не просто «высказать мнение».

## 📚 Теория

### Почему разделение ролей работает

Одна большая задача заставляет модель усреднять: она одновременно держит в голове структуру, стиль, факты и длину — и делает всё посредственно. Разделение даёт три выигрыша:

1. **Фокус.** У каждого шага один критерий, который легко проверить.
2. **Разные настройки.** Планировщику нужна температура 0.3 и большой контекст, писателю — 0.8, фактчекеру — 0 и доступ к RAG.
3. **Точка отказа видна.** Плохая статья — это плохой план, плохой текст или пропущенный факт. Без разделения вы не знаете, что чинить.

Цена — задержка и деньги: четыре вызова вместо одного. Для статьи, которую пишут раз в неделю, это неважно. Для ответа в чате — критично.

### Передача состояния: контракты между ролями

Роли общаются не текстом, а структурами. План — это не «вот примерный текст плана», а объект: заголовок, аудитория, тезисы, для каждого тезиса — нужен ли факт из базы знаний.

Правило: **выход каждой роли валидируется до передачи дальше**. Если планировщик выдал два тезиса вместо пяти, писатель об этом не узнает — он просто напишет короткую статью, и виноват будет он.

### Кто может сказать «нет»

В конвейере должна быть роль с правом остановить публикацию. У нас это фактчекер: он проверяет каждое фактическое утверждение по базе знаний (из A5) и возвращает список неподтверждённых.

Важная деталь: **фактчекер не переписывает текст**. Он выносит вердикт. Смешивать проверку и исправление в одной роли нельзя — тот, кто исправляет, склонен оправдывать написанное.

## 💻 Практика

```python
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"
MAX_REVISIONS = 2

# --- Контракты между ролями ---
PLAN_TOOL = {
    "name": "save_plan",
    "input_schema": {"type": "object", "properties": {
        "title": {"type": "string"},
        "audience": {"type": "string"},
        "sections": {"type": "array", "minItems": 4, "maxItems": 7, "items": {
            "type": "object", "properties": {
                "heading": {"type": "string"},
                "claim": {"type": "string", "description": "Главный тезис раздела"},
                "needs_fact": {"type": "boolean", "description": "Нужен факт из базы знаний"},
            }, "required": ["heading", "claim", "needs_fact"]}},
    }, "required": ["title", "audience", "sections"]},
}

FACTCHECK_TOOL = {
    "name": "report",
    "input_schema": {"type": "object", "properties": {
        "unsupported": {"type": "array", "items": {"type": "object", "properties": {
            "quote": {"type": "string"}, "why": {"type": "string"}}, "required": ["quote", "why"]}},
        "verdict": {"type": "string", "enum": ["publish", "revise", "reject"]},
    }, "required": ["unsupported", "verdict"]},
}


def call(system, user, tool, temperature, max_tokens=2500):
    resp = client.messages.create(
        model=MODEL, max_tokens=max_tokens, temperature=temperature, system=system,
        tools=[tool], tool_choice={"type": "tool", "name": tool["name"]},
        messages=[{"role": "user", "content": user}])
    return next(b for b in resp.content if b.type == "tool_use").input


def plan(topic):
    p = call("Ты редактор техблога для ML-инженеров. Строй план от проблемы читателя, "
             "а не от структуры темы. Всегда вызывай save_plan.",
             f"Тема: {topic}", PLAN_TOOL, temperature=0.3)
    if len(p["sections"]) < 4:                       # валидация до передачи дальше
        raise ValueError("план слишком короткий")
    return p


def write(plan_obj, facts):
    return call("Ты пишешь по готовому плану. Не добавляй разделов, не выдумывай цифры. "
                "Фактические утверждения бери только из блока ФАКТЫ.",
                f"ПЛАН:\n{json.dumps(plan_obj, ensure_ascii=False)}\n\nФАКТЫ:\n{facts}",
                DRAFT_ARTICLE_TOOL, temperature=0.8)


def edit(article):
    return call("Ты редактор. Убери воду и штампы, сохрани все факты и структуру. "
                "Не добавляй новых утверждений.",
                article["body"], DRAFT_ARTICLE_TOOL, temperature=0.3)


def factcheck(article, facts):
    """Только вердикт, без переписывания: проверяющий не должен оправдывать текст."""
    return call("Ты фактчекер. Для каждого фактического утверждения проверь, есть ли оно в ФАКТАХ. "
                "Мнения и рассуждения не проверяй. Всегда вызывай report.",
                f"ФАКТЫ:\n{facts}\n\nСТАТЬЯ:\n{article['body']}",
                FACTCHECK_TOOL, temperature=0)


def produce(topic):
    plan_obj = plan(topic)
    queries = [s["claim"] for s in plan_obj["sections"] if s["needs_fact"]]
    facts = "\n\n".join(f"[{i+1}] {c['text']}" for i, (c, _) in
                        enumerate(sum((search(q, k=2) for q in queries), [])))   # RAG из A5

    article = write(plan_obj, facts)
    for attempt in range(MAX_REVISIONS + 1):
        article = edit(article)
        report = factcheck(article, facts)
        if report["verdict"] == "publish":
            return {"status": "ready", "article": article, "attempts": attempt + 1}
        if report["verdict"] == "reject" or attempt == MAX_REVISIONS:
            return {"status": "to_human", "article": article,
                    "problems": report["unsupported"], "attempts": attempt + 1}
        # доработка: писателю передают конкретные проблемы, а не «сделай лучше»
        article = call("Перепиши только проблемные утверждения. Остальной текст не трогай.",
                       f"СТАТЬЯ:\n{article['body']}\n\nПРОБЛЕМЫ:\n"
                       f"{json.dumps(report['unsupported'], ensure_ascii=False)}\n\nФАКТЫ:\n{facts}",
                       DRAFT_ARTICLE_TOOL, temperature=0.5)
    return {"status": "to_human", "article": article, "attempts": MAX_REVISIONS + 1}


result = produce("Мониторинг ML-моделей в проде: что ломается после деплоя")
print(result["status"], "| попыток:", result["attempts"])
for p in result.get("problems", []):
    print(f"  ✗ {p['quote'][:70]} — {p['why']}")
```

Что здесь важно:

1. **Схема плана требует 4–7 разделов.** Планировщик не может отделаться тремя пунктами, а писатель получает гарантированную структуру.
2. **Фактчекер только выносит вердикт.** Исправляет другой вызов — тот, кто писал, не оправдывает сам себя.
3. **Доработка получает конкретный список проблем**, а не «улучши». Это разница между сходящимся циклом и бесконечным спором.
4. **Три исхода, а не два:** опубликовать, переписать, отдать человеку. Третий исход обязателен — иначе система будет крутиться, пока не кончатся деньги.

**Задание.** Прогоните три темы и посмотрите на распределение: сколько статей прошли с первой попытки, сколько со второй, сколько ушло человеку. Если человеку уходит больше половины — проблема в плане или в базе знаний, а не в писателе.

## 📌 Запомнить

- Одна большая просьба заставляет модель усреднять. Роли с одним критерием каждая работают лучше.
- Роли передают структуры, а не текст; выход каждой валидируется до передачи дальше.
- В конвейере нужна роль с правом вето — и она не должна сама исправлять то, что проверяет.
- Любой цикл доработки ограничен по числу итераций, и у него есть третий исход: отдать человеку.
- Доработка получает конкретные проблемы, а не пожелание «сделай лучше».
- Мультиагентность стоит денег и задержки: она оправдана для статьи и не оправдана для ответа в чате.
