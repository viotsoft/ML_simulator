# Модуль C15. Structured output через tool use и JSON Schema

> **Уровень:** Architect · **Время:** ~45 минут · **Формат:** ситуация → теория → практика → квиз
>
> **Цель экзамена CCAR-F:** 4.3 — Enforce structured output using tool use and JSON schemas

---

## 🏢 Ситуация

Новый продукт: система извлечения данных из документов поставщиков. Счета, акты, спецификации — двадцать разных форматов от разных контрагентов, дальше в ERP.

Первая версия просила модель «вернуть JSON» и парсила ответ. Смотрите статистику за неделю:

- **8%** ответов не парсятся: то запятая лишняя, то текст «Вот извлечённые данные:» перед JSON, то ```-обёртка.
- **12%** парсятся, но поля не те: сумма попала в `tax`, дата поставки в `invoice_date`.
- **6%** содержат выдуманные значения: у поставщика в счёте нет ИНН, а в JSON он есть — правдоподобный, но несуществующий.
- Тип документа заранее неизвестен, а схемы для счёта и акта разные. Сейчас команда угадывает по имени файла.

Даша, которая ведёт проект: «Мы поставили парсер поустойчивее, ошибки упали с 8% до 5%. Дальше не идёт.»

Дальше и не пойдёт: проблема не в парсере.

## 🎯 Ваша задача

1. Гарантировать соответствие схеме через tool use — и понять, какие ошибки это устраняет, а какие нет.
2. Выбрать режим `tool_choice` под ситуацию, когда тип документа неизвестен.
3. Спроектировать схему так, чтобы модель не выдумывала значения ради обязательных полей.

---

## 📚 Теория

### Tool use как механизм structured output

Тезис цели: **tool use с JSON-схемой — самый надёжный подход к гарантированно соответствующему схеме структурированному выводу; он устраняет синтаксические ошибки JSON**.

Идея простая: вы объявляете инструмент, чьи `input_schema` — это и есть схема ваших данных. Модель «вызывает» его, и то, что она передаёт в параметрах, гарантированно валидно по схеме. Никакого парсинга текста.

Разберите проценты Даши по этому разделению: 8% синтаксических ошибок tool use снимает полностью. 12% «поля не те» и 6% выдуманных значений — не снимает: это семантика.

### tool_choice под задачу

Три режима вы уже видели в модуле C8, здесь они применяются к извлечению:

| Режим | Поведение | Когда |
| --- | --- | --- |
| `"auto"` | модель может вернуть текст вместо вызова | не годится для извлечения |
| `"any"` | обязана вызвать инструмент, но выбирает какой | **тип документа неизвестен**, схем несколько |
| `{"type": "tool", "name": "..."}` | вызывает именно этот | тип известен либо нужен фиксированный первый шаг |

Ответ на четвёртую проблему Даши — `"any"`: объявляете инструмент на каждый тип документа (`extract_invoice`, `extract_delivery_note`, `extract_spec`), и модель сама выбирает подходящий, но **обязана** вернуть структуру. Угадывание по имени файла уходит.

Принудительный выбор конкретного инструмента остаётся для случая «сначала `extract_metadata`, потом обогащение» — тот же приём, что в C8.

### Дизайн схемы: три приёма

**1. Опциональные (nullable) поля там, где данных может не быть.** Это прямой ответ на выдуманный ИНН. Если поле обязательное, а в документе его нет, модель вынуждена что-то положить — и кладёт правдоподобное. Гайд формулирует это как навык: **делать поля опциональными, когда исходные документы могут не содержать информации, чтобы модель не фабриковала значения ради обязательных полей**.

**2. Значение `"unclear"` в enum для неоднозначных случаев.** Та же логика на уровне перечислений: если в списке нет варианта «непонятно», модель выберет ближайший — и вы даже не узнаете, что она сомневалась.

**3. Паттерн `"other"` + строка с деталями** для расширяемых категорий. Классификатор с закрытым списком на реальных данных рано или поздно встретит то, чего в списке нет. `"other"` плюс `other_detail` сохраняет и корректность, и информацию — а заодно даёт материал для расширения списка.

И четвёртое, не про схему: **правила нормализации формата задаются в промпте рядом со строгой схемой**. Схема скажет, что `date` — строка; что даты приводятся к `YYYY-MM-DD` независимо от того, как они выглядят в документе, скажет промпт.

## 💻 Практика

Извлечение с гарантией схемы, `tool_choice: any` для неизвестного типа и схема, спроектированная против выдумывания.

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

MONEY = {"type": "number", "description": "Сумма в рублях, точка как разделитель"}

EXTRACTORS = [
    {
        "name": "extract_invoice",
        "description": "Извлечь данные СЧЁТА на оплату. Признаки: есть итоговая сумма к оплате, "
                       "реквизиты для перечисления, номер и дата счёта.",
        "input_schema": {"type": "object", "properties": {
            "invoice_number": {"type": "string"},
            "invoice_date": {"type": "string", "description": "YYYY-MM-DD"},
            "supplier_name": {"type": "string"},
            # опционально: в счетах небольших поставщиков ИНН может отсутствовать
            "supplier_tax_id": {"type": ["string", "null"],
                                "description": "ИНН поставщика. null, если в документе его нет. "
                                               "Не выводить из названия и не угадывать."},
            "line_items": {"type": "array", "items": {"type": "object", "properties": {
                "description": {"type": "string"},
                "quantity": {"type": "number"},
                "unit_price": MONEY,
                "amount": MONEY,
            }, "required": ["description", "amount"]}},
            "stated_total": {**MONEY, "description": "Итог, КАК НАПИСАН в документе"},
            "currency": {"type": "string", "enum": ["RUB", "USD", "EUR", "other"]},
            "currency_other": {"type": ["string", "null"],
                               "description": "Заполнить, только если currency = other"},
            "payment_terms": {"type": "string", "enum": ["prepaid", "on_delivery", "net_30", "unclear"],
                              "description": "unclear — если условия в документе не указаны или неоднозначны"},
        }, "required": ["invoice_number", "supplier_name", "stated_total", "currency", "payment_terms"]},
    },
    {
        "name": "extract_delivery_note",
        "description": "Извлечь данные НАКЛАДНОЙ или акта приёмки. Признаки: перечень отгруженного, "
                       "подписи сторон, отсутствие требования оплаты.",
        "input_schema": {"type": "object", "properties": {
            "note_number": {"type": "string"},
            "delivery_date": {"type": "string", "description": "YYYY-MM-DD"},
            "supplier_name": {"type": "string"},
            "items": {"type": "array", "items": {"type": "object", "properties": {
                "description": {"type": "string"}, "quantity": {"type": "number"},
            }, "required": ["description", "quantity"]}},
            "accepted_by": {"type": ["string", "null"],
                            "description": "ФИО принявшего. null, если подпись не расшифрована."},
        }, "required": ["note_number", "supplier_name", "items"]},
    },
]

NORMALIZATION = """
Правила нормализации (применяй независимо от того, как выглядит документ):
— даты приводи к YYYY-MM-DD; «14.08.2026», «14 августа 2026 г.» и «2026/08/14» → «2026-08-14»;
— суммы возвращай числом без разделителей разрядов: «1 234,56» → 1234.56;
— если значение в документе отсутствует, а поле допускает null — верни null;
   НЕ выводи значение из других полей и не подставляй правдоподобное;
— если категория не подходит ни под один вариант enum, выбери "other"/"unclear"
   и заполни соответствующее поле с деталями.
"""

def extract(document: str) -> tuple[str, dict]:
    """tool_choice: any — тип документа неизвестен, но структура обязана вернуться."""
    resp = client.messages.create(
        model=MODEL, max_tokens=2000, tools=EXTRACTORS,
        tool_choice={"type": "any"},
        messages=[{"role": "user", "content": NORMALIZATION + f"\n\nДокумент:\n{document}"}])
    block = next(b for b in resp.content if b.type == "tool_use")
    return block.name, block.input

DOC = """
                          СЧЁТ № 4412 от 14 августа 2026 г.
Поставщик: ООО «Стройкомплект»
Наименование                Кол-во   Цена      Сумма
Профиль стальной 40х40       120     185,00    22 200,00
Крепёж монтажный             400      37,50    15 000,00
                                      Итого:   37 200,00
Оплата в течение 30 дней с даты счёта.
"""

if __name__ == "__main__":
    name, data = extract(DOC)
    print(f"выбран инструмент: {name}")
    print(json.dumps(data, ensure_ascii=False, indent=2))
    # ИНН в документе отсутствует — ожидаем null, а не выдуманное значение
    print("\nsupplier_tax_id:", data.get("supplier_tax_id"))
```

**Задание.**

1. Сделайте `supplier_tax_id` обязательной строкой (уберите `null` из типа и добавьте в `required`) и прогоните тот же документ пять раз. Посчитайте, сколько раз появился выдуманный ИНН. Это ровно 6% Даши.
2. Замените `tool_choice` на `"auto"` и подайте документ, который трудно классифицировать. Посмотрите, сколько ответов вернулись текстом вместо вызова.
3. Уберите `"unclear"` из `payment_terms` и подайте счёт без указания условий оплаты. Модель выберет что-то — проверьте, что именно, и подумайте, как бы вы узнали об этом в проде.
4. Уберите блок `NORMALIZATION` и подайте три документа с разными форматами дат. Схема останется соблюдённой, а данные — разнородными: это и есть граница между формой и смыслом.

## 🎯 На экзамене

- **Цель 4.3** закрыта: tool use со схемой как самый надёжный способ, различие трёх режимов `tool_choice`, устранение синтаксических ошибок при сохранении семантических, дизайн схемы (обязательные против опциональных, `"unclear"`, `"other"` + детали), нормализация в промпте рядом со схемой.
- Сценарий: **Structured Data Extraction** — построен вокруг этой цели целиком.
- Ключевая ловушка: вариант «строгая схема гарантирует корректность данных». Гайд отдельно подчёркивает, что схема устраняет синтаксические ошибки, но **не предотвращает семантические** — несходящиеся суммы, значения не в тех полях.
- Ловушка про `tool_choice`: при неизвестном типе документа и нескольких схемах правильный ответ — `"any"`. Вариант `"auto"` оставляет модели возможность вернуть текст, вариант с принудительным именем требует знать тип заранее.
- Ловушка про выдуманные значения: варианты «добавить в промпт запрет выдумывать» или «понизить температуру». Ожидаемый ответ — сделать поле опциональным (nullable), чтобы модель не была вынуждена его заполнять.
- Про enum помните два паттерна: `"unclear"` для неоднозначности и `"other"` + строка деталей для расширяемых категорий.

## 📌 Запомнить

- Structured output получают через tool use с JSON-схемой в `input_schema`, а не парсингом текста. Синтаксические ошибки исчезают как класс.
- Схема гарантирует форму, но не смысл: суммы могут не сходиться, значения — стоять не в тех полях.
- `"auto"` допускает текст вместо вызова; `"any"` гарантирует вызов при неизвестном типе документа; принудительный выбор фиксирует конкретный инструмент.
- Обязательное поле, которого нет в источнике, — прямое приглашение к выдумыванию. Такие поля делают nullable.
- В enum добавляют `"unclear"` для неоднозначных случаев и `"other"` со строкой деталей для расширяемых категорий.
- Правила нормализации формата живут в промпте рядом со схемой: схема про типы, промпт про приведение к виду.
