## 🏢 Ситуация

Полгода работы. Система стабильна, откаты есть, инцидентов почти нет. И именно в этот момент Марина задаёт неудобный вопрос:

> «Доля писем без правок — 78%. Столько же было в феврале. Мы полгода что-то улучшаем, а число стоит. Мы вообще движемся?»

Вы открываете свои задачи за квартал: чинили промпт после жалобы Игоря, добавили проверку после инцидента с «1С», подкрутили температуру, потому что Даше показалось суховато. Всё это — реакции на отдельные случаи. Ни одна не была выбрана потому, что она **самая частая или самая дорогая**.

Игорь тем временем правит письма каждый день — и его правки нигде не сохраняются. Самый ценный сигнал о качестве уходит в мусор.

## 🎯 Ваша задача

1. Собирать обратную связь так, чтобы она превращалась в данные, а не в ощущения.
2. Классифицировать ошибки по типам, чтобы чинить классы, а не случаи.
3. Выбирать, что чинить, по частоте и цене, а не по громкости жалобы.

## 📚 Теория

### Обратная связь: три источника, разная цена

| Источник | Что даёт | Сколько стоит собрать |
| --- | --- | --- |
| **Неявный сигнал** — правки человека перед отправкой | Точный, объёмный, без просьб | Почти ноль: нужно лишь сохранять diff |
| **Явный сигнал** — 👍/👎 с причиной | Разметка причины, редкие случаи | Секунды человека, но не все жмут |
| **Исход** — ответы, встречи, сделки | Единственная правда о ценности | Задержка в недели, шум от рынка |

Ошибка большинства команд — строить только третье и мучиться от задержки, игнорируя первое. **Правка перед отправкой — это готовая разметка**: было / стало / кто правил / когда. Её достаточно, чтобы понять, что систематически не так.

Правило для типов ошибок: их **должно быть 5–8**, они должны различаться способом починки. «Плохое письмо» — не тип. «Зацепка не связана с событием лида» — тип, потому что понятно, что делать: чинить сборщик контекста или требовать источник для зацепки.

### Еженедельный разбор: тридцать минут, которые двигают продукт

Формат, который работает:

1. **Числа** (5 минут): доля правок, отказов, эскалаций, срабатываний проверок, стоимость — по сравнению с прошлой неделей.
2. **Топ-3 типа ошибок** (10 минут): что выросло, что упало и почему.
3. **Пять случайных прогонов** (10 минут): читаем целиком, включая хорошие. Именно здесь находятся вещи, которых нет в метриках.
4. **Одно решение** (5 минут): что чиним на следующей неделе и как поймём, что помогло.

Ключевое — пункт 4 в единственном числе. Три параллельные правки означают, что вы не узнаете, какая сработала.

### Замыкание петли

Правка → тип ошибки → кейс в golden set (A6) → изменение → канарейка (A16) → измерение → снова правки. Петля замкнута, когда **каждый шаг автоматический, кроме решения, что чинить**. Это решение остаётся за человеком, потому что оно про приоритеты бизнеса, а не про данные.

## 💻 Практика

```python
import os, json, difflib, collections, datetime as dt, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

ERROR_TYPES = [
    "weak_hook",        # зацепка общая или не связана с событием лида
    "too_long",         # длиннее нужного
    "wrong_tone",       # тон не подходит адресату
    "stale_fact",       # факт о продукте устарел
    "hallucination",    # утверждение, которого нет в фактах
    "wrong_recipient",  # письмо не тому человеку / не в той стадии
    "formatting",       # структура, приветствие, подпись
]

CLASSIFY_TOOL = {
    "name": "classify_edit",
    "input_schema": {"type": "object", "properties": {
        "types": {"type": "array", "items": {"type": "string", "enum": ERROR_TYPES}},
        "severity": {"type": "string", "enum": ["cosmetic", "material", "harmful"]},
        "note": {"type": "string", "description": "Что именно исправил человек, одной фразой"},
    }, "required": ["types", "severity", "note"]},
}


def capture_edit(trace_id, lead_id, original, final, editor):
    """Самый ценный сигнал: правка перед отправкой. Сохраняем всегда."""
    if original.strip() == final.strip():
        return None                                  # отправлено без правок — тоже данные
    diff = "\n".join(difflib.unified_diff(
        original.splitlines(), final.splitlines(), lineterm="", n=1))
    resp = client.messages.create(
        model=MODELS["small"], max_tokens=400, temperature=0,
        system="Ты классифицируешь правку, которую человек внёс в черновик письма перед "
               "отправкой. Определи типы проблем исходного текста. Всегда вызывай classify_edit.",
        tools=[CLASSIFY_TOOL], tool_choice={"type": "tool", "name": "classify_edit"},
        messages=[{"role": "user", "content": f"БЫЛО:\n{original}\n\nСТАЛО:\n{final}\n\nDIFF:\n{diff}"}])
    cls = next(b for b in resp.content if b.type == "tool_use").input
    store_feedback({"trace_id": trace_id, "lead_id": lead_id, "editor": editor,
                    "diff": diff, "types": cls["types"], "severity": cls["severity"],
                    "note": cls["note"], "at": dt.datetime.now(dt.timezone.utc).isoformat()})
    return cls


# Цена типа ошибки: во сколько обходится один случай (заполняется командой, не моделью)
COST_WEIGHT = {"weak_hook": 1, "too_long": 1, "wrong_tone": 1, "formatting": 0.5,
               "stale_fact": 5, "wrong_recipient": 8, "hallucination": 20}

def weekly_report(days=7):
    fb = load_feedback(days)
    total_runs = count_runs(days)
    counter = collections.Counter(t for f in fb for t in f["types"])

    rows = []
    for etype, n in counter.items():
        rows.append({
            "тип": etype,
            "случаев": n,
            "доля_прогонов": round(n / max(total_runs, 1), 3),
            "приоритет": round(n * COST_WEIGHT.get(etype, 1), 1),   # частота × цена
        })
    rows.sort(key=lambda r: -r["приоритет"])

    return {
        "прогонов": total_runs,
        "правок": len(fb),
        "доля_без_правок": round(1 - len(fb) / max(total_runs, 1), 3),
        "по_типам": rows,
        "чинить_первым": rows[0]["тип"] if rows else None,
    }


def promote_worst_to_golden(limit=5):
    """Худшие случаи недели автоматически становятся кейсами набора (A6, A14)."""
    fb = sorted(load_feedback(7), key=lambda f: -COST_WEIGHT.get(f["types"][0], 1))[:limit]
    for f in fb:
        promote_to_golden(f["trace_id"],
                          name=f"{f['types'][0]} · {f['at'][:10]}",
                          expectation=f["note"])
    return len(fb)


if __name__ == "__main__":
    rep = weekly_report()
    print(f"Без правок: {rep['доля_без_правок']:.0%} на {rep['прогонов']} прогонах")
    for r in rep["по_типам"][:5]:
        print(f"  {r['тип']:16} {r['случаев']:4} случаев · доля {r['доля_прогонов']:.1%} "
              f"· приоритет {r['приоритет']}")
    print("Чиним на этой неделе:", rep["чинить_первым"])
    print("Добавлено кейсов в golden set:", promote_worst_to_golden())
```

Что меняется после первого же отчёта:

1. **Ответ Марине становится содержательным.** Не «78%, как в феврале», а «доля правок по слабой зацепке выросла с 30% до 41% — это и есть наш потолок».
2. **Приоритет считается, а не обсуждается.** «Выдумка» — 6% случаев, но с весом 20 она обгоняет «не тот тон» с 15%.
3. **Правки перестают пропадать.** Каждый вечер Игорь, сам того не зная, размечает данные.
4. **Худшие случаи недели автоматически едут в golden set** — набор растёт сам, без отдельной дисциплины.
5. **Одно решение в неделю.** Через квартал у вас есть история: что меняли, что это дало.

**Задание.** Соберите правки за последнюю неделю (даже если руками, из почты) и разложите по типам. Посчитайте частоту × цену. Почти наверняка первое место займёт не то, что вы чинили последним.

## 📌 Запомнить

- Правка человека перед отправкой — самый дешёвый и точный сигнал качества. Сохраняйте её всегда.
- Типов ошибок должно быть 5–8, и они различаются способом починки, а не формулировкой.
- Приоритет = частота × цена. Громкость жалобы к приоритету отношения не имеет.
- Еженедельный разбор: числа, топ типов, пять случайных прогонов целиком, одно решение.
- Одно изменение за раз — иначе вы не узнаете, какое из них помогло.
- Петля замкнута, когда автоматизировано всё, кроме решения, что чинить. Это решение — человеческое.
