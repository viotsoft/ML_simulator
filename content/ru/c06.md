> **Уровень:** Foundations · **Время:** ~45 минут · **Формат:** ситуация → теория → практика → квиз
>
> **Цель экзамена CCAR-F:** 1.6 — Design task decomposition strategies for complex workflows

---

## 🏢 Ситуация

Две задачи приходят в один день, и обе выглядят как «прогони через агента».

**Первая.** Костя ставит автоматическое ревью на пул-реквесты. Первый большой PR — 18 файлов, 2400 строк. Агент получает весь дифф одним куском и возвращает шесть замечаний, все про первые два файла. Про остальные шестнадцать — тишина. При этом самый неприятный дефект был как раз межфайловый: в `payments/refund.py` изменили сигнатуру, а в `support/handlers.py` вызов остался старый.

**Вторая.** Виктор просит: «покройте тестами биллинг, там 40 тысяч строк без единого теста, и я нервничаю». Костя предлагает план: пройти по файлам по алфавиту и написать тесты. Вы смотрите на список файлов и понимаете, что первые тридцать — это конфиги и константы, а весь риск сидит в трёх модулях, про которые вы пока даже не знаете, в каких именно.

Задачи разные, и **стратегия декомпозиции у них тоже должна быть разной** — это и есть содержание последней цели первого домена.

## 🎯 Ваша задача

1. Различить два паттерна: фиксированный конвейер (prompt chaining) и динамическую адаптивную декомпозицию.
2. Разложить ревью большого PR так, чтобы межфайловый дефект не потерялся.
3. Построить план для открытой задачи, который сначала изучает структуру, а потом решает, что делать.

**Prompt chaining** — цепочка заранее известных шагов. Каждый шаг получает результат предыдущего. Подходит там, где список аспектов фиксирован: ревью по безопасности → по стилю → по покрытию тестами. Предсказуемо, дёшево, легко отлаживается.

**Динамическая адаптивная декомпозиция** — подзадачи создаются на основе промежуточных находок. Первый шаг — разведка, дальше план строится по её результатам и продолжает меняться, когда обнаруживаются зависимости. Дороже, но только так решаются задачи, где вы заранее не знаете, из чего они состоят.

### Ревью большого PR: локально + межфайловый проход

Проблема Кости называется **размытием внимания** (attention dilution): чем больше материала в одном запросе, тем поверхностнее разбор каждой его части. Шесть замечаний по первым двум файлам — классический симптом.

Гайд даёт конкретный рецепт:

```
Проход 1 (локальный, по файлу — параллельно):
  payments/refund.py     → замечания внутри файла
  support/handlers.py    → замечания внутри файла
  ... ещё 16 файлов
        │
        ▼
Проход 2 (межфайловый, отдельный):
  на вход — сводки локальных проходов и список изменённых сигнатур
  ищем: рассогласованные вызовы, циклические зависимости, разъехавшиеся контракты
```

Ключевое слово — **отдельный** межфайловый проход. Его нельзя «дописать» в конец локального: локальный видит один файл, а межфайловый дефект по определению живёт между ними. Именно поэтому изменённую сигнатуру в `refund.py` не поймал бы ни один локальный проход, каким бы внимательным он ни был.

### Открытая задача: сначала карта, потом план

Для «покройте тестами легаси» гайд описывает последовательность из трёх шагов, и её стоит запомнить как рецепт:

1. **Составить карту структуры** — что за модули, как связаны, где входные точки.
2. **Найти зоны высокого влияния** — где чаще меняют код, где идут деньги, где падает прод.
3. **Построить приоритизированный план, который адаптируется** по мере обнаружения зависимостей.

Третий пункт — не украшение. Когда вы возьмётесь за тесты для модуля возвратов, выяснится, что он зависит от четырёх других, и половина из них требует моков, которых нет. План обязан это впитать — иначе он развалится на второй неделе.

Алфавитный обход Кости — это конвейер, применённый к задаче, для которой он не предназначен: он тратит первые тридцать шагов на конфиги и не имеет способа узнать, что три модуля важнее остальных вместе взятых.

## 💻 Практика

Оба паттерна в одном файле: цепочка для предсказуемого ревью и адаптивный планировщик для открытой задачи.

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

def ask(prompt: str, system: str = "", max_tokens: int = 1500) -> str:
    resp = client.messages.create(model=MODEL, max_tokens=max_tokens, system=system,
                                  messages=[{"role": "user", "content": prompt}])
    return "".join(b.text for b in resp.content if b.type == "text")

# ---------- паттерн 1: prompt chaining для ревью ----------
def review_pr(files: dict[str, str]) -> dict:
    """Локальный проход по каждому файлу + ОТДЕЛЬНЫЙ межфайловый проход."""
    local = {}
    for path, diff in files.items():                       # параллелится тривиально
        local[path] = ask(
            f"Ревью изменений в одном файле.\n\nФайл: {path}\n```\n{diff}\n```\n"
            "Верни только замечания по этому файлу. Отдельно перечисли изменённые "
            "публичные сигнатуры в формате `имя(параметры)` — они понадобятся на следующем шаге.",
            system="Ты ревьюер. Замечания конкретные, с указанием строк. Без общих советов.")

    # межфайловый проход получает сводки, а не полный дифф: внимание не размывается
    summaries = "\n\n".join(f"### {p}\n{r}" for p, r in local.items())
    cross = ask(
        f"Сводки локального ревью по {len(files)} файлам:\n\n{summaries}\n\n"
        "Найди проблемы, которые невозможно увидеть внутри одного файла: "
        "вызовы с устаревшей сигнатурой, разъехавшиеся контракты, циклические зависимости, "
        "изменения, требующие правки в другом месте. Если таких нет — так и напиши.",
        system="Ты архитектурный ревьюер. Тебя интересуют только межфайловые несогласованности.")
    return {"local": local, "cross_file": cross}

# ---------- паттерн 2: динамическая декомпозиция ----------
PLAN_TOOL = [{
    "name": "submit_plan",
    "description": "Приоритизированный план работ, адаптируемый по мере находок.",
    "input_schema": {"type": "object", "properties": {
        "high_impact_areas": {"type": "array", "items": {"type": "string"},
                              "description": "Где сосредоточен риск и почему"},
        "tasks": {"type": "array", "items": {"type": "object", "properties": {
            "target": {"type": "string"},
            "why": {"type": "string"},
            "priority": {"type": "integer"},
            "depends_on": {"type": "array", "items": {"type": "string"},
                           "description": "Что должно быть сделано раньше"},
        }, "required": ["target", "why", "priority"]}},
        "open_questions": {"type": "array", "items": {"type": "string"},
                           "description": "Что выяснится только в процессе и может изменить план"},
    }, "required": ["high_impact_areas", "tasks"]},
}]

def plan_open_ended(goal: str, structure_map: str) -> dict:
    """Шаг 1 — карта структуры (передана). Шаг 2 — зоны влияния. Шаг 3 — адаптируемый план."""
    resp = client.messages.create(
        model=MODEL, max_tokens=2000, tools=PLAN_TOOL,
        tool_choice={"type": "tool", "name": "submit_plan"},
        messages=[{"role": "user", "content":
            f"Цель: {goal}\n\nКарта структуры:\n{structure_map}\n\n"
            "Не иди по файлам подряд. Сначала определи, где сосредоточен риск "
            "(деньги, частые изменения, внешние интеграции), и приоритизируй по нему. "
            "В open_questions вынеси то, что способно изменить план по ходу работы."}],
    )
    return next(b.input for b in resp.content if b.type == "tool_use")

if __name__ == "__main__":
    pr = {
        "payments/refund.py": "- def refund(order_id):\n+ def refund(order_id, reason, actor_id):\n      ...",
        "support/handlers.py": "  def on_refund_request(req):\n      return refund(req.order_id)",
        "config/limits.py": "- REFUND_LIMIT = 500\n+ REFUND_LIMIT = 5000",
    }
    r = review_pr(pr)
    print("=== МЕЖФАЙЛОВЫЙ ПРОХОД ===")
    print(r["cross_file"][:800])

    print("\n=== ПЛАН ДЛЯ ОТКРЫТОЙ ЗАДАЧИ ===")
    plan = plan_open_ended(
        "Покрыть тестами биллинговый модуль (40 тыс. строк, тестов нет)",
        "billing/\n  refunds.py (вызывается из support, gateway, admin)\n"
        "  gateway_client.py (внешний API, ретраи)\n  invoices.py\n"
        "  constants.py\n  formatters.py\n  ... ещё 28 файлов утилит")
    print(json.dumps(plan, ensure_ascii=False, indent=2)[:900])
```

**Задание.**

1. Уберите межфайловый проход и убедитесь, что рассогласование `refund(order_id)` против новой сигнатуры не находится ни одним локальным ревью. Это дефект из ситуации.
2. Скормите весь дифф одним запросом вместо локальных проходов и сравните, сколько файлов реально получили замечания. Так выглядит размытие внимания.
3. Замените в `plan_open_ended` инструкцию на «пройди по файлам в алфавитном порядке» и посмотрите, куда уйдут первые пять задач плана.

## 🎯 На экзамене

- **Цель 1.6** закрыта: prompt chaining против динамической декомпозиции, правило выбора, локальные + межфайловый проходы, трёхшаговый рецепт для открытых задач.
- Сценарии: **Claude Code for Continuous Integration** (ревью больших PR), **Developer Productivity with Claude** (легаси, тесты, исследование незнакомого кода).
- Ловушка: «увеличить контекстное окно / отдать весь PR одним запросом, раз он влезает». Влезает — не значит разбирается: размытие внимания названо в гайде отдельно.
- Ловушка: «добавить проверку межфайловых зависимостей в промпт локального прохода». Локальный проход видит один файл; нужен **отдельный** межфайловый проход.
- Для открытых задач ответ почти всегда содержит порядок: **сначала карта структуры, потом зоны высокого влияния, потом приоритизированный адаптируемый план** — а не «начать писать тесты с первого файла».

## 📌 Запомнить

- Список шагов известен заранее — prompt chaining. Список шагов зависит от находок — динамическая декомпозиция.
- Большое ревью режется на локальные проходы по файлам **плюс отдельный межфайловый проход**. Без второго межфайловые дефекты не находятся никогда.
- Размытие внимания — реальный эффект: чем больше в одном запросе, тем поверхностнее разбор каждой части.
- Открытая задача решается в порядке: карта структуры → зоны высокого влияния → приоритизированный план.
- План для открытой задачи обязан адаптироваться: зависимости обнаруживаются по ходу, и жёсткий план ломается на них.
