>
> **Цель экзамена CCAR-F:** 4.4 — Implement validation, retry, and feedback loops for extraction quality

---

## 🏢 Ситуация

Синтаксические ошибки после C15 исчезли. Остались те самые 12% и 6% — семантика. Даша приносит три конкретных случая из продакшена.

**Случай 1.** Счёт с четырьмя позициями: 22 200 + 15 000 + 3 400 + 900. В извлечении `stated_total: 37 200` — как в документе, а сумма позиций 41 500. В документе опечатка поставщика, но система об этом не знает и отправляет в ERP несходящийся счёт.

**Случай 2.** Извлечение упало на валидации: дата поставки в неверном формате. Система повторила запрос — с тем же промптом и тем же документом. Пять раз. Результат тот же.

**Случай 3.** Обязательное поле `contract_number` пустое в 30% документов. Система ретраит каждый такой документ трижды. Разбираетесь: номера договора в этих счетах нет — он в приложении к рамочному договору, которого системе никто не давал. Ретраи не помогут никогда.

И отдельно, из ревью кода (модуль C14): Костя говорит, что разработчики отклоняют находки, но понять закономерность невозможно — в отклонённых замечаниях нет ничего, по чему их можно сгруппировать.

## 🎯 Ваша задача

1. Построить цикл «валидация → конкретная ошибка → повтор» вместо слепых ретраев.
2. Научиться отличать случаи, где ретрай поможет, от случаев, где он бесполезен.
3. Спроектировать самопроверку в самой схеме и добавить поле, по которому можно анализировать ложные срабатывания.

## 📚 Теория

### Ретрай с обратной связью об ошибке

Ключевой приём: при повторе к промпту **добавляются конкретные ошибки валидации**. Не «попробуй ещё раз», а «вот документ, вот твой предыдущий ответ, вот что в нём не так».

Экзамен требует уметь **определять, когда ретраи бесполезны**: если нужная информация просто отсутствует в исходном документе, повторять нечего. Случай 3 у Даши — ровно это: тридцать процентов документов уходят в трёхкратный ретрай ради поля, которого в них физически нет. Правильная реакция — вернуть `null` (см. дизайн схемы в C15) и пометить документ как требующий дополнительного источника.

### Самопроверка, встроенная в схему

Случай 1 — несходящаяся сумма — решается изящным приёмом из гайда: **извлекать `calculated_total` рядом со `stated_total`**, чтобы расхождение стало видимым.

```json
{
  "stated_total": 37200.00,      ← как написано в документе
  "calculated_total": 41500.00,  ← сумма позиций, посчитанная моделью
  "totals_match": false,
  "conflict_detected": true,
  "conflict_note": "Сумма позиций превышает заявленный итог на 4300"
}
```

Ни одно из этих полей не «валидирует» в строгом смысле — валидацию делает ваш код, сравнивая два числа. Но схема заставляет модель **выписать оба значения явно**, и расхождение из невидимого становится проверяемым одной строкой кода.

Второй вариант того же приёма — булево **`conflict_detected`** для противоречивых исходных данных: в шапке одна дата, в подписи другая; в позициях валюта USD, в итоге RUB.

### detected_pattern: анализ ложных срабатываний

Проблема Кости из ревью решается отдельным полем. Гайд называет навык прямо: **добавлять поле `detected_pattern` в структурированные находки, чтобы анализировать ложные срабатывания, когда разработчики отклоняют замечания**.

Смысл в том, что находка перестаёт быть уникальным текстом и получает **машиночитаемую метку конструкции**, которая её вызвала:

```json
{
  "category": "correctness",
  "message": "Возможна потеря исключения при таймауте",
  "detected_pattern": "broad_except_with_return_default"
}
```

Теперь отклонённые находки группируются: «паттерн `broad_except_with_return_default` отклонён 34 раза из 36» — и вы точно знаете, какой few-shot пример добавить (модуль C14). Без метки у вас есть только 214 разных текстов и никакой закономерности.

### Различие, которое легко забыть

| Тип ошибки | Кто устраняет |
| --- | --- |
| Синтаксис JSON | tool use со схемой (C15) — исчезает как класс |
| Семантика: не сходится, не туда, противоречит | валидация в коде + ретрай с обратной связью |

Это продолжение того же тезиса, что и в C15: схема про форму, валидация про смысл.

## 💻 Практика

Полный цикл: извлечение → валидация → ретрай с конкретными ошибками → решение о безнадёжности.

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

EXTRACT_TOOL = [{
    "name": "extract_invoice",
    "description": "Извлечь данные счёта.",
    "input_schema": {"type": "object", "properties": {
        "invoice_number": {"type": "string"},
        "invoice_date": {"type": "string", "description": "строго YYYY-MM-DD"},
        "line_items": {"type": "array", "items": {"type": "object", "properties": {
            "description": {"type": "string"}, "amount": {"type": "number"},
        }, "required": ["description", "amount"]}},
        "stated_total": {"type": "number", "description": "Итог, КАК НАПИСАН в документе"},
        # самопроверка внутри схемы
        "calculated_total": {"type": "number",
                             "description": "Сумма amount всех позиций, посчитанная тобой. "
                                            "Считай честно, даже если расходится со stated_total."},
        "conflict_detected": {"type": "boolean",
                              "description": "true, если в документе есть противоречивые данные "
                                             "(разные даты, разные валюты, несходящиеся суммы)"},
        "conflict_note": {"type": ["string", "null"], "description": "Чем именно противоречат данные"},
        "contract_number": {"type": ["string", "null"],
                            "description": "Номер договора. null, если в ЭТОМ документе его нет."},
    }, "required": ["invoice_number", "invoice_date", "line_items",
                    "stated_total", "calculated_total", "conflict_detected"]},
}]

import re
def validate(data: dict) -> list[str]:
    """Семантическая валидация: то, что схема гарантировать не может."""
    errors = []
    if not re.fullmatch(r"\d{4}-\d{2}-\d{2}", data.get("invoice_date", "")):
        errors.append(f"invoice_date = {data.get('invoice_date')!r}: требуется формат YYYY-MM-DD")
    s, c = data.get("stated_total"), data.get("calculated_total")
    items_sum = round(sum(i["amount"] for i in data.get("line_items", [])), 2)
    if c is not None and abs(c - items_sum) > 0.01:
        errors.append(f"calculated_total = {c}, но сумма позиций = {items_sum}: пересчитай")
    if s is not None and c is not None and abs(s - c) > 0.01 and not data.get("conflict_detected"):
        errors.append(f"stated_total = {s} не равен calculated_total = {c}, "
                      "но conflict_detected = false: отметь расхождение")
    return errors

# Отсутствие данных — не ошибка валидации: ретраить бессмысленно
def missing_from_source(data: dict) -> list[str]:
    return [k for k in ("contract_number",) if data.get(k) is None]

def extract_with_retry(document: str, max_attempts: int = 3):
    messages = [{"role": "user", "content": f"Извлеки данные счёта.\n\nДокумент:\n{document}"}]
    for attempt in range(1, max_attempts + 1):
        resp = client.messages.create(model=MODEL, max_tokens=2000, tools=EXTRACT_TOOL,
                                      tool_choice={"type": "tool", "name": "extract_invoice"},
                                      messages=messages)
        data = next(b.input for b in resp.content if b.type == "tool_use")
        errors = validate(data)
        print(f"  попытка {attempt}: ошибок валидации — {len(errors)}")
        if not errors:
            return {"data": data, "attempts": attempt,
                    "needs_external_source": missing_from_source(data)}

        # Ретрай С ОБРАТНОЙ СВЯЗЬЮ: документ + неудачное извлечение + конкретные ошибки
        messages = [
            {"role": "user", "content": f"Извлеки данные счёта.\n\nДокумент:\n{document}"},
            {"role": "assistant", "content": resp.content},
            {"role": "user", "content":
                "Извлечение не прошло валидацию. Ошибки:\n"
                + "\n".join(f"— {e}" for e in errors)
                + "\n\nИсправь именно их. Остальные поля оставь как есть. "
                  "Если данных в документе нет — верни null, не выдумывай."},
        ]
    return {"data": data, "attempts": max_attempts, "unresolved": errors}

DOC = """
СЧЁТ № 4412 от 14.08.2026
Профиль стальной        22 200,00
Крепёж монтажный        15 000,00
Доставка                 3 400,00
Упаковка                   900,00
                Итого:  37 200,00
"""

if __name__ == "__main__":
    r = extract_with_retry(DOC)
    d = r["data"]
    print(f"\nstated_total     : {d['stated_total']}")
    print(f"calculated_total : {d['calculated_total']}")
    print(f"conflict_detected: {d['conflict_detected']} — {d.get('conflict_note')}")
    print(f"попыток          : {r['attempts']}")
    if r.get("needs_external_source"):
        print(f"⚠ нужен внешний источник для полей: {r['needs_external_source']} — ретраи не помогут")
```

**Задание.**

1. Замените ретрай с обратной связью на слепой повтор (`messages` не меняются между попытками) и подайте документ с датой в формате `14/08/26`. Посчитайте, сколько попыток уйдёт впустую.
2. Уберите `calculated_total` из схемы и проверьте, заметит ли система несходящийся счёт вообще. Это случай 1 Дашы.
3. Добавьте в схему обязательное `contract_number` (без `null`) и подайте документ без него. Сравните поведение с текущим вариантом: сколько ретраев и что в итоге в поле.
4. Добавьте в находки ревью из модуля C14 поле `detected_pattern` с перечислением ваших категорий конструкций. Прогоните на десяти диффах и сгруппируйте по паттерну — станет видно, какие few-shot примеры нужны в первую очередь.

## 🎯 На экзамене

- **Цель 4.4** закрыта: ретрай с обратной связью об ошибке, границы применимости ретраев, `detected_pattern` для анализа отклонений, самопроверка через `calculated_total`/`stated_total` и `conflict_detected`, различие семантических ошибок и синтаксических.
- Сценарий: **Structured Data Extraction**, частично **Claude Code for Continuous Integration** (анализ ложных срабатываний).
- Ловушка про ретраи: вариант «увеличить число попыток» или «добавить экспоненциальную задержку», когда информации нет в документе. Ожидаемый ответ — распознать, что ретраи бесполезны, и запросить другой источник.
- Ловушка про повтор: «повторить запрос с той же формулировкой» против «включить в повтор исходный документ, неудачное извлечение и конкретные ошибки». Второе.
- Ловушка про сходимость сумм: вариант «добавить в промпт просьбу проверять арифметику». Приём гайда конкретнее — извлекать посчитанный итог рядом с заявленным, чтобы расхождение стало данными.
- Про `detected_pattern` помните мотивацию: без машиночитаемой метки отклонённые находки нельзя сгруппировать и систематически проанализировать.

## 📌 Запомнить

- Повтор без обратной связи — это тот же запрос: модель не знает, что было не так, и отвечает так же.
- В повтор кладут исходный документ, неудачное извлечение и **конкретные** ошибки валидации.
- Ретрай помогает при несовпадении формата и структурных ошибках вывода. Если сведений нет в источнике — не помогает никогда, нужен другой документ.
- `calculated_total` рядом со `stated_total` превращает невидимое расхождение в проверяемое поле. `conflict_detected` делает то же для противоречивых данных.
- `detected_pattern` в находках позволяет группировать отклонённые замечания и системно бороться с ложными срабатываниями.
- Схема снимает синтаксис, валидация в коде — семантику. Это разные слои, и второй не исчезает вместе с первым.
