## 🏢 Ситуация

Ревью в CI запущено правильно (C13): `-p`, схема вывода, прошлые находки в контексте. И всё равно команда его игнорирует.

Костя приносит цифры за месяц: из 214 замечаний разработчики приняли 61. Разбираете по категориям:

| Категория | Замечаний | Принято |
| --- | --- | --- |
| Безопасность | 18 | 16 |
| Логические ошибки | 44 | 33 |
| Устаревшие комментарии | 87 | 4 |
| Стиль именования | 65 | 8 |

Две категории тянут вниз всё остальное. Хуже того, разработчики теперь просматривают комментарии по диагонали — и пропускают те самые шестнадцать замечаний по безопасности, ради которых всё затевалось.

Смотрите промпт. Про комментарии там сказано: «проверь, что комментарии точны». Про стиль: «сообщай о нарушениях именования». А в конце Костя дописал: «будь консервативен, сообщай только о находках, в которых уверен».

Отдельно — вторая проблема. Формат замечаний плавает: иногда «файл:строка — проблема», иногда абзац рассуждения, иногда список из пяти пунктов с предложением в конце. Скрипт публикации это переживает благодаря схеме, а человек — нет.

## 🎯 Ваша задача

1. Заменить расплывчатые инструкции категориальными критериями.
2. Понять, почему «будь консервативен» не работает — и что делать с категорией, которая портит доверие.
3. Добиться единообразия вывода few-shot примерами, а не более длинным описанием.

Первый тезис цели 4.1: **явные критерии сильнее расплывчатых инструкций**. Канонический пример гайда — ровно проблема Кости:

```
❌ «проверь, что комментарии точны»
✅ «сообщай о комментарии, только если заявленное в нём поведение
   противоречит фактическому поведению кода»
```

Второй тезис, менее очевидный: **общие указания вроде «будь консервативен» или «сообщай только о находках с высокой уверенностью» не улучшают точность** по сравнению с конкретными категориальными критериями. Модель не имеет калиброванного порога «уверенности», который можно подкрутить словом. Работает не фильтр по уверенности, а определение того, **что считается проблемой**.

Отсюда практический навык: писать критерии, которые перечисляют, о чём сообщать (ошибки, безопасность) и что пропускать (мелкий стиль, локальные паттерны проекта), — вместо попыток отфильтровать по уверенности.

Третий тезис — про доверие. **Высокая доля ложных срабатываний в одной категории подрывает доверие к точным категориям.** Поэтому у гайда есть отдельный навык: **временно отключить проблемную категорию**, чтобы вернуть доверие, и параллельно чинить её промпт. Это не поражение, а управление вниманием людей.

И четвёртый приём: **явные критерии серьёзности с конкретными примерами кода на каждый уровень**. «Blocker», «major», «minor» без примеров каждый раз классифицируются по-новому.

### Few-shot: когда описания недостаточно

Вторая проблема Кости — плавающий формат. Здесь работает цель 4.2, и её первый тезис категоричен: **few-shot примеры — самый действенный приём для единообразно отформатированного, применимого вывода, когда подробные инструкции сами по себе дают непоследовательный результат**.

Что показывают примерами:

- **желаемый формат вывода** — расположение, проблема, серьёзность, предлагаемое исправление;
- **обработку неоднозначных случаев** — и, важно, **рассуждение**, почему выбрано одно действие, а не правдоподобная альтернатива;
- **границу между приемлемым паттерном и настоящей проблемой** — это снижает ложные срабатывания;
- **разные структуры документов** — цитаты внутри текста против списка литературы, раздел методологии против деталей, размазанных по тексту;
- **корректное извлечение из документов разного формата** — против пустых значений в обязательных полях.

Объём: **2–4 целевых примера**. Не двадцать: смысл не в покрытии случаев, а в передаче принципа.

Важнейшее свойство, которое экзамен проверяет отдельно: few-shot примеры позволяют модели **обобщать суждение на новые паттерны**, а не только сопоставлять с заранее перечисленными случаями. Поэтому пример с рассуждением сильнее примера без него: он передаёт критерий, а не запись.

```
Пример (приемлемый паттерн, НЕ сообщать):
  код:   except Exception: logger.warning(...); return default
  разбор: в этом проекте graceful degradation — принятый паттерн для
          внешних вызовов, исключение логируется. Это не проглатывание ошибки.

Пример (настоящая проблема, сообщать):
  код:   except Exception: pass
  разбор: исключение не логируется и не обрабатывается — сбой станет невидимым.
          Серьёзность major: данные не теряются, но диагностика невозможна.
```

Два примера рядом задают границу лучше, чем абзац описания: модель видит не список запретов, а признак, по которому они различаются.

## 💻 Практика

Промпт ревью с явными критериями и few-shot. Сравните его с формулировкой «проверь, что комментарии точны».

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

CRITERIA = """
Сообщай о находках ТОЛЬКО в этих категориях:

1. security — ввод пользователя попадает в запрос/команду без экранирования;
   секрет в коде; отсутствие проверки прав перед операцией над чужими данными.
2. correctness — код не делает того, что должен: неверное условие, потерянная
   ветка, необработанный краевой случай с конкретным входом, который его вызовет.
3. stale_comment — сообщай ТОЛЬКО если заявленное в комментарии поведение
   противоречит фактическому поведению кода. Неполный, устаревший по стилю или
   просто короткий комментарий — не находка.

НЕ сообщай: именование, форматирование, порядок импортов, предпочтения по стилю,
локальные паттерны проекта, «можно было бы сделать элегантнее».

Серьёзность:
  blocker — приводит к потере данных, утечке или падению прода.
            Пример: SQL-запрос со склейкой пользовательского ввода.
  major   — неверное поведение на реальном входе, диагностика невозможна.
            Пример: except Exception: pass в обработчике платежа.
  minor   — верное поведение, но повышенный риск при следующем изменении.
            Пример: магическое число вместо константы в условии лимита.
"""

FEW_SHOT = """
Примеры разбора. Обрати внимание на рассуждение: важен признак, а не совпадение.

Пример 1 — приемлемый паттерн, НЕ сообщать:
  код:  try: rate = fx.get(cur)
        except TimeoutError: logger.warning("fx timeout, using cached"); rate = cached(cur)
  вывод: находки нет. Исключение узкое, залогировано, есть осмысленный фолбэк —
         это управляемая деградация, а не проглоченная ошибка.

Пример 2 — настоящая проблема, сообщать:
  код:  try: charge(card, amount)
        except Exception: pass
  вывод: {"category": "correctness", "severity": "major",
          "message": "Сбой списания проглатывается: исключение не логируется и не
                      пробрасывается, платёж молча не проходит",
          "suggestion": "Логировать с суммой и id операции, пробросить наверх"}

Пример 3 — неоднозначный комментарий, НЕ сообщать:
  код:  # возвращает список активных пользователей
        def active_users(limit=None): ...
  вывод: находки нет. Комментарий неполон (не упомянут limit), но не противоречит
         поведению. Критерий stale_comment требует противоречия.

Пример 4 — комментарий противоречит коду, сообщать:
  код:  # таймаут 30 секунд
        client = Client(timeout=5)
  вывод: {"category": "stale_comment", "severity": "minor",
          "message": "Комментарий заявляет таймаут 30 секунд, в коде 5",
          "suggestion": "Привести комментарий в соответствие или вернуть 30"}
"""

SCHEMA_TOOL = [{
    "name": "submit_findings",
    "description": "Отправить результаты ревью.",
    "input_schema": {"type": "object", "properties": {
        "findings": {"type": "array", "items": {"type": "object", "properties": {
            "file": {"type": "string"}, "line": {"type": "integer"},
            "category": {"type": "string", "enum": ["security", "correctness", "stale_comment"]},
            "severity": {"type": "string", "enum": ["blocker", "major", "minor"]},
            "message": {"type": "string"}, "suggestion": {"type": "string"},
        }, "required": ["file", "line", "category", "severity", "message"]}},
    }, "required": ["findings"]},
}]

def review(diff: str, *, with_criteria=True, with_few_shot=True) -> dict:
    system = CRITERIA if with_criteria else (
        "Отревьюй код. Проверь, что комментарии точны, и сообщи о нарушениях именования. "
        "Будь консервативен, сообщай только о находках, в которых уверен.")
    prompt = (FEW_SHOT + "\n\n" if with_few_shot else "") + f"Дифф:\n```\n{diff}\n```"
    resp = client.messages.create(
        model=MODEL, max_tokens=2000, system=system, tools=SCHEMA_TOOL,
        tool_choice={"type": "tool", "name": "submit_findings"},
        messages=[{"role": "user", "content": prompt}])
    return next(b.input for b in resp.content if b.type == "tool_use")

DIFF = """
--- a/billing/charge.py
+++ b/billing/charge.py
@@
+# повторяет попытку до 3 раз
+def charge_with_retry(card, amount):
+    for _ in range(2):
+        try:
+            return charge(card, amount)
+        except Exception:
+            pass
+    return None
+
+def find_invoice(user_input):
+    return db.query("SELECT * FROM invoices WHERE ref = '" + user_input + "'")
"""

if __name__ == "__main__":
    for label, kw in [("критерии + few-shot", {}),
                      ("только критерии", {"with_few_shot": False}),
                      ("расплывчато", {"with_criteria": False, "with_few_shot": False})]:
        r = review(DIFF, **kw)
        cats = [f"{f['category']}/{f['severity']}" for f in r["findings"]]
        print(f"{label:22} → {len(r['findings'])} находок: {cats}")
```

**Задание.**

1. Прогоните три конфигурации по пять раз. Сравните не только число находок, но и стабильность: находится ли SQL-склейка каждый раз, а комментарий «повторяет до 3 раз» при цикле на 2 итерации — классифицируется ли одинаково.
2. Уберите из `CRITERIA` блок про серьёзность с примерами и посмотрите, как поплывёт классификация одной и той же находки между прогонами.
3. Добавьте пятый few-shot пример — приемлемый паттерн из вашего проекта, который агент раньше помечал ошибочно. Проверьте, что модель обобщила признак, а не запомнила конкретный код: подсуньте похожий, но не идентичный фрагмент.

## 🎯 На экзамене

- **Цель 4.1**: явные критерии против расплывчатых инструкций, бесполезность «будь консервативен», влияние ложных срабатываний на доверие, временное отключение слабой категории, критерии серьёзности с примерами кода.
- **Цель 4.2**: few-shot как самый действенный приём для единообразия, 2–4 целевых примера, показ рассуждения, обобщение на новые паттерны, различение приемлемых паттернов и настоящих проблем, разные структуры документов, борьба с пустыми полями при извлечении.
- Сценарии: **Claude Code for Continuous Integration** (ложные срабатывания в ревью) и **Structured Data Extraction** (few-shot против галлюцинаций и пустых полей).
- Главная ловушка 4.1: вариант «добавить в промпт „сообщай только при высокой уверенности“». Гайд прямо называет это неработающим по сравнению с категориальными критериями.
- Вторая ловушка 4.1: «убрать категорию навсегда» против «временно отключить и чинить промпт». Ожидается второе.
- Ловушка 4.2: «написать более детальную инструкцию по формату». Если инструкции уже подробные, а результат непоследовательный — ответ few-shot.
- Ещё ловушка 4.2: «добавить примеры на все возможные случаи». Гайд говорит про 2–4 целевых примера и про обобщение, а не про покрытие.

## 📌 Запомнить

- Критерий должен быть проверяемым и категориальным: «противоречит фактическому поведению», а не «неточен».
- «Будь консервативен» и «только уверенные находки» не повышают точность. Повышает — определение того, что считается проблемой, и что пропускать.
- Одна шумная категория обесценивает точные. Её временно отключают и чинят промпт, а не терпят.
- Уровни серьёзности задают примерами кода, иначе классификация плавает между прогонами.
- Когда подробные инструкции дают непоследовательный результат — нужны few-shot примеры, а не более подробные инструкции.
- 2–4 примера, обязательно с рассуждением, зачем выбрано это, а не правдоподобная альтернатива. Так модель обобщает, а не запоминает.
- Пара примеров «приемлемый паттерн против настоящей проблемы» — самый прямой способ сбить ложные срабатывания.
