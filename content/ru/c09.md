## 🏢 Ситуация

К вам приходит новый разработчик, Артём, с задачей: «переименовать функцию `calculate_refund` и починить всех её вызывающих». Он открывает Claude Code и через сорок минут приходит обратно:

> «Оно прочитало восемьдесят файлов, съело весь контекст и в итоге предложило переименовать не там. И ещё Edit у него падает с ошибкой про неуникальный текст, он теперь боится трогать файл.»

Вы смотрите транскрипт и видите три отдельные ошибки выбора инструмента:

1. **Разведка чтением.** Агент начал с `Read` по всем файлам подряд, чтобы «понять кодовую базу». Восемьдесят файлов, из которых относятся к делу четыре.
2. **Поиск не тем инструментом.** Чтобы найти вызовы, он перебирал файлы по имени через `Glob`, надеясь угадать, где они лежат.
3. **Edit без плана Б.** Строка `return calculate_refund(order)` встречается в файле трижды, `Edit` не может выбрать якорь и падает. Артём решил, что файл «сломанный».

Ни одна из этих ошибок не про модель. Все три — про то, какой инструмент чему предназначен. Это самая приземлённая цель второго домена и одна из самых частых на экзамене.

## 🎯 Ваша задача

1. Разложить по полочкам, что ищет `Grep`, а что — `Glob`.
2. Понять, когда `Edit`, а когда `Read` + `Write`.
3. Построить правильный порядок исследования незнакомого кода.

**`Grep` — поиск по содержимому.** Имена функций, сообщения об ошибках, строки импорта. «Найди всех, кто вызывает `calculate_refund`» — это `Grep`.

**`Glob` — поиск по шаблону пути.** «Найди все файлы `**/*.test.tsx`» — это `Glob`. Он ничего не знает о содержимом.

**`Read` / `Write`** — работа с файлом целиком. **`Edit`** — точечное изменение по уникальному совпадению текста.

**`Bash`** — всё остальное: запустить тесты, посмотреть git-историю, выполнить команду.

### Когда Edit падает

`Edit` находит место по уникальному тексту-якорю. Если строка встречается в файле несколько раз, однозначного места нет, и правка не проходит. Это не поломка файла — это отсутствие уникального якоря.

Гайд даёт конкретный запасной путь: **`Read` + `Write`**. Прочитать файл целиком, изменить нужное место в известном контексте, записать обратно. Второй, более элегантный вариант — расширить якорь, включив в него окружающие строки, чтобы совпадение стало уникальным. Оба подхода лучше, чем сдаваться.

### Порядок исследования: Grep → Read → правка

Ошибка Артёма номер один — самая дорогая. Гайд формулирует навык явно: **строить понимание кодовой базы инкрементально — начинать с `Grep`, чтобы найти точки входа, затем `Read`, чтобы пройти по импортам и трассировать потоки, вместо чтения всех файлов заранее**.

Разница драматическая:

```
❌ Прочитать 80 файлов → контекст забит, понимания нет
✅ Grep "calculate_refund" → 6 файлов → Read этих шести → понятно всё
```

И отдельный приём для сквозных переименований, который гайд описывает пошагово: **сначала найти все экспортируемые имена, потом искать каждое имя по кодовой базе**. Это нужно, когда функция проходит через модули-обёртки: `calculate_refund` может экспортироваться как `refund` в `__init__.py`, и прямой поиск исходного имени не найдёт половину вызовов.

## 💻 Практика

Здесь практика идёт не в Python, а в самом Claude Code — на этом репозитории. Все команды безопасны, ничего не меняют.

**Упражнение 1. Grep против Glob.** В сессии Claude Code в корне проекта попросите:

```
Найди все места, где вызывается countPassed — только через поиск по содержимому,
не читая файлы целиком. Покажи, какой инструмент использовал.
```

Затем:

```
Найди все markdown-файлы агентного трека по шаблону имени. Какой инструмент здесь правильный?
```

Первое — `Grep` (содержимое), второе — `Glob` (пути). Обратите внимание, что `Grep` находит вызовы, даже не зная, в каких файлах искать.

**Упражнение 2. Правильный порядок исследования.** Два запроса в разных сессиях, сравните расход контекста:

```
Сессия A: Прочитай все файлы в public/js/ и content/, потом объясни,
          как устроено разделение треков.
Сессия B: Объясни, как устроено разделение треков. Начни с поиска по содержимому,
          читай только те файлы, которые действительно нужны.
```

Сессия B обычно укладывается в 4–6 чтений вместо десятков — и ответ получается точнее, потому что внимание не размыто (тот же эффект, что в модуле C6).

**Упражнение 3. Неуникальный якорь.** Найдите в `public/js/app.js` строку, которая встречается несколько раз, — например, `bindSectionTabs();`. Попросите:

```
Замени третье вхождение bindSectionTabs() на bindSectionTabs(); // проверка
```

Посмотрите, как агент справится: расширит якорь окружающими строками либо прочитает файл целиком и запишет обратно. Оба пути правильные; вариант «сдаться» — нет.

**Упражнение 4. Сквозное переименование через обёртки.** Попросите:

```
Функция gradeQuiz в server.js вызывается из нескольких мест. Сначала найди все
имена, под которыми она экспортируется или переприсваивается, затем поиском
по каждому имени собери полный список вызывающих. Ничего не меняй.
```

Это ровно тот двухшаговый приём из гайда: сначала список имён, потом поиск по каждому.

## 📌 Запомнить

- `Grep` — внутрь файлов, `Glob` — по именам файлов. Это первое, что проверяют вопросы этой цели.
- `Edit` работает по уникальному текстовому якорю. Неуникальное совпадение — не ошибка файла, а отсутствие якоря.
- Запасной путь при неуникальном совпадении — `Read` + `Write` (либо расширить якорь окружающим контекстом).
- Кодовую базу изучают инкрементально: `Grep` находит точки входа, `Read` идёт по импортам. Массовое чтение заранее тратит контекст и не даёт понимания.
- Для сквозной трассировки через обёртки сначала собирают все экспортируемые имена, потом ищут каждое.
