# Модуль A9. Инструменты и интеграции

> **Уровень:** Middle AI · **Время:** ~55 минут · **Формат:** ситуация → теория → практика → квиз

---

## 🏢 Ситуация

Игорь приходит с очевидной просьбой:

> «Агент пишет письма, я их отправляю, а потом руками записываю в CRM: отправил, ответил, договорились созвониться. Полчаса в день на копипаст. Пусть он сам пишет в CRM.»

Просьба разумная. Но за ней стоит переход, который вы ещё не делали: до сих пор агент только **читал** и **генерировал**. Теперь он будет **менять состояние в чужой системе**.

Через час к вам заходит Оля из юридического:

> «Мне сказали, вы даёте роботу доступ в CRM. Какими правами? Кто увидит персональные данные? Что будет, если он удалит сделку? Мне нужен ответ до того, как это заработает, а не после.»

Правильные вопросы. Ответы на них — это и есть модуль.

## 🎯 Ваша задача

1. Дать агенту инструменты записи так, чтобы худший случай был терпимым.
2. Разобраться с секретами: агент не должен видеть ваш API-ключ от CRM.
3. Понять, что такое MCP и когда он избавляет от написания интеграций.

## 📚 Теория

### Инструмент — это API вашей системы для модели

Описание инструмента — не документация для человека, а контракт. Три правила, которые экономят недели отладки:

1. **Узкая задача.** Не `crm_update(entity, field, value)`, а `crm_log_reply(lead_id, category, note)`. Широкий инструмент = широкий класс ошибок.
2. **Описание объясняет, когда вызывать.** «Записать ответ лида в CRM. Вызывать только после того, как ответ классифицирован» — модель читает это как инструкцию.
3. **Ошибка возвращается текстом, а не исключением.** Модель должна увидеть «лид не найден» и попробовать иначе, а не уронить процесс.

### Секреты не попадают в модель

Ключ от CRM живёт в вашем сервисе, а не в контексте модели. Модель вызывает `crm_log_reply(lead_id=...)`, ваш код подставляет токен и делает запрос. Модель никогда не видит ключ — значит, не может его случайно процитировать в письме и не отдаст его при инъекции.

Отсюда же правило про идентификаторы: агент оперирует `lead_id`, а не почтой и телефоном клиента. Персональные данные в контекст попадают только те, что нужны для задачи.

### Идемпотентность записи

Ретрай (из A2) плюс запись = двойные записи в CRM. Решение — ключ идемпотентности: `f"{lead_id}:{message_id}"`. Повторный вызов с тем же ключом не создаёт вторую заметку, а возвращает первую. Без этого повтор после таймаута удваивает данные, и никто не поймёт почему.

### MCP: когда не писать интеграцию руками

**Model Context Protocol** — стандарт, по которому инструменты описываются один раз и подключаются к любому клиенту. Смысл прост: вместо того чтобы писать обёртки над каждым API под каждого агента, вы подключаете готовый MCP-сервер (или пишете один свой, и он работает везде).

Когда полезен: типовые системы, где сервер уже существует; несколько агентов над одними и теми же инструментами; желание отделить владельца интеграции от владельца агента.

Когда нет: одна-две узкие операции — своя функция на 20 строк проще; и помните, что MCP не отменяет ни прав, ни идемпотентности, ни журналирования.

## 💻 Практика

```python
import os, json, hashlib, requests, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

# Секреты живут здесь и никогда не попадают в контекст модели
CRM_TOKEN = os.environ["CRM_AGENT_TOKEN"]      # токен ТЕХНИЧЕСКОГО пользователя с урезанной ролью
CRM_URL = os.environ["CRM_URL"]

# --- Узкие инструменты: одна операция — один инструмент ---
TOOLS = [
    {"name": "crm_get_lead",
     "description": "Получить карточку лида по id. Возвращает только рабочие поля, "
                    "без персональных контактов.",
     "input_schema": {"type": "object", "properties": {"lead_id": {"type": "string"}},
                      "required": ["lead_id"]}},
    {"name": "crm_log_reply",
     "description": "Записать в CRM результат разбора ответа лида. Вызывать только после "
                    "классификации ответа. Повторный вызов с тем же message_id безопасен.",
     "input_schema": {"type": "object", "properties": {
         "lead_id": {"type": "string"},
         "message_id": {"type": "string", "description": "id письма — ключ идемпотентности"},
         "category": {"type": "string", "enum": CATEGORIES},     # из A3
         "note": {"type": "string", "description": "Одно предложение для менеджера"},
         "follow_up_date": {"type": ["string", "null"]},
     }, "required": ["lead_id", "message_id", "category", "note"]}},
    # Инструмента crm_delete_lead здесь нет и не будет — ответ на вопрос Оли
]

SAFE_FIELDS = {"id", "company", "industry", "stage", "owner", "last_touch_at"}

def crm_get_lead(lead_id):
    r = requests.get(f"{CRM_URL}/leads/{lead_id}",
                     headers={"Authorization": f"Bearer {CRM_TOKEN}"}, timeout=10)
    if r.status_code == 404:
        return {"error": "лид не найден"}          # ошибка возвращается модели текстом
    r.raise_for_status()
    data = r.json()
    return {k: v for k, v in data.items() if k in SAFE_FIELDS}   # фильтр персональных данных


def crm_log_reply(lead_id, message_id, category, note, follow_up_date=None):
    # Ключ идемпотентности: повтор после таймаута не создаст вторую заметку
    key = hashlib.sha256(f"{lead_id}:{message_id}".encode()).hexdigest()[:32]
    r = requests.post(
        f"{CRM_URL}/leads/{lead_id}/notes",
        headers={"Authorization": f"Bearer {CRM_TOKEN}", "Idempotency-Key": key},
        json={"category": category, "note": note[:500], "follow_up_date": follow_up_date,
              "author": "agent:outreach"},         # видно, что запись сделал робот
        timeout=10)
    if r.status_code == 409:
        return {"ok": True, "note": "запись уже существовала (идемпотентность)"}
    if r.status_code == 403:
        return {"error": "нет прав на эту операцию"}   # модель увидит и не будет пытаться снова
    r.raise_for_status()
    return {"ok": True, "note_id": r.json()["id"]}


IMPL = {"crm_get_lead": crm_get_lead, "crm_log_reply": crm_log_reply}

def run_tool(name, args):
    try:
        return json.dumps(IMPL[name](**args), ensure_ascii=False)
    except Exception as e:
        # Модель должна увидеть ошибку как результат, а не получить падение процесса
        return json.dumps({"error": f"{type(e).__name__}: {e}"}, ensure_ascii=False)


def process_reply(lead_id, message_id, email_text):
    messages = [{"role": "user", "content":
                 f"lead_id={lead_id}, message_id={message_id}\nПисьмо:\n{email_text}\n"
                 "Разбери ответ и запиши результат в CRM."}]
    for _ in range(5):                                    # лимит цикла из A7
        resp = client.messages.create(model=MODEL, max_tokens=800, tools=TOOLS, messages=messages)
        if resp.stop_reason != "tool_use":
            return resp.content[0].text
        messages.append({"role": "assistant", "content": resp.content})
        messages.append({"role": "user", "content": [
            {"type": "tool_result", "tool_use_id": b.id, "content": run_tool(b.name, b.input)}
            for b in resp.content if b.type == "tool_use"]})
    return "остановлен по лимиту шагов"
```

Что здесь важно и что вы отвечаете Оле:

1. **Отдельный технический пользователь** с урезанной ролью. В журнале CRM видно `agent:outreach` — понятно, кто автор записи.
2. **Удалить сделку он не может:** такого инструмента нет и роль этого не позволяет. Ограничение на уровне возможностей, а не просьбы в промпте.
3. **Персональные контакты не попадают в контекст** — фильтр `SAFE_FIELDS` на выходе чтения.
4. **Ключ идемпотентности** делает повторы безопасными: ретрай после таймаута не удвоит записи.
5. **Ошибки возвращаются модели текстом.** Она видит «нет прав» и не зацикливается на попытках.

**Задание.** Составьте для своей CRM три списка: что агент читает, что пишет, что запрещено навсегда. Для каждого пункта из второго списка напишите, как вы откатите ошибку. Пункт, для которого нет ответа, переезжает в третий список.

## 📌 Запомнить

- Инструмент — узкий контракт: одна операция, описание с условием вызова, ошибки текстом.
- Права проектируют от худшего случая. Чего нельзя делать никогда — для того не должно быть инструмента.
- Секреты живут в вашем коде, а не в контексте модели: агент оперирует id, а не ключами и контактами.
- Любая запись во внешнюю систему идемпотентна, иначе ретраи удваивают данные.
- Действия агента идут от отдельного технического пользователя — в журнале видно, что сделал робот.
- MCP избавляет от написания одинаковых интеграций, но не отменяет права, идемпотентность и журнал.

**Что почитать:** спецификация Model Context Protocol; практики least privilege из OWASP; документация вашей CRM по идемпотентным запросам и техническим пользователям.
