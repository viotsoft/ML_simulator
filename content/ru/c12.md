# Модуль C12. Plan mode против прямого исполнения

> **Уровень:** Practitioner · **Время:** ~50 минут · **Формат:** ситуация → теория → практика → квиз
>
> **Цели экзамена CCAR-F:** 3.4 — Determine when to use plan mode vs direct execution · 3.5 — Apply iterative refinement techniques for progressive improvement

---

## 🏢 Ситуация

Понедельник, две задачи в очереди, и вы наблюдаете, как команда решает обе неправильно — в противоположных направлениях.

**Задача первая.** Артём получил стектрейс: в `formatInvoice` падает на пустой дате. Правка на две строки, файл один. Артём открывает plan mode, агент двадцать минут исследует репозиторий, выдаёт план на страницу, Артём его утверждает — и агент делает те же две строки. Полчаса на однострочную защиту.

**Задача вторая.** Костя мигрирует биллинг с одной библиотеки платежей на другую: 45 файлов, два способа интеграции с разной инфраструктурой. Он пишет «замени везде» и запускает напрямую. Через час — 45 изменённых файлов, выбран способ, требующий вебхук-эндпоинта, которого нет, и половина правок нерабочая. Откат.

К вечеру добавляется третья история. Даша просит агента написать нормализатор адресов: «приводи адреса к единому виду». Три итерации, три разных представления о «едином виде». На четвёртой она пишет пять примеров «вход → выход» — и получает то, что нужно, с первого раза.

## 🎯 Ваша задача

1. Сформулировать критерий выбора между планированием и прямым исполнением.
2. Понять роль субагента Explore в многофазных задачах.
3. Освоить четыре приёма итеративного уточнения — и правило, когда чинить всё разом, а когда по одному.

**Plan mode** нужен, когда есть хотя бы одно из четырёх: масштабные изменения, несколько допустимых подходов, архитектурные последствия, правки во многих файлах. Его смысл — **безопасное исследование и проектирование до того, как что-то изменено**, чтобы не платить за переделку.

**Прямое исполнение** — для простых изменений с ясной областью: одна функция, понятный стектрейс, очевидное решение.

И третий вариант, который экзамен упоминает отдельно: **комбинация**. Спланировать миграцию в plan mode, выбрать подход — затем выполнить выбранное прямым исполнением. Именно этого не хватило Косте.

### Субагент Explore

В многофазных задачах есть отдельная проблема: фаза разведки многословна. Обход репозитория, чтение файлов, поиск зависимостей — всё это забивает контекст ещё до того, как начнётся работа.

Решение — **субагент Explore**: он изолирует многословный вывод разведки и возвращает в основной разговор **сводку**. Механика та же, что у `context: fork` в модуле C11, только применённая к фазе исследования.

Это прямо связано с plan mode: планирование по определению начинается с разведки, и без изоляции контекст может кончиться раньше, чем появится план.

### Четыре приёма итеративного уточнения

Третья история — про Дашу и «единый вид» адресов. Гайд перечисляет приёмы, и первый из них — её решение.

**1. Конкретные примеры «вход → выход».** Самый действенный способ передать ожидаемое преобразование, когда проза интерпретируется по-разному. Два-три примера снимают неоднозначность, которую не снимет ни один абзац описания:

```
"ул. Ленина д.5 кв.12"     → {street: "Ленина", building: "5", apartment: "12"}
"Ленина 5-12"              → {street: "Ленина", building: "5", apartment: "12"}
"пр-т Мира, 18, стр. 2"    → {street: "Мира", building: "18", block: "2"}
```

**2. Итерация через тесты.** Сначала пишется набор тестов — ожидаемое поведение, краевые случаи, требования к производительности, — потом реализация, и дальше вы **делитесь падениями тестов** как обратной связью. Тест — это тот же пример «вход → выход», только исполняемый.

**3. Паттерн интервью.** Попросить Claude **задать вам вопросы** до реализации, чтобы всплыли соображения, которых вы не предусмотрели. Особенно полезно в незнакомой предметной области: стратегия инвалидации кэша, режимы отказа, поведение при частичном сбое — вещи, о которых вспоминают на третий день работы.

**4. Правило группировки исправлений.** Тонкий момент, который любят на экзамене:

| Ситуация | Как чинить |
| --- | --- |
| Проблемы **взаимодействуют** между собой | все в одном подробном сообщении |
| Проблемы **независимы** | последовательно, по одной |

Логика простая: если исправление одной проблемы меняет условия для другой, чинить их по очереди — значит переделывать. А независимые проблемы, сваленные в одно сообщение, размывают внимание — тот же эффект, что в модуле C6.

## 💻 Практика

Практика — в Claude Code на этом репозитории. Ничего разрушительного.

**Упражнение 1. Калибровка выбора.** Для каждой задачи решите: plan mode, прямое исполнение или комбинация. Затем выполните обе первые и сравните время.

```
A. В server.js добавить проверку, что amount в квизе — целое число.
B. Вынести хранение прогресса из data/users.json в SQLite, сохранив API.
C. Исправить опечатку в русском тексте модуля c03.
D. Добавить четвёртый трек в симулятор.
```

A и C — прямое исполнение (одно место, очевидное решение). B и D — plan mode: много файлов, архитектурные последствия, несколько допустимых подходов.

**Упражнение 2. Explore в разведке.** Задайте один и тот же вопрос двумя способами и сравните остаток контекста:

```
Способ 1: Разберись, как устроена генерация маркетингового контента,
          прочитав все файлы в marketing/.
Способ 2: Разберись, как устроена генерация маркетингового контента.
          Разведку вынеси в субагента Explore, в основную сессию верни сводку.
```

**Упражнение 3. Примеры вместо прозы.** Попросите написать функцию нормализации заголовков модулей сначала прозой:

```
Напиши функцию, которая приводит заголовки модулей к единому виду.
```

Затем — примерами:

```
Напиши функцию нормализации заголовков модулей. Примеры:
"# Модуль A1. Идея CEO"          → {track: "a", num: 1, title: "Идея CEO"}
"# Module C10. CLAUDE.md: hierarchy" → {track: "c", num: 10, title: "CLAUDE.md: hierarchy"}
"# Модуль M21. ML System Design" → {track: "m", num: 21, title: "ML System Design"}
```

Сравните, сколько итераций потребовалось до рабочего результата.

**Упражнение 4. Паттерн интервью.** Перед тем как просить реализацию, напишите:

```
Я хочу добавить кэширование отрендеренного markdown модулей на сервере.
Не пиши код. Задай мне вопросы, ответы на которые нужны, чтобы решение
не пришлось переделывать. Особенно про инвалидацию и режимы отказа.
```

Обратите внимание, сколько из заданных вопросов вы не продумали заранее.

**Упражнение 5. Группировка исправлений.** Найдите в своём коде две связанные проблемы (например, формат даты и сортировка по этой дате) и две независимые. Первые опишите одним сообщением, вторые — по очереди. Сравните, где было бы больнее сделать наоборот.

## 🎯 На экзамене

- **Цель 3.4**: критерии plan mode (масштаб, несколько подходов, архитектура, много файлов) против прямого исполнения (простое, с ясной областью), безопасное исследование до изменений, субагент Explore, комбинация «план → исполнение».
- **Цель 3.5**: примеры «вход → выход», итерация через тесты, паттерн интервью, правило группировки взаимодействующих и независимых проблем.
- Сценарии: **Code Generation with Claude Code**, **Developer Productivity with Claude**.
- Ловушка про plan mode: вариант «использовать plan mode для всех задач ради безопасности». Экзамен явно называет прямое исполнение уместным для простых изменений с ясной областью.
- Ловушка про уточнение: «переписать описание задачи подробнее». Когда проза интерпретируется по-разному, ответ — конкретные примеры входа и выхода, а не более длинная проза.
- Ловушка про группировку: варианты обычно предлагают «всегда чинить по одной проблеме за раз» или «всегда присылать всё сразу». Правильный ответ зависит от того, взаимодействуют ли проблемы.
- Про Explore помните формулировку: изолировать многословный вывод разведки и вернуть сводку, чтобы не исчерпать контекстное окно.

## 📌 Запомнить

- Plan mode — масштаб, несколько подходов, архитектура, много файлов. Прямое исполнение — понятная задача с ясной областью.
- Планирование существует, чтобы исследовать безопасно и не платить за переделку. Оно не бесплатно: на однострочной правке это чистые потери.
- Комбинация законна и часто оптимальна: планируем выбор подхода, выполняем прямым исполнением.
- Субагент Explore изолирует многословную разведку и возвращает сводку — так контекст доживает до реализации.
- Когда проза понимается по-разному, дают 2–3 примера «вход → выход». Это сильнее любого уточнённого описания.
- Тесты вперёд, потом итерации по падениям. Паттерн интервью вытаскивает вопросы, о которых вы не подумали.
- Взаимодействующие проблемы чинят одним сообщением, независимые — по очереди.
