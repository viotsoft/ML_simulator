## 🏢 Ситуация

Виктор, CFO, приносит счёт за API: 340 тысяч рублей за месяц. Разбираетесь, куда уходит.

Две крупные статьи. Первая — **предмерж-проверки**: агент ревьюит каждый PR, разработчик ждёт результата, чтобы мержить. Вторая — **ночная генерация тестов** и **еженедельный аудит документов поставщиков**: три тысячи документов по субботам, результат нужен к понедельнику.

Костя предлагает: «Перевести всё на Message Batches API, там пятьдесят процентов экономии». Вы понимаете, что половина этого предложения правильная, а вторая половина остановит разработку.

Заодно всплывает старая история. Джоб генерации кода и джоб его ревью — один процесс: агент пишет код, потом в том же контексте его проверяет. Из последних тридцати сгенерированных функций ревью не нашло ни одной проблемы. Тестировщики нашли шесть.

И третье: ревью больших PR по-прежнему даёт противоречивые замечания — в одном файле предлагает вынести общую логику, в другом ровно её же продублировать.

## 🎯 Ваша задача

1. Определить, какие нагрузки годятся для батчей, а какие нет.
2. Посчитать частоту отправки батчей под SLA и разобраться с обработкой сбоев.
3. Развести генерацию и ревью по независимым экземплярам и убрать противоречия многопроходной архитектурой.

Что нужно помнить про Message Batches API:

- **экономия 50%** по цене;
- **окно обработки до 24 часов**, **без гарантированного SLA по задержке**;
- подходит для **неблокирующих, терпимых к задержке** нагрузок: ночные отчёты, недельные аудиты, ночная генерация тестов;
- **не подходит для блокирующих** процессов — предмерж-проверок в первую очередь;
- **не поддерживает многошаговый tool calling внутри одного запроса**: выполнить инструмент по ходу и вернуть результат нельзя. Это ограничение отсекает целый класс агентных задач;
- **`custom_id`** связывает запрос и ответ в батче.

Предложение Кости надо разрезать: ночная генерация тестов и субботний аудит — в батчи; предмерж-проверки остаются синхронными, иначе разработчик будет ждать мержа сутки.

**Расчёт частоты.** Приём из гайда: если SLA 30 часов, а обработка занимает до 24, документ не может ждать отправки дольше 6 часов — отправляйте батч каждые 4 часа, оставив запас на пересылку сбойных.

**Обработка сбоев.** Повторно отправляются **только упавшие документы**, найденные по `custom_id`, — и с изменениями, устраняющими причину: например, документ, превысивший лимит контекста, разбивается на части. Слепая переотправка всего батча удваивает счёт и повторяет ту же ошибку.

**И приём, экономящий больше всего:** отладить промпт на **выборке** до запуска на большом объёме. Три тысячи документов, обработанных плохим промптом, — это три тысячи документов, которые придётся обработать ещё раз.

### Независимое ревью против самопроверки

Второй симптом — ревью, которое не находит своих же ошибок. Гайд объясняет почему: **модель сохраняет контекст рассуждений с этапа генерации, и в той же сессии менее склонна ставить под сомнение собственные решения**.

И даёт вывод, который часто выбирают неверно: **независимый экземпляр без предшествующего контекста рассуждений эффективнее ловит тонкие проблемы, чем инструкции по самопроверке или расширенное размышление**. То есть «попроси подумать ещё раз» и «включи thinking» — не замена независимому ревьюеру.

Это то же утверждение, что вы видели в модуле C13 применительно к CI, здесь оно сформулировано как архитектурный принцип.

### Многопроходное ревью

Третий симптом — противоречивые замечания. Лечение вам уже знакомо по модулю C6, но здесь у него другой акцент: **разделение на локальные проходы по файлам плюс межфайловые интеграционные проходы позволяет избежать размытия внимания И противоречивых находок**.

Противоречие возникает, когда один запрос пытается одновременно держать в голове локальный контекст двадцати файлов и общую картину. Разделение проходов снимает конфликт: локальный проход отвечает за файл, интеграционный — за поток данных между файлами.

И третий приём цели: **проходы верификации, где модель сама сообщает уверенность по каждой находке**, чтобы маршрутизировать ревью калиброванно. Находки с низкой уверенностью уходят человеку, с высокой — публикуются сразу. Подробнее калибровка разбирается в модуле C20.

## 💻 Практика

```python
# pip install anthropic
import os, json, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

# ---------- 4.5: маршрутизация нагрузки и расчёт частоты батчей ----------
def route(workload: str, blocking: bool, needs_tool_calling: bool) -> str:
    if blocking:
        return f"{workload}: синхронный API — результата ждут"
    if needs_tool_calling:
        return f"{workload}: синхронный API — батчи не поддерживают многошаговый tool calling"
    return f"{workload}: Message Batches API — экономия 50%"

def batch_interval_hours(sla_hours: float, batch_window_hours: float = 24, reserve_hours: float = 2) -> float:
    """Максимальная пауза между отправками, чтобы уложиться в SLA с запасом на пересылку."""
    return max(0.0, sla_hours - batch_window_hours - reserve_hours)

# ---------- 4.6: генерация и независимое ревью ----------
def generate(spec: str) -> str:
    resp = client.messages.create(model=MODEL, max_tokens=1500,
        system="Ты пишешь производственный Python. Только код, без объяснений.",
        messages=[{"role": "user", "content": spec}])
    return "".join(b.text for b in resp.content if b.type == "text")

def self_review(spec: str, code: str) -> str:
    """Плохой вариант: тот же контекст, что и при генерации."""
    resp = client.messages.create(model=MODEL, max_tokens=1500,
        system="Ты пишешь производственный Python. Только код, без объяснений.",
        messages=[{"role": "user", "content": spec},
                  {"role": "assistant", "content": code},
                  {"role": "user", "content": "Проверь свой код и найди проблемы."}])
    return "".join(b.text for b in resp.content if b.type == "text")

def independent_review(code: str) -> str:
    """Правильный вариант: чистый контекст, никаких рассуждений автора."""
    resp = client.messages.create(model=MODEL, max_tokens=1500,
        system="Ты ревьюер. Ты не писал этот код и не знаешь намерений автора. "
               "Ищи дефекты: краевые случаи, потерянные ошибки, гонки, неверные условия.",
        messages=[{"role": "user", "content": f"Отревьюй:\n```python\n{code}\n```"}])
    return "".join(b.text for b in resp.content if b.type == "text")

# ---------- 4.6: многопроходное ревью с самооценкой уверенности ----------
VERIFY_TOOL = [{
    "name": "submit_verified_findings",
    "description": "Находки с самооценкой уверенности для калиброванной маршрутизации.",
    "input_schema": {"type": "object", "properties": {
        "findings": {"type": "array", "items": {"type": "object", "properties": {
            "file": {"type": "string"}, "issue": {"type": "string"},
            "scope": {"type": "string", "enum": ["local", "cross_file"]},
            "confidence": {"type": "string", "enum": ["high", "medium", "low"],
                           "description": "high — дефект воспроизводим на конкретном входе; "
                                          "low — подозрение, требующее взгляда человека"},
        }, "required": ["file", "issue", "scope", "confidence"]}},
    }, "required": ["findings"]},
}]

def multi_pass_review(files: dict[str, str]) -> dict:
    local = {}
    for path, src in files.items():
        r = client.messages.create(model=MODEL, max_tokens=1200, tools=VERIFY_TOOL,
            tool_choice={"type": "tool", "name": "submit_verified_findings"},
            system="Локальный проход: только проблемы внутри этого файла. scope всегда local.",
            messages=[{"role": "user", "content": f"Файл {path}:\n```python\n{src}\n```"}])
        local[path] = next(b.input for b in r.content if b.type == "tool_use")["findings"]

    summaries = "\n".join(f"{p}: " + "; ".join(f["issue"] for f in fs) for p, fs in local.items())
    r = client.messages.create(model=MODEL, max_tokens=1200, tools=VERIFY_TOOL,
        tool_choice={"type": "tool", "name": "submit_verified_findings"},
        system="Интеграционный проход: только поток данных МЕЖДУ файлами. scope всегда cross_file. "
               "Не повторяй локальные находки.",
        messages=[{"role": "user", "content": f"Сводки локальных проходов:\n{summaries}"}])
    cross = next(b.input for b in r.content if b.type == "tool_use")["findings"]

    all_findings = [f for fs in local.values() for f in fs] + cross
    return {
        "auto_post": [f for f in all_findings if f["confidence"] == "high"],
        "to_human":  [f for f in all_findings if f["confidence"] != "high"],
    }

if __name__ == "__main__":
    print(route("предмерж-проверка PR", blocking=True, needs_tool_calling=False))
    print(route("ночная генерация тестов", blocking=False, needs_tool_calling=False))
    print(route("агент поддержки с MCP-инструментами", blocking=False, needs_tool_calling=True))
    print(f"\nSLA 30 ч → отправлять батчи не реже, чем каждые {batch_interval_hours(30)} ч")

    spec = "Напиши функцию, которая делит сумму заказа между позициями пропорционально их весу."
    code = generate(spec)
    print("\n--- самопроверка (тот же контекст) ---\n", self_review(spec, code)[:400])
    print("\n--- независимое ревью (чистый контекст) ---\n", independent_review(code)[:400])
```

**Задание.**

1. Прогоните пару «самопроверка / независимое ревью» на пяти сгенерированных функциях и сравните число найденных дефектов. Затем добавьте в самопроверку фразу «подумай особенно тщательно» и проверьте, догонит ли она независимый вариант.
2. Посчитайте `batch_interval_hours` для SLA 26, 30 и 48 часов. Обратите внимание, при каком SLA батчи перестают быть применимы вообще.
3. Отправьте в `multi_pass_review` три файла, где общая логика продублирована. Убедитесь, что противоречивое замечание («вынести» против «продублировать») не возникает: локальный проход про него не знает, а интеграционный видит оба файла.
4. Смоделируйте сбой батча: пометьте два документа как упавшие и напишите функцию, которая формирует повторный батч только из них, разбивая слишком длинные на части.

## 🎯 На экзамене

- **Цель 4.5**: экономия 50%, окно 24 часа, отсутствие SLA, применимость к неблокирующим нагрузкам, отсутствие многошагового tool calling, `custom_id`, расчёт частоты отправки под SLA, пересылка только сбойных документов, отладка промпта на выборке.
- **Цель 4.6**: ограничения самопроверки, превосходство независимого экземпляра над инструкциями и расширенным размышлением, локальные плюс интеграционные проходы против размытия внимания и противоречий, самооценка уверенности для маршрутизации.
- Сценарии: **Structured Data Extraction** (объёмы, батчи), **Claude Code for Continuous Integration** (предмерж против ночных задач, независимое ревью).
- Ловушка 4.5: «перевести все нагрузки на батчи ради экономии». Предмерж-проверка блокирует разработчика — она остаётся синхронной.
- Вторая ловушка 4.5: агентная задача с инструментами в батче. Батчи не поддерживают многошаговый tool calling внутри запроса.
- Ловушка 4.6: «добавить в промпт самопроверку» или «включить расширенное размышление» вместо второго экземпляра. Гайд прямо называет независимый экземпляр более эффективным.
- При сбое батча ожидаемый ответ — переотправить **только упавшие** по `custom_id`, с изменениями (например, разбив длинные документы), а не весь батч заново.

## 📌 Запомнить

- Батчи: −50% цены, окно до 24 часов, гарантий по задержке нет. Годятся там, где никто не ждёт.
- Блокирующие процессы и многошаговый tool calling внутри запроса — только синхронный API.
- Частота отправки считается из SLA: SLA минус окно обработки минус запас на пересылку сбойных.
- Пересылают только упавшие документы по `custom_id`, устранив причину сбоя.
- Промпт отлаживают на выборке до большого объёма — иначе платите за тысячи документов дважды.
- Сессия, сгенерировавшая код, хуже видит его дефекты. Независимый экземпляр сильнее самопроверки и расширенного размышления.
- Локальные проходы плюс интеграционный убирают и размытие внимания, и противоречивые находки.
- Самооценка уверенности в находках позволяет отправлять сомнительное человеку, а уверенное — публиковать сразу.
