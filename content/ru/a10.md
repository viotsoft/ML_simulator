## 🏢 Ситуация

Первая жалоба от клиента, а не от коллеги. Игорь пересылает:

> «Вы уже третий раз пишете мне одно и то же. В январе я ответил, что мы не рассматриваем новых поставщиков до конца года. Вы не читаете ответы?»

Проверяете: ответ января есть в CRM, категория `not_now`, дата возврата — декабрь. Всё записано правильно. Просто агент, который писал письмо в марте, ничего об этом не знал: он получил строку CRM с компанией, ролью и событием — и написал первое касание.

Агент без памяти каждый раз знакомится заново. Для человека это выглядит как неуважение.

## 🎯 Ваша задача

1. Разделить, что агент помнит в пределах одной задачи, а что — между задачами.
2. Собирать в контекст только то, что относится к делу: класть всю историю нельзя.
3. Ответить Оле из юридического: сколько и как долго вы храните и что делать по запросу на удаление.

### Больше контекста ≠ лучше

Соблазн: «окно 200 тысяч токенов, положим всю историю переписки». Три причины не делать так:

1. **Деньги.** Вы платите за каждый токен на каждом вызове. История в 20 писем на 3000 лидов — это ощутимая строка в счёте.
2. **Точность.** Модели хуже находят нужное в длинном контексте, особенно в середине. Пять релевантных фактов работают лучше двадцати страниц.
3. **Приватность.** Всё, что попало в контекст, попадает в логи, трейсы и, возможно, в письмо.

Правило: **извлекайте факты, а не храните стенограмму**. После каждого взаимодействия — короткая запись: что узнали нового о клиенте.

### Факт памяти — это структура

Не «клиент сказал, что сейчас не время», а объект: тип (`constraint`), значение (`не раньше декабря 2026`), источник (`письмо msg-4821`), дата, срок жизни. Такой факт можно отфильтровать по актуальности, показать человеку и удалить по запросу.

Особое внимание — **противоречиям**. Клиент в январе сказал «не раньше декабря», в мае написал «а давайте обсудим сейчас». Побеждает более свежий факт, но старый не стирают: он объясняет историю отношений.

### Приватность: ответ Оле

Три вопроса, на которые должен отвечать ваш дизайн памяти:

- **Что храним?** Только факты, нужные для работы. Не «клиент был груб», не здоровье, не личное.
- **Сколько?** У каждого факта — срок жизни. Ограничение по дате («не писать до декабря») живёт до этой даты плюс запас; заметка о роли — год; отписка — **вечно**, иначе вы напишете человеку снова.
- **Как удалить?** Запрос на удаление персональных данных должен выполняться одной операцией по ключу клиента — включая факты, логи и трейсы. Если это невозможно, вы не готовы к такому запросу.

## 💻 Практика

```python
import os, json, sqlite3, datetime as dt, anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-sonnet-5"

db = sqlite3.connect("memory.db")
db.execute("""CREATE TABLE IF NOT EXISTS facts (
    id INTEGER PRIMARY KEY, lead_id TEXT NOT NULL, kind TEXT NOT NULL,
    value TEXT NOT NULL, source TEXT, created_at TEXT NOT NULL,
    expires_at TEXT, superseded_by INTEGER)""")
db.execute("CREATE INDEX IF NOT EXISTS idx_lead ON facts(lead_id)")

# Срок жизни зависит от типа факта: отписка не истекает никогда
TTL_DAYS = {"constraint": 400, "role": 365, "objection": 365,
            "referral": 180, "unsubscribe": None}

EXTRACT_TOOL = {
    "name": "save_facts",
    "description": "Извлечь из письма факты о клиенте, которые пригодятся в будущем",
    "input_schema": {"type": "object", "properties": {
        "facts": {"type": "array", "items": {"type": "object", "properties": {
            "kind": {"type": "string", "enum": list(TTL_DAYS)},
            "value": {"type": "string", "description": "Факт одной фразой, без пересказа письма"},
        }, "required": ["kind", "value"]}}}, "required": ["facts"]},
}

def remember(lead_id, email_text, message_id):
    """После каждого взаимодействия — извлекаем факты, а не сохраняем стенограмму."""
    resp = client.messages.create(
        model=MODEL, max_tokens=500, temperature=0,
        system="Извлекай только факты, влияющие на будущие контакты: ограничения по времени, "
               "роль и полномочия, возражения, рекомендации других людей, отписки. "
               "Не сохраняй эмоции, здоровье и личные обстоятельства. Всегда вызывай save_facts.",
        tools=[EXTRACT_TOOL], tool_choice={"type": "tool", "name": "save_facts"},
        messages=[{"role": "user", "content": email_text}])
    facts = next(b for b in resp.content if b.type == "tool_use").input["facts"]

    now = dt.datetime.now(dt.timezone.utc)
    for f in facts:
        ttl = TTL_DAYS[f["kind"]]
        expires = (now + dt.timedelta(days=ttl)).isoformat() if ttl else None
        # Новый факт того же типа отменяет старый, но не стирает его
        db.execute("UPDATE facts SET superseded_by = -1 WHERE lead_id = ? AND kind = ? "
                   "AND superseded_by IS NULL", (lead_id, f["kind"]))
        db.execute("INSERT INTO facts (lead_id, kind, value, source, created_at, expires_at) "
                   "VALUES (?,?,?,?,?,?)",
                   (lead_id, f["kind"], f["value"], message_id, now.isoformat(), expires))
    db.commit()
    return facts


def recall(lead_id):
    """В контекст идут только актуальные факты — не вся история."""
    now = dt.datetime.now(dt.timezone.utc).isoformat()
    rows = db.execute(
        "SELECT kind, value, created_at FROM facts WHERE lead_id = ? AND superseded_by IS NULL "
        "AND (expires_at IS NULL OR expires_at > ?) ORDER BY created_at DESC LIMIT 8",
        (lead_id, now)).fetchall()
    return [{"kind": k, "value": v, "since": c[:10]} for k, v, c in rows]


def can_contact(lead_id):
    """Жёсткие блокировки проверяются кодом до генерации, а не подсказываются модели."""
    now = dt.datetime.now(dt.timezone.utc).isoformat()
    if db.execute("SELECT 1 FROM facts WHERE lead_id=? AND kind='unsubscribe'",
                  (lead_id,)).fetchone():
        return False, "клиент отписался"
    row = db.execute("SELECT value, expires_at FROM facts WHERE lead_id=? AND kind='constraint' "
                     "AND superseded_by IS NULL AND expires_at > ? ORDER BY created_at DESC LIMIT 1",
                     (lead_id, now)).fetchone()
    if row and "декабр" in row[0].lower() and dt.date.today().month < 12:
        return False, f"ограничение клиента: {row[0]}"
    return True, None


def forget(lead_id):
    """Право на забвение: одна операция удаляет всё по клиенту."""
    n = db.execute("DELETE FROM facts WHERE lead_id = ?", (lead_id,)).rowcount
    db.commit()
    purge_traces(lead_id)          # и в трейсах тоже — иначе удаление неполное
    return n


# --- Использование ---
ok, why = can_contact("lead-4821")
if not ok:
    print(f"— не пишем: {why}")           # именно это спасло бы от третьего письма
else:
    memory = recall("lead-4821")
    draft = generate_grounded(lead, ctx, memory=memory)   # факты уходят в контекст письма
```

Что здесь важно:

1. **Извлечение вместо стенограммы.** В базе — восемь коротких фактов, а не двадцать писем.
2. **Срок жизни у каждого типа.** Отписка не истекает никогда — это не оптимизация, это требование.
3. **Жёсткая проверка в коде.** `can_contact` останавливает письмо до генерации: модель не должна «решать», уважать ли ограничение клиента.
4. **История сохраняется через `superseded_by`.** Новый факт отменяет старый, но видно, что клиент передумал.
5. **`forget()` удаляет всё по ключу**, включая трейсы. Без последнего удаление формальное.

## 📌 Запомнить

- Память — это извлечённые факты со сроком жизни, а не вся переписка в контексте.
- Длинный контекст стоит денег, снижает точность и растаскивает персональные данные по логам.
- Факт памяти — структура: тип, значение, источник, дата, срок жизни. Иначе его нельзя ни отфильтровать, ни удалить.
- Противоречия решаются свежестью, но старый факт не стирают — он объясняет историю отношений.
- Жёсткие ограничения (отписка, «не раньше декабря») проверяются кодом до генерации, а не советом модели.
- Право на забвение — это одна операция по ключу клиента, включая логи и трейсы.
