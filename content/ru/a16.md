## 🏢 Ситуация

Вы нашли способ улучшить письма: новая версия промпта на golden set даёт +9% по персонализации. Выкатываете в среду утром, идёте пить кофе.

К обеду Игорь пишет: «Что-то письма стали странные. Половина нормальные, половина как будто от другого человека».

Вы смотрите: промпт v4 действительно лучше на golden set. Но в проде он встретил случаи, которых в наборе не было — лиды без события, где v3 отказывался писать, а v4 начал придумывать зацепку. Метрика выросла, продукт стал хуже.

И главное — вы не можете быстро откатиться: v4 уже записал 200 писем в очередь, часть ушла, часть ждёт подтверждения. Тимур спрашивает: «У вас вообще есть кнопка "как было вчера"?»

## 🎯 Ваша задача

1. Выкатывать изменения так, чтобы они сначала касались части трафика.
2. Иметь настоящий откат — на конфиге, а не на новом деплое.
3. Понять, что у агента версионируется не только код.

## 📚 Теория

### Что здесь вообще версия

В обычном сервисе версия — это коммит. У агента поведение задают минимум пять независимых вещей:

| Что | Меняется | Кто обычно меняет |
| --- | --- | --- |
| Код конвейера | Релизом | Инженер |
| Версия промпта | Отдельно от кода (A4) | Инженер, иногда продакт |
| Модель и её версия | Провайдером тоже! | Провайдер без вашего участия |
| Схемы инструментов | Релизом | Инженер |
| База знаний RAG | Постоянно | Маркетинг, поддержка |

Отсюда два следствия. Первое: **фиксируйте версию модели явно**, не «последняя». Второе: в трейс (A14) пишут все пять версий — иначе «что изменилось между вчера и сегодня» останется без ответа.

### Разделение выкатки и включения

Ключевая практика: **деплой ≠ релиз**. Код с новой версией промпта выкатывается выключенным, а включается конфигом. Тогда:

- откат не требует деплоя и занимает секунды;
- одна и та же сборка обслуживает обе версии, и сравнение честное;
- можно включить новую версию только для внутренних пользователей.

Для агентов это важнее, чем для обычных сервисов: вы будете переключаться туда-сюда чаще, потому что качество не бинарно.

### Идемпотентность при откате

Откат посреди работы — это состояние, в котором часть задач сделана новой версией, часть старой. Из A13 у нас есть ключи задач; здесь добавляется правило: **версия фиксируется на входе задачи и не меняется по ходу**. Задача, начатая на v4, доживает на v4, даже если глобально включили v3. Иначе получится письмо, наполовину собранное разными правилами.

## 💻 Практика

```python
import os, json, hashlib, time

# --- Конфиг выкатки: живёт вне кода, меняется без деплоя ---
# rollout.json: {"outreach_prompt": {"stable": "v3", "canary": "v4", "percent": 5,
#                                    "force_users": ["igor@datacore.io"]}}
class Rollout:
    def __init__(self, path="rollout.json", ttl=15):
        self.path, self.ttl, self._at, self._cfg = path, ttl, 0, {}

    def cfg(self, key):
        if time.time() - self._at > self.ttl:            # перечитываем без рестарта
            self._cfg = json.load(open(self.path, encoding="utf-8"))
            self._at = time.time()
        return self._cfg.get(key, {})

    def variant(self, key, unit_id, user=None):
        """Стабильное разделение: один и тот же лид всегда попадает в одну ветку."""
        c = self.cfg(key)
        if user and user in c.get("force_users", []):
            return c.get("canary", c["stable"]), "forced"
        bucket = int(hashlib.sha256(f"{key}:{unit_id}".encode()).hexdigest()[:8], 16) % 100
        if bucket < c.get("percent", 0):
            return c.get("canary", c["stable"]), "canary"
        return c["stable"], "stable"


rollout = Rollout()

# --- Версия фиксируется на входе задачи и живёт с ней до конца ---
def start_task(lead, campaign_id):
    version, branch = rollout.variant("outreach_prompt", lead["id"])
    task = {"lead": lead, "campaign_id": campaign_id,
            "pinned": {"prompt": version, "model": MODELS["large"],   # модель — явно, не «последняя»
                       "code": os.environ.get("GIT_SHA", "dev")},
            "branch": branch}
    save_task(task)
    return task


def run_task(task):
    with span("outreach", lead_id=task["lead"]["id"], **task["pinned"], branch=task["branch"]):
        # промпт берётся из зафиксированной версии, а не из текущего конфига
        system = load_prompt("outreach", task["pinned"]["prompt"])
        return build_email_with(system, task["lead"])


# --- Сравнение веток: не только качество, но и «здоровье» поведения ---
def canary_report(key, hours=24):
    rows = query_spans(name="outreach", since_hours=hours)
    out = {}
    for branch in ("stable", "canary"):
        b = [r for r in rows if r["branch"] == branch]
        if not b:
            continue
        out[branch] = {
            "прогонов": len(b),
            "отказов_генерации": round(share(b, lambda r: r["status"] == "refused"), 3),
            "правок_человеком": round(share(b, lambda r: r.get("edited")), 3),
            "срабатываний_проверок": round(share(b, lambda r: r.get("checks_failed")), 3),
            "эскалаций": round(share(b, lambda r: r.get("escalated")), 3),
            "стоимость_запуска": round(avg(b, lambda r: r["cost"]), 4),
        }
    return out


# --- Автоматический откат по стоп-условиям ---
STOP_RULES = [
    ("правок_человеком",        lambda s, c: c > s * 1.3, "правки выросли более чем на 30%"),
    ("срабатываний_проверок",   lambda s, c: c > s * 1.5, "автопроверки срабатывают чаще"),
    ("отказов_генерации",       lambda s, c: c < s * 0.5, "агент перестал отказываться — подозрительно"),
    ("стоимость_запуска",       lambda s, c: c > s * 2.0, "стоимость выросла вдвое"),
]

def guard_canary(key):
    rep = canary_report(key)
    if "canary" not in rep or rep["canary"]["прогонов"] < 30:
        return {"decision": "wait", "why": "мало данных"}
    for metric, rule, why in STOP_RULES:
        s, c = rep["stable"][metric], rep["canary"][metric]
        if rule(s, c):
            set_percent(key, 0)                       # откат конфигом, без деплоя
            alert(f"канарейка {key} откатана: {why} (stable={s}, canary={c})")
            return {"decision": "rollback", "why": why, "report": rep}
    return {"decision": "ok", "report": rep}
```

Что бы это дало в нашей истории:

1. **v4 увидели бы 5% лидов**, а не все. Игорь заметил бы странность на десяти письмах, а не на сотне.
2. **Стоп-правило про отказы поймало бы проблему автоматически.** Падение доли отказов с 12% до 1% — сигнал, что агент перестал признавать незнание, хотя качество «выросло».
3. **Откат — это `percent: 0` в конфиге**, применяется за секунды.
4. **Задачи в очереди доработали бы на своей версии**, без письма-гибрида.
5. **`force_users`** позволяет команде увидеть новую версию раньше клиентов.

**Задание.** Возьмите последнее изменение промпта и задним числом посчитайте по трейсам, как выглядели бы обе ветки: отказы, правки, стоимость. Часто оказывается, что изменение, которое приняли как улучшение, ухудшило одну из этих метрик — просто её никто не смотрел.

## 📌 Запомнить

- У агента версионируется пятёрка: код, промпт, модель, схемы инструментов и база знаний.
- Версию модели фиксируют явно: провайдер может обновить «последнюю» без вашего участия.
- Деплой и релиз разделяют: включение — конфигом, поэтому откат занимает секунды.
- Канарейку двигают по числам, а не по расписанию, и на каждой ступени смотрят не только качество.
- Резкое улучшение метрики — повод разобраться: падение доли отказов обычно означает потерю осторожности.
- Версия фиксируется на входе задачи и живёт с ней до конца, иначе получаются результаты-гибриды.
